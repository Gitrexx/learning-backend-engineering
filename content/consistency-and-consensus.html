Distributed Systems & Scaling // 03

Consistency Models, CAP & Consensus

Replication & Partitioning established that once data lives on more than one node, a write to one copy takes time to reach the others, and a reader can land on a node that hasn't caught up yet. That page named three specific staleness anomalies (read-your-writes, monotonic reads, consistent prefix reads) as symptoms. This page is about the underlying question those symptoms are all instances of: what does a distributed system actually promise about what a reader sees, how much of that promise you can afford to keep once the network fails, and how a cluster of independent machines manages to agree on anything — like who the leader even is — when failures are the normal case, not the exception.

The consistency spectrum

"Consistency" gets used loosely; precisely, it's a spectrum of guarantees about the order and recency of the values different clients are allowed to observe. Stronger guarantees are easier to reason about and strictly more expensive to provide.

Linearizability (strong consistency)
Every operation appears to take effect instantaneously at some single point between its invocation and its response, and all clients agree on that single global order — as if there were only one copy of the data and every operation touched it atomically in real time. Once a write completes, every subsequent read, by any client, on any node, must see it or something newer. This is the guarantee that matches naive intuition about "a variable," which is exactly why its absence is what surprises people in distributed systems.
Sequential consistency
All clients agree on a single global order of operations, and each client's own operations appear in that order in the sequence it issued them — but that order doesn't have to match real-time/wall-clock order across clients. Weaker than linearizability (a stale-but-consistently-stale view is allowed) but still a single agreed-upon timeline for the whole system, which is more than most real systems actually provide.
Causal consistency
Operations that are causally related — B read a value that A wrote, or B and A were issued by the same client in sequence — are seen by everyone in that same order. Operations with no causal relationship (concurrent, unrelated writes from different clients) can be observed in different orders by different readers, and that's allowed. This is the guarantee behind "you never see a reply before the comment it's replying to," the consistent-prefix-reads property from the replication page — it's a special case of causal consistency, not a separate rule.
Eventual consistency
The only promise: if writes stop, all replicas eventually converge to the same value. No promise about ordering, no promise about how long "eventually" takes, no promise about what an in-flight reader sees. The weakest useful guarantee, and the cheapest — it's what you get by default from asynchronous replication with no extra machinery.

The read-your-writes and monotonic-reads guarantees from the replication page live inside this spectrum too — they're client-centric guarantees: promises about what one specific client sees across its own requests, weaker than causal consistency (they say nothing about what a different client sees) but considerably stronger than raw eventual consistency, and cheap to provide with sticky routing rather than requiring every node to agree on a global order.

✓ Tip

Consistency is not one setting for "the database" — it's a choice you make per operation, and mature systems mix levels deliberately. A bank might read account balance linearizably before approving a transfer, but serve the transaction history list eventually consistent because a half-second-stale history is harmless. Ask "what does this specific read need to be true?" before reaching for the strongest (and slowest) option everywhere.

CAP, precisely

CAP is one of the most cited and most misquoted results in distributed systems. The informal "pick two of three" framing is wrong; here's the version that actually holds:

  • Consistency (C) — in CAP's original sense, this means linearizability: every read sees the most recent write or an error.
  • Availability (A) — every request to a non-failed node receives a (non-error) response, without guarantee that it's the most recent write.
  • Partition tolerance (P) — the system keeps operating despite the network dropping or delaying an arbitrary number of messages between nodes.

The theorem: if the network partitions, you must choose between C and A for that operation — you cannot have both. It is not a menu where you pick two; P isn't optional because networks do partition (that's the first fallacy of distributed computing, previewed on Networking & Protocols), so the real choice every system with more than one node makes, whether its designers state it or not, is: when a partition happens, does this operation refuse to answer (favor C) or answer with possibly-stale data (favor A)?

! Pitfall

"We chose AP" as a blanket description of a whole database is a category error CAP gets blamed for. CAP is a statement about behavior during a partition, and often per operation — a system can serve linearizable reads on one key path and eventually-consistent reads on another. Worse, most outages aren't a clean network split; they're a slow node, a GC pause, an overloaded link — CAP doesn't even have a category for "technically reachable but too slow to matter," which is why PACELC, next, is the more useful mental model for day-to-day design.

PACELC extends CAP with the case CAP is silent about: normal operation, no partition. It says: if Partitioned, trade off Availability vs Consistency; Else (no partition), trade off Latency vs Consistency. Even when the network is fine, a linearizable read still has to talk to a quorum or the leader before answering — that's latency you pay whether or not a partition ever happens, and it's the trade-off you're actually tuning most of the time in production, not the rarer partition case.

Quorums: R + W > N

Leaderless and tunable-consistency systems (Dynamo, Cassandra, Riak) don't hardwire a single answer to the CAP trade-off — they expose it as a per-request knob using three numbers: N (how many replicas hold the data), W (how many must acknowledge a write before it's considered successful), and R (how many must respond to a read before it's returned to the client). The load-bearing rule:

If R + W > N, every possible read quorum and every possible write quorum share at least one node in common — so any read is guaranteed to overlap the most recent successful write and see it (or a newer one).

This is the same pigeonhole argument as a majority vote: if a value was written to more than half the replicas, any other majority-sized group you sample must include at least one node that has it. R + W > N is the general form — it doesn't require either R or W alone to be a majority, only their sum to exceed N. W = N, R = 1 satisfies it (write everywhere, read anywhere is guaranteed fresh, but a single down replica blocks every write). W = 1, R = N also satisfies it (opposite trade-off). The common middle ground, R = W = (N/2 + 1), balances read and write latency/availability evenly.

i Note — sloppy quorums and hinted handoff

A strict quorum blocks a write if fewer than W of the designated N replicas are reachable, even if plenty of other healthy nodes exist elsewhere in the cluster. A sloppy quorum relaxes this: if a designated replica is down, the write goes to a different, temporarily-standing-in node instead, which forwards ("hands off") the write once the rightful replica recovers. This buys write availability during a partition at a real cost — R + W > N no longer guarantees overlap, because the write might have landed somewhere a normal read quorum never looks. It's an explicit AP choice, not a free upgrade.

Consensus: getting machines to agree

Quorums answer "did enough replicas see this write." Consensus answers a harder question: how do a set of nodes agree on a single, ordered sequence of values — a replicated log — when nodes can crash, restart, and messages can be delayed or lost, without ever disagreeing about what was decided? This is the machinery underneath leader election (who's allowed to be "the" leader after a failover), distributed locks, and configuration changes that must be seen identically by everyone.

Raft is the consensus protocol most production systems reach for today (etcd, Consul, CockroachDB, TiKV) — designed explicitly to be more understandable than its predecessor, Paxos, while providing the same safety guarantees. Its model, in four ideas:

Terms
Time is divided into numbered terms, each with at most one leader. A term is Raft's logical clock — every message carries a term number, and any node seeing a higher term than its own immediately recognizes its own information (and any leader it thought it had) as stale.
Leader election
Every follower runs a randomized election timeout; if it hears no heartbeat from a leader before the timeout fires, it becomes a candidate, increments the term, and requests votes from every other node. A node grants at most one vote per term, and only to a candidate whose log is at least as up to date as its own (the safety check that prevents electing a leader who'd overwrite already-committed data). A candidate that wins votes from a majority of all nodes becomes leader for that term. Randomized timeouts exist specifically so two nodes rarely time out simultaneously and split the vote.
Log replication
Clients only talk to the leader. The leader appends each write to its own log, then sends it to followers via AppendEntries RPCs. An entry is committed — safe to apply and safe to acknowledge to the client — only once a majority of nodes (leader included) have durably stored it. This is the exact same R+W>N pigeonhole logic as quorums above, specialized to "the write quorum is a majority and the leader always reads its own up-to-date log," which is what makes a newly elected leader's log provably contain every previously committed entry.
Safety under partition
If the cluster splits, only the side with a majority of nodes can elect a leader or commit new entries — the minority side may still have a node that believes it's leader (from before the split), but it can no longer reach a majority, so it can accept writes into its own log yet can never commit them. This is consensus choosing C over A during a partition, deliberately: it is safer for the minority side to stop making progress than to let two leaders in two terms disagree about the log.
★ Insight

Consensus and quorum-based replication look similar (both need a majority) but answer different questions. A Dynamo-style quorum store lets any node accept a write and reconciles divergent histories after the fact (eventual consistency, AP). Raft never lets two nodes disagree about the committed log in the first place — it trades availability during a partition (the minority literally cannot commit anything) for the guarantee that "committed" only ever means one thing. That's why systems that need a single source of truth about cluster membership or configuration (etcd storing Kubernetes state, ZooKeeper electing a Kafka controller) use consensus, not a Dynamo-style store — the cost of two disagreeing "truths" there is much higher than the cost of a brief unavailability.

★ ML-systems bridge

Distributed training coordination is a consensus problem wearing an ML costume: a parameter-server or all-reduce job needs every worker to agree on which node is the current coordinator/rank-0 and which gradient step is the latest committed one — lose that agreement (a coordinator dies mid-step and two workers disagree about whether step N landed) and you get silently corrupted training, not just a slow epoch, which is why production training orchestrators lean on the same primitives (etcd, ZooKeeper) as backend systems rather than inventing their own. Feature stores map onto the CAP choice directly too: an online store serving features at inference time usually chooses AP — serve a slightly stale feature rather than time out the request, because a marginally-stale feature degrades a prediction; an offline store used to generate training labels from point-in-time-correct data needs something closer to CP, because training on a feature value that silently changed after the fact is the textbook definition of train/serve skew.

1. A social app guarantees that a reply is never shown before the comment it replies to, but is fine with two unrelated comments posted at the same moment showing up in different orders to different viewers. Which consistency model is this?

This is causal consistency by definition: order is preserved only along causal chains (B read/depends on A), while concurrent, causally unrelated writes may be observed in different orders by different clients — which is exactly what's described and is considerably cheaper to provide than linearizability.

2. During a network partition, a distributed key-value store keeps answering read and write requests on both sides of the split, accepting the risk that the two sides may now hold different values for the same key. What CAP choice did it make, and what does PACELC say about its behavior when there's no partition?

Answering on both sides of a split with possibly divergent values is the textbook AP choice. PACELC's "Else" branch describes normal-operation behavior separately from the partition case — a system engineered to stay available under a partition is almost always also engineered to minimize latency (not wait on cross-node coordination) when there's no partition, i.e. PA/EL.

3. A 7-node Raft cluster splits into a 4-node side and a 3-node side. What happens on each side?

Raft only requires a majority (4 of 7 here), not all nodes — that's exactly the point of majority quorums. The larger side keeps making progress; the smaller side is structurally unable to reach a majority, so it cannot commit, which is Raft choosing consistency over availability for the minority rather than risking two leaders disagreeing about the log.
