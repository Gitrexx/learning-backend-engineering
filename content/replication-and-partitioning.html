Distributed Systems & Scaling // 02

Replication & Partitioning

Scaling & Load Balancing made the app tier stateless and fungible — any instance can serve any request because all the state that matters lives somewhere external. This page is about that "somewhere": the data layer, which cannot just be duplicated blindly the way stateless app servers can. Data has to survive a machine dying (replication) and has to fit on more disk and serve more throughput than one machine can provide (partitioning, a.k.a. sharding). Both are simple to state and genuinely hard to get right, because both create a new category of bug that doesn't exist on a single machine: the copies, or the shards, can disagree — even briefly, even by design — about what's true.

Why replicate at all

Replication means keeping the same data on multiple machines. Three distinct motivations, and it matters which one you're solving for because they push toward different designs:

  • Availability — if the only copy of a row lives on one disk, that disk dying is data loss and downtime. N copies survive N−1 failures.
  • Read throughput — one primary database has a ceiling on reads/sec. Replicas let you spread read traffic across machines (this is not the same as sharding — every replica holds the full dataset).
  • Locality / latency — a replica near your users in another region answers reads in single-digit milliseconds instead of crossing an ocean.

All three motivations share the same hard problem: once data exists in more than one place, a write to one copy has to reach the others, and that propagation takes non-zero time. What you do about that gap — who's allowed to write, how followers catch up, what a reader sees in between — is the entire subject of this page.

Replication topologies

There are three structural answers to "who can accept a write," and they trade off write availability against how hard conflicts are to reason about.

TopologyWho accepts writesStrengthWeakness
Single-leader One designated leader; all writes go through it and are streamed to followers No write conflicts — there's one order of truth. The default for Postgres, MySQL, MongoDB replica sets. The leader is a write bottleneck and, until failover completes, a single point of failure for writes.
Multi-leader Several nodes (often one per data center) each accept local writes and replicate to the others Writes survive a whole data center going dark; low local write latency Two leaders can accept conflicting writes to the same row at the same time — conflict detection and resolution becomes the application's problem
Leaderless Any replica accepts a write; the client (or a coordinator) writes to several replicas directly and reads from several, reconciling on read No leader means no failover pause — the system degrades gracefully as nodes come and go. Dynamo, Cassandra, Riak. Consistency is a per-request choice (quorums, below) rather than a structural guarantee; the client/driver carries real logic
! Pitfall

Multi-leader replication looks like a free lunch — "just let every region write locally" — until two customers in two regions update the same shopping cart within the same second. Now you have two histories that both happened and disagree, and something has to decide the outcome: last-write-wins (silently drops one customer's change), a merge function (correct only if the data type supports it, e.g. a CRDT counter), or surfacing the conflict to a human. There is no topology that makes this problem disappear — multi-leader just moves it from "does this happen" to "how do I resolve it," which is why most teams default to single-leader unless multi-region write availability is a hard requirement.

Replication lag and the anomalies it causes

Even the simple case — single-leader, asynchronous replication — has a gap: the leader acknowledges a write before every follower has applied it. That gap is replication lag, and a reader who hits a follower during it can observe the past. Three specific anomalies, precisely defined, because interviewers ask for exactly this vocabulary:

Read-your-writes consistency
A guarantee that a client who just wrote a value will see that value on their very next read — even if that read lands on a lagging replica. Violating it looks like: you post a comment, refresh, and it's gone. The fix is routing: either read your own writes from the leader for some window after writing, or read from whichever replica you just wrote through, or stamp the write with a version and require the replica serving the read to be at least that version ("read-after-write" via a monotonic cursor).
Monotonic reads
A guarantee that a client's reads never go backward in time, even across multiple lagging replicas. Violating it looks like: you read a fresh comment from replica A, refresh, get routed to replica B which hasn't caught up yet, and the comment is gone again. The usual fix is sticky routing — pin a client to the same replica for the duration of a session, so it only ever sees that one replica's timeline, which is monotonic by construction.
Consistent prefix reads
A guarantee that if write A happened-before write B, no reader ever observes B without A — you never see an answer before its question. This mostly bites in partitioned/sharded systems where causally related writes land on different partitions that replicate independently and can be observed out of order.

All three are about asynchronous replication specifically. Synchronous replication — the leader waits for one or more followers to confirm before acknowledging the write — eliminates lag-based staleness entirely, at the direct cost of write latency (now bounded by your slowest required follower) and write availability (that follower being down blocks writes). Most production systems pick a middle ground: one synchronous follower for durability, the rest asynchronous for read scaling — a trade-off you should be ready to name explicitly, not something to treat as a fixed default.

Failover

When a single leader dies, something has to promote a follower to take its place. Getting this wrong is one of the most common sources of real production data loss, so the mechanics matter:

  1. Detect the leader is actually down (not just slow) — usually via missed heartbeats to a coordination service (etcd, ZooKeeper) or the followers themselves.
  2. Elect a new leader — typically the follower with the most up-to-date replicated log, decided via a consensus protocol (previewed here, covered properly in Consistency Models, CAP & Consensus).
  3. Reconfigure clients and the load balancer to send writes to the new leader.
! Caution — split brain

If the old leader wasn't actually dead — just partitioned from the coordination service by a network blip — it may still think it's the leader and keep accepting writes while a new leader is elected elsewhere. Now two nodes both believe they're the leader and both accept writes: split brain. The standard defense is fencing — the new leader's epoch/term number is written somewhere all clients and storage check, and anything presenting an old epoch is rejected, including the old leader trying to write to shared storage. Failover that skips fencing trades a short outage for a subtler, worse bug: two histories that both look authoritative.

There's also a real trade-off in how fast to fail over. Failing over too eagerly on a transient blip causes unnecessary leader churn and possible data loss (in-flight writes to the old leader that hadn't replicated yet); waiting too long extends the write outage. Most systems tune this with a timeout in the 10–30s range plus a required quorum of followers agreeing the leader is unreachable — precisely to avoid one confused node triggering failover on its own.

Partitioning: when replication isn't the axis you need

Replication gives every node the same full dataset — it solves durability and read throughput, but does nothing for a dataset or write volume too large for one machine. Partitioning (sharding) splits the data itself across machines, so each holds a subset. Production systems combine both: N partitions, each replicated M ways. Two structural choices for how to split:

StrategyHow it splitsStrengthWeakness
Range partitioning Contiguous key ranges go to each partition (e.g. users A–F, G–M, ...) Range scans stay on one partition — "give me all events from today" is fast Sequential keys (timestamps, auto-increment IDs) concentrate all new writes on the single partition holding the current tail — a moving hot spot
Hash partitioning Hash the key, use the hash to pick a partition — spreads keys near-uniformly Kills the sequential-write hot spot; even load without careful key design A range scan now has to fan out to every partition and merge results — you traded hot spots for scatter-gather
! Pitfall — the hot partition

Partitioning assumes access is roughly uniform across keys. It usually isn't. A celebrity account's posts, a viral product ID, "today" in a range-partitioned event log — one key or one narrow range absorbs disproportionate traffic, and adding more partitions doesn't help because the hot key still lives on exactly one of them. Fixes are all application-aware: salt the hot key into several sub-keys and fan reads out across them, cache the hot key aggressively (Caching Strategies) so the partition layer rarely sees it, or move that one key to dedicated capacity. There's no partitioning scheme that makes a skewed access pattern uniform for free.

Consistent hashing: partitioning that survives resizing

Naive hash partitioning — partition = hash(key) % N — has the exact failure mode flagged in the load-balancing page's caution: change N by adding or removing one node, and the modulo output changes for almost every key, not just the ones that needed to move. For a load balancer that's an annoying stampede; for a sharded database it means re-copying nearly the entire dataset every time you resize the cluster.

Consistent hashing fixes this by hashing both keys and nodes onto the same circular space (a "ring") and assigning each key to the next node found walking clockwise. Adding a node only steals the keys between it and its clockwise neighbor — roughly a 1/N share — and removing a node only affects the keys it was holding, which fall through to its neighbor. Nobody else's assignment changes. Real implementations give each physical node many virtual nodes (dozens to hundreds of points on the ring) rather than one, because a single point per node makes each node's share of the ring lumpy — virtual nodes average that out into a much more even distribution, and also mean a node's departure spreads its load across many neighbors instead of dumping it all on one.

★ ML-systems bridge

A feature store has the exact same shape as this page. An online feature store (Redis, DynamoDB) is typically written by a streaming or batch pipeline and read by the serving path at request time — that's single-leader replication with the pipeline as the sole writer. Replication lag here is feature staleness: a feature computed at t and served at t+lag is exactly the read-your-writes problem, just renamed — "the model scored against a feature that doesn't reflect the user's latest action yet" is the ML term for a stale read. And a feature store keyed by user ID has the same hot-partition risk as any other partitioned store: a small number of extremely active users can dominate a partition's read/write volume unless the key space is spread deliberately (hashing, salting) rather than left to fall wherever a natural ID happens to land.

1. A user updates their profile photo, and the page immediately re-fetches the profile to show it — but the request lands on a replica that hasn't applied the write yet, so the old photo flashes briefly. Which guarantee was violated?

This is precisely read-your-writes: a client's own write should be visible on that same client's next read. The fix is routing that client's read to the leader (or to a replica known to be caught up to that write) for a short window, not a general consistency setting on the whole database.

2. A cluster resizes from 4 to 5 nodes. Under naive hash(key) % N partitioning, roughly what fraction of keys typically end up mapped to a different node than before, compared to consistent hashing for the same resize?

This is the whole reason consistent hashing exists: modulo partitioning is a function of N, so any change to N perturbs nearly every key's assignment, forcing a near-total data reshuffle. Consistent hashing only reassigns the ring segment adjacent to the node that joined or left.

3. A products table is range-partitioned by created_at so recent-first queries stay on one partition. Ingestion suddenly hot-spots on a single partition during a product launch. Why, and what's a fix that doesn't abandon range partitioning's scan advantage entirely?

Sequential/monotonic keys are the textbook range-partitioning hot spot: "now" always lives on one partition. Salting/bucketing the key spreads writes across partitions while a query can still target the small known set of buckets for a given time range, keeping most of the scan benefit.
