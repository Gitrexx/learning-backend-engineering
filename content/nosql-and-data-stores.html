NoSQL & Choosing a Data Store

Every deep-dive in this section so far has quietly assumed one storage model: rows, columns, foreign keys, joins. That model is extremely good at what it's good at — but "the relational database" was never the only answer, and the last two decades produced an entire family of stores built by companies that hit a specific wall the relational model doesn't handle well: Amazon's Dynamo paper (2007) came from needing a shopping cart that stays writable even during a network partition; Google's Bigtable paper (2006) came from needing to store the entire crawled web, sparse and sharded across thousands of machines. Neither problem is "we don't like SQL" — both are "our access pattern and our scale don't fit a single-machine, row-oriented, strongly-consistent design." That's the right frame for this whole page: NoSQL isn't a replacement for relational databases, it's a set of other data models, each one a deliberate trade of something relational databases give you (joins, ad hoc queries, multi-row transactions) for something else (horizontal scale, write throughput, schema flexibility, a shape that matches one specific access pattern exactly). Picking one without knowing which trade you're making is how "we went NoSQL for scale" becomes "we went NoSQL and now nobody can answer a simple cross-entity question without three round trips."

i Note

"NoSQL" is a marketing-era umbrella term, not a technical category — the more accurate (if clunkier) name that stuck in some circles is "not only SQL." The useful unit of analysis isn't "SQL vs. NoSQL," it's the specific data model a store commits to, because that's what determines which access patterns it's fast at and which ones it's actively bad at. This page covers four families.

The four data-model families

Every NoSQL store you'll meet in production is built around one of these four data models (some, like Cosmos DB, offer more than one through different APIs on the same engine — but the underlying model per API is still one of these four).

Key-value

The simplest possible model: an opaque key maps to an opaque value. The store has no idea what's inside the value — it's a blob to GET, SET, or DELETE by key. No query language, no secondary indexes (in the purest form), no schema.

Access pattern it's built for
Point lookups by a known key, at extreme low latency and extreme scale. If your query is always "give me the thing with ID X," a key-value store does it about as fast as physically possible — often sub-millisecond, in-memory.
Examples
Redis and Memcached (in-memory, often used as a cache — see the next deep-dive), DynamoDB and Riak (durable, partitioned, key-value at the core, with some secondary-index bolt-ons).
Where it breaks down
The moment you need to ask "which values have field X equal to Y" without knowing the key. A pure key-value store can't answer that without scanning every value client-side — you have to build your own secondary index (e.g. a second key-value entry mapping X → key) and keep it in sync yourself.

Document

A step up in structure: values are semi-structured documents (JSON/BSON in practice), and the store does understand the internal structure well enough to query and index into nested fields, not just the top-level key.

Access pattern it's built for
"Fetch (or query) one aggregate whose shape varies between records and changes over time" — a user profile, a product listing, a CMS article with an arbitrary set of custom fields. Read patterns that want the whole nested object back in one round trip, without a join.
Examples
MongoDB, Firestore, Couchbase. Several relational databases (Postgres's JSONB, MySQL's JSON type) now embed a document model as a column type — a sign of how blurry this line has gotten.
Where it breaks down
Multi-document, ad hoc, relational-style querying across different document types — "join" is either unsupported, expensive, or an application-side fan-out of multiple queries. And schema flexibility is a double-edged sword: nothing stops five services from writing five subtly different shapes of "the same" document unless you add your own validation layer.

Wide-column (column-family)

Rows are grouped under a partition key, and within a partition, data is physically sorted by a clustering (sort) key — so a row can have an effectively unbounded, sparse set of columns, and the store is built to write huge volumes fast and scan a bounded range within one partition efficiently.

Access pattern it's built for
Extremely high write volume, queried by (partition key, sort-key range) — time-series, event logs, IoT telemetry, messaging history. "Give me everything for partition P between time T1 and T2," known in advance, is the query this model is built around; anything not indexed by the partition key requires a full scatter-gather across the whole cluster.
Examples
Cassandra, HBase, Google Bigtable. Most of these are LSM-tree-backed under the hood — worth reconnecting to the Indexes & Storage Engines deep-dive: the reason wide-column stores absorb huge write volume is the same LSM write path (sequential append to a memtable, flush to sorted files, merge later in the background) covered there. This isn't a coincidence — the storage engine and the data model co-evolved to serve the same workload.
Where it breaks down
Any query that doesn't start from the partition key becomes a full-cluster scan — there is no free-form WHERE on a non-key column the way a relational index gives you. You must know your access patterns before you design the table, because the partition/sort key choice is the query plan.

Graph

Data is modeled explicitly as nodes and edges (often with properties on both), and the engine is built to traverse relationships — not to look them up by scanning join tables, but to walk pointers directly from node to node.

Access pattern it's built for
Multi-hop relationship traversal: "friends of friends," shortest path, recommendation via shared connections, fraud rings via shared attributes. Called index-free adjacency — each node stores direct pointers to its neighbors, so hopping from one node to the next is O(1) regardless of how many total nodes are in the graph, instead of an index lookup (or worse, a join) per hop.
Examples
Neo4j (property graph, Cypher query language), Amazon Neptune (property graph or RDF), ArangoDB (multi-model, graph included).
Where it breaks down
Bulk analytical scans over the whole dataset, or high-volume simple key lookups — graph engines are optimized for traversal depth, not for "aggregate this column across ten million rows," which a wide-column or columnar analytical store does far better.
★ And relational is still one of the options

It's worth saying plainly: the relational model from the earlier deep-dives — rows, normalized tables, joins, multi-row ACID transactions — is not "the old way" that NoSQL superseded. It's the right answer whenever the access pattern genuinely needs ad hoc, unpredictable joins across entities, or an all-or-nothing transaction spanning multiple records. The rest of this page is about recognizing when it isn't the best fit — not about assuming it never is.

What you give up, precisely

None of the four families above are "the relational model minus limitations" — they are different trades, and naming the trade precisely is what lets you reason about it instead of guessing.

Give upWhat that costs you in practice
Ad hoc joins A question you didn't anticipate at design time ("which customers in city X bought product Y last month") is cheap in a relational store with the right indexes, and often outright unsupported — or an expensive application-side fan-out — in the other three families. You're trading query flexibility for the performance of the queries you did design for.
Multi-record ACID transactions Recall from Transactions, ACID & Isolation Levels: atomicity across multiple rows is what stops "payment succeeded, inventory update failed" from leaving visible garbage. Most NoSQL stores guarantee atomicity only within one key/document/partition — some now offer limited multi-item transactions (DynamoDB transactions, MongoDB multi-document transactions), but at a real latency and throughput cost, because it works against the store's whole scale-out design.
Enforced schema Flexibility to change shape without a migration cuts both ways — nothing stops inconsistent shapes from accumulating in production unless the application layer enforces one. "Schemaless" moves validation from the database to your code; it doesn't remove the need for it.
A single, simple consistency story Many of these stores are built to keep writing during a network partition by replicating across nodes with weaker consistency guarantees than a single-node relational database's default. That's a deliberate, useful trade for availability — and it's deep enough to be its own deep-dive later (Consistency Models, CAP & Consensus); the short version here is: distributed NoSQL stores generally make you reason explicitly about staleness in a way a single-node relational database doesn't force on you by default.

Choosing from access patterns, not hype

"We're at scale, so we need NoSQL" is usually the wrong reasoning chain — plenty of relational databases handle tens of thousands of writes per second with the right sharding and indexing, and plenty of NoSQL migrations have made a system worse because the access pattern needed joins the team didn't realize they'd need until reporting requirements showed up six months later. The right chain starts from the query, not the database:

  1. Write down your top 3–5 access patterns first — the literal queries the application will run, with roughly what fraction of traffic each one is. If you can't name them, you don't yet know enough to pick a store.
  2. Do any of them need a transaction spanning multiple records? If yes, that's a strong pull toward relational (or a NoSQL store's limited multi-item transaction feature, accepting the cost).
  3. Do any of them need an unpredictable join — a query shape that wasn't fixed at design time, especially for reporting/analytics? Relational (or a purpose-built analytical/columnar store) usually wins here.
  4. Is the dominant pattern "huge write volume, known key + range query"? Wide-column is built exactly for this.
  5. Is the dominant pattern "fetch one variably-shaped aggregate by ID"? Document fits, especially if the shape changes often.
  6. Is the dominant pattern "point lookup by exact key, extreme latency floor"? Key-value fits — and often sits in front of whichever store above as a cache (next deep-dive).
  7. Is the dominant pattern "traverse relationships several hops deep"? Graph fits, and nothing else comes close once you're past 2–3 hops.
✕ Pitfall

"Our schema changes sometimes" is not the same access pattern as "our schema is fundamentally unknowable per record." A bounded, well-understood set of ~50 attributes that occasionally gets a new column is a completely normal relational migration — reach for a document store's flexibility only when different records genuinely need structurally different shapes at read time, not just because "schema changes" sounds like a NoSQL keyword.

The trap: schemaless doesn't mean model-less

This is the part teams miss most often when they move fast into a document or wide-column store: you still have to design for your access patterns — the modeling effort from Relational Data Modeling doesn't disappear, it moves. In a relational database you normalize first and let joins reassemble data for whatever query shows up later. In a document or wide-column store, there usually is no cheap join, so you model by denormalizing on purpose, toward the queries you already know you'll run — the opposite instinct from normalization, and just as deliberate:

  • Embed data that's always read together into one document (a blog post embedding its comments) — trading update cost (editing an embedded comment means rewriting part of the parent document) for read cost (one fetch instead of a join).
  • Reference (store an ID, fetch separately) data that's large, updated independently, or shared across many parents — trading a second round trip for not duplicating or bloating the primary document.
  • In wide-column stores this goes further: it's common and correct to store the same data twice, once per access pattern, each copy keyed and sorted for one specific query — DynamoDB's "single-table design" is this taken to its logical extreme, deliberately duplicating data across item types so every one of the app's known queries is a single partition read.

None of this is a workaround or a hack — it's the actual design skill this data model demands, and skipping it (treating a document store like "a relational table but schema-optional") is exactly how teams end up doing joins in application code, one document at a time, and wondering why it's slow.

★ ML-systems bridge: polyglot persistence in a feature platform

A production feature store is rarely one database — it's usually two or three of these families deliberately combined, exactly the "polyglot persistence" pattern this page argues for. The offline store (historical features for training) is typically wide-column or a columnar file format on object storage — huge write volume from pipelines, queried by entity + time range, exactly the wide-column access pattern. The online store (features for real-time inference) is typically key-value — Redis or DynamoDB — because inference needs a point lookup by entity ID under a strict latency budget, and nothing else fits that shape as well. Vector databases (Pinecone, pgvector, Milvus) are a newer, ML-specific fifth family worth naming here: they index embeddings for approximate nearest-neighbor search — a genuinely different access pattern (similarity, not equality or range) from all four families above, which is exactly why they exist as their own category rather than bolting onto one of the others. "Why does our ML platform have four different databases" is this exact reasoning, made concrete.

Polyglot persistence, and its own cost

Using several stores in one system — Postgres for the transactional core, Redis for hot-path caching, Elasticsearch for full-text search, Cassandra for event history — lets every access pattern sit on the store built for it. The cost is operational: every extra store is another thing to run, monitor, back up, and keep roughly in sync (usually via change-data-capture or an event stream — a preview of the Messaging, Queues & Event-Driven Architecture deep-dive later in this roadmap), and every sync path is a place staleness can creep in between stores. The rule of thumb: add a second store when a specific access pattern is genuinely failing on your primary one, not preemptively "for scale" — every store you add has to earn its operational cost.

1. A team picks a document database for a new service mainly "because NoSQL scales better." Three months later, finance needs ad hoc joins across orders, customers, and refunds for reporting, and the team is writing this in application code as multiple sequential queries. What was the modeling mistake?

The core lesson of this page: start from the top access patterns, not from "which database is trendy right now." Ad hoc, unplanned joins across entities is the single strongest signal to reach for a relational database (or a dedicated analytical store), regardless of scale.

2. A time-series workload writes 200,000 sensor readings/second and is almost always queried as "sensor_id + a time range." Which data-model family fits, and why?

Wide-column stores are purpose-built for "huge write volume, query by partition key + a sorted range" — precisely this workload. A key-value store loses the ability to range-scan by time efficiently, since it only supports exact-key lookups.

3. Why is "schemaless doesn't mean model-less" the central design discipline for document and wide-column stores?

Relational normalization defers the "how do I reassemble this for a query" decision to join time. Document and wide-column stores generally don't have a cheap equivalent, so that decision has to be made up front, by denormalizing (embedding, referencing deliberately, or even storing the same data multiple times per access pattern) toward the queries you already know you need.
