Beyond REST: gRPC, GraphQL & Streaming

The previous deep-dive treated REST as the default — and it is, for the same reason English is the default language of international business: not because it's optimal, but because enough people already speak it that switching costs dominate the decision. REST's cost shows up in three specific places it wasn't optimized for: shaving milliseconds off high-volume service-to-service calls, letting wildly different clients each get exactly the data shape they need, and anything that isn't fundamentally a question-then-answer exchange at all. This page is about recognizing those three shapes and picking the tool built for each — and, just as importantly, about not reaching for them when plain REST still fits, because each one trades away something REST gives you for free.

Three shapes that aren't "request, then response"

Every protocol on this page exists because a mismatch between REST's model and a real requirement got expensive enough to justify a different tool:

Machine-to-machine efficiency
Two of your own services calling each other thousands of times a second, where JSON's text parsing and REST's "one resource per call" shape start showing up in latency budgets and CPU bills. gRPC is built for this.
Client-shaped queries
Wildly different clients (a mobile app on a slow connection, a admin dashboard, a partner integration) each wanting a different slice and depth of the same underlying data, where REST forces a choice between too little data (many round trips) or too much (wasted bandwidth). GraphQL is built for this.
Continuous push
Updates that originate on the server with no client request to respond to — a chat message, a live price tick, the next token of a streaming completion — where "poll repeatedly and hope you're not too late or too early" is the only way to fake it over plain request/response. WebSockets and Server-Sent Events are built for this.

None of these retire REST — a typical production system runs REST (or GraphQL) at its public edge, gRPC between its internal services, and a streaming channel wherever something needs to be pushed rather than pulled. Knowing which is which, and being able to say why out loud, is exactly the kind of trade-off reasoning a system-design interview is probing for.

gRPC: RPC over HTTP/2 with a strict schema

gRPC is a remote-procedure-call framework: instead of designing URLs and verbs around resources, you define functions a service exposes — in a .proto file, using Protocol Buffers (protobuf) as the interface-definition language: 

service InventoryService {
  rpc GetStock (StockRequest) returns (StockReply);
}

message StockRequest {
  string sku = 1;
}
message StockReply {
  string sku = 1;
  int32  quantity = 2;
}

A code generator turns that one file into client and server stubs in whatever languages your services are written in — call GetStock(request) in Go, and code you never wrote by hand serializes it to binary (not JSON text), sends it over an HTTP/2 connection, and deserializes the reply back into a typed Go struct on the other end. Two things fall out of this that REST+JSON doesn't give you: the wire format is compact binary instead of verbose text (materially less CPU and bandwidth at high call volumes), and the contract is enforced at compile time in every language that consumes it — a client and server built from the same .proto literally cannot disagree about a field's name or type, which is a whole category of bug REST's "the docs said it was a string" contracts leave to runtime.

Four shapes of RPC

Because gRPC rides on HTTP/2's multiplexed, bidirectional streams (the same primitive that made HTTP/2 fix REST's head-of-line-blocking problem), it can express more than request-then-response on a single call:

RPC typeShapeExample
UnaryOne request, one responseGetStock(sku) — the REST-equivalent case
Server streamingOne request, a stream of responsesSubscribe to price updates for one symbol
Client streamingA stream of requests, one responseUpload a large file in chunks, get one confirmation
Bidirectional streamingBoth sides stream independently, concurrentlyA live translation session — audio in, translated text out, continuously
! Pitfall

Protobuf's compile-time safety only holds if you follow its evolution rules: every field has a permanent, immutable field number (the = 1, = 2 above) that's what actually gets encoded on the wire — field names are a source-code-only convenience. Reusing a retired field number for a new field means old binary data on disk or in flight gets silently misinterpreted as the new type, with no error. The safe evolution moves are the same spirit as REST's, just enforced by the format instead of convention: add new fields with new numbers, never renumber or reuse a removed field's number, and only ever widen a field's meaning, never narrow it.

! Caution

Browsers can't speak raw gRPC — it depends on HTTP/2 trailer frames that fetch/XHR don't expose. gRPC-Web works around this with a translating proxy (Envoy is the common choice), but that's an extra hop and operational piece most teams don't want for a public-facing API. This alone rules gRPC out for "an API a browser calls directly" — reach for it behind your own edge, between services you control, not as the thing a customer's frontend talks to.

GraphQL: let the client shape the response

REST fixes the shape of a resource server-side — GET /orders/482 always returns the same fields, so a client that only needs the order's status still downloads the shipping address, the line items, and everything else (over-fetching), while a client that needs an order and its customer's name has to make two round trips (under-fetching). GraphQL inverts this: one endpoint, and the client sends a query describing exactly the shape it wants back. 

query {
  order(id: 482) {
    status
    customer { name }
    lineItems { sku quantity }
  }
}

The server has a schema (a typed graph of object types and the fields/relationships that connect them) and a resolver function per field that knows how to fetch it — often from entirely different backends (a SQL table for orders, a separate service for customers). One request, exactly the fields asked for, arbitrarily nested. This is why GraphQL wins for clients with genuinely different, unpredictable data needs: a mobile app on a metered connection and an internal admin dashboard can hit the same schema and each get their own precise shape, instead of the backend team building (and maintaining) a bespoke REST endpoint per client need.

The N+1 trap

The naive way to implement a resolver for lineItems { product { name } } is: fetch the order's line items, then loop over them issuing one query per item to fetch each product's name. For an order with 20 line items, that's 1 query to get the items plus 20 more to get each product — the N+1 problem, and it's the single most common way a naive GraphQL server turns a "one request" pitch into 21 database round trips hidden behind it.

★ Insight

The fix is batching: instead of each resolver instance firing its own query immediately, it registers "I need product 91" with a per-request batch collector (the DataLoader pattern, originally from GraphQL.js) that waits a tick, gathers every product ID requested during that window, and issues one WHERE id IN (...) query for all of them — turning N+1 queries into 2. This is the same fan-out-amplification problem you'll meet again in Performance, Profiling & Capacity Planning, just triggered by a query's declarative shape instead of an explicit loop in application code — which is exactly why it's easy to miss until a schema allows deep nesting and someone writes a query that walks it.

Push: WebSockets vs. Server-Sent Events

Everything so far is still request-then-response — the client always initiates. Some problems have no natural request: a chat message arrives whenever the other person sends it, not when you ask. Polling ("call GET /messages every 2 seconds") fakes this badly — it's wasteful when nothing changed and adds up to 2 seconds of needless latency when something did. Two real push mechanisms exist, and they aren't interchangeable:

WebSockets
An HTTP request that upgrades the connection to a persistent, full-duplex raw socket — both sides can send at any time, independently, over the same connection. The right tool when the client also needs to push: chat, multiplayer state, collaborative editing (two people typing in the same document).
Server-Sent Events (SSE)
A plain HTTP response that never closes — the server keeps writing text/event-stream chunks and the browser's built-in EventSource API delivers each as an event. One-directional, server → client only. The right tool when only the server has something to push: live notifications, a stock ticker, a chat model streaming its reply token by token.

i Note

Default to SSE whenever the traffic really is one-directional — it's dramatically less to operate: no custom reconnect logic, no special load-balancer configuration for a raw socket protocol, and it degrades gracefully through plain HTTP infrastructure. Reach for WebSockets only when the client genuinely has its own stream of pushes to send, because that's a real requirement SSE structurally cannot meet — not because WebSockets are the more "advanced" or impressive-looking choice.

★ ML-systems bridge

Both halves of this page show up directly in ML infrastructure. Model-serving frameworks (TensorFlow Serving, Triton, TorchServe) expose a gRPC endpoint alongside a REST one for exactly the reasons above: internal, latency-sensitive, high-volume inference calls between your own services want binary encoding and a compile-time-checked tensor schema, not JSON parsing overhead on every request. And every major LLM API (chat completions with stream=true) sends tokens back over SSE, not WebSockets — the traffic is genuinely one-directional (you send one prompt, the server pushes tokens), so SSE's simpler operational story wins, and EventSource's built-in reconnect means a client that drops mid-stream can resume without you hand-rolling that logic. If you've ever consumed a streaming completion API, you've already used SSE — probably without knowing it had a name.

A decision framework

In interview-speak, the answer to "REST, gRPC, or GraphQL?" is never "gRPC is faster" in the abstract — it's naming which of these axes matters most for the specific system in front of you, out loud:

If this is the dominant constraint……reach for
Broad, unpredictable client compatibility (public API, partners, browsers, curl-ability)REST
Internal service-to-service, polyglot, latency/CPU-sensitive at high call volumegRPC
Clients with genuinely different, nested, unpredictable data needs from the same underlying graphGraphQL
Client also needs to push (chat, collaboration, multiplayer)WebSockets
Only the server pushes (notifications, live feeds, token streaming)SSE
HTTP/CDN caching by URL matters a lotREST (GraphQL and gRPC both work against this by design)

Real systems combine these rather than picking one globally: a public REST or GraphQL edge, gRPC between the services behind it, and an SSE or WebSocket channel wherever something needs to be pushed. ProtocolFitWhy

1. In a .proto file, why is it dangerous to reuse a field number after removing the old field it belonged to?

Field numbers, not names, are what's actually on the wire. Names exist only in the generated source code. Reusing a number is the protobuf equivalent of REST silently changing a field's type on a live endpoint — except it can corrupt already-serialized data with no parse error at all, which is what makes it worse.

2. Why does GraphQL mostly defeat standard HTTP/CDN caching, in a way plain REST doesn't?

REST's resource-per-URL design is what makes it cache-friendly for free — a CDN can cache GET /orders/482 by its URL. GraphQL's single-endpoint, query-shaped-by-the-client model breaks that key, which is why GraphQL deployments need their own caching layer (persisted queries, response caching keyed on the query+variables) to get comparable behavior.

3. A team is building a feature where an LLM streams its reply token-by-token to a web chat UI, with no need for the client to send anything mid-stream. Which should they reach for, and why?

Browsers can't call raw gRPC without a translating proxy, ruling out (b). WebSockets would work but is solving a harder problem (full duplex) than the one that exists (one-directional push) — the general rule from this page: match the mechanism's directionality to the actual requirement, don't reach for the more powerful-sounding tool by default.
