Distributed Systems & Scaling // 01

Scaling & Load Balancing

Everything in Concurrency, Threads & Async I/O lived inside one process on one machine: a fixed number of threads, one ρ = λ·S/N curve, one point where the queue tips over. This page asks the question that follows naturally once that ceiling is real: what do you do when one machine — however well-tuned — genuinely isn't enough? The answer, almost always, is more machines. But "more machines" only works if something in front of them decides which machine handles which request, and does so in a way that keeps failing machines from taking the whole service down with them. That something is a load balancer, and the decisions it makes are a direct, mechanical extension of the same ρ math you already know — just with N now counted in servers instead of threads.

Vertical vs. horizontal scaling

There are exactly two ways to add capacity to a system, and they have very different ceilings and failure characteristics.

Vertical scaling (scale up)
Give the existing machine more resources — more CPU, more RAM, faster disks. Simple: no architectural change, no new failure modes. But it has a hard ceiling (the biggest instance your cloud provider sells), it doesn't help with availability (one machine is still one machine — it goes down, you're down), and cost tends to grow faster than linearly as you approach the top of an instance family.
Horizontal scaling (scale out)
Add more machines running the same service and spread the load across them. In principle unbounded — need more capacity, add another box. It also buys availability for free: if one of ten instances dies, you lose 10% of capacity, not 100% of the service. The cost is architectural: now something has to route requests to the right instance, and the instances have to agree on or externalize any state they'd otherwise have kept locally.

Production systems do both — vertical scaling buys headroom cheaply up to a point, horizontal scaling is what actually removes the ceiling — but the interesting engineering, and the rest of this roadmap's Distributed Systems section, is almost entirely about the second kind.

Statelessness is what makes horizontal scaling possible

Imagine a service that stores each user's shopping cart in the memory of whichever process handled their last request. The moment you run two instances, this breaks: a request that lands on instance B has no idea what instance A put in the cart. Scaling out didn't just add capacity — it silently deleted user data, non-deterministically, depending on which instance a load balancer happened to pick.

A stateless service is one where any instance can handle any request, because nothing about the outcome depends on which instance previously talked to this client. All the state that matters — session data, cart contents, in-progress workflow — lives somewhere external and shared: a database, a distributed cache like Redis, a signed token the client carries itself. The app tier becomes a fungible pool of identical workers; the hard state-consistency problem is pushed down into the data layer, which is built (see Caching Strategies and the upcoming Replication & Partitioning) to actually handle it.

★ Insight

Statelessness isn't a nice-to-have style preference — it's the precondition for horizontal scaling to work at all. If any instance can serve any request interchangeably, you can add or remove instances at will, kill an unhealthy one without losing anything a user cares about, and let a simple algorithm pick among them. The moment a request's correctness depends on which instance handles it, you've reintroduced a single point of failure and made every scaling decision a data-consistency decision too.

"Stateless" doesn't mean "no state exists" — it means no state lives only in one process's memory. Sticky sessions (below) are the load-balancer-side patch for services that haven't fully externalized their state; they work, but they're a workaround, not the goal.

What a load balancer actually does

A load balancer sits between clients and a pool of backend instances and, for every incoming request, decides which backend handles it. That's the whole job description, but it implies three separate responsibilities that are worth naming precisely:

  • Distribution — pick a backend using some algorithm (below).
  • Health checking — stop sending traffic to a backend that's down or degraded, and resume once it recovers.
  • Termination point — often also where TLS is terminated and where the "L4 vs L7" distinction lives: an L4 (transport-layer) balancer routes TCP/UDP connections based on IP and port without looking at the request itself; an L7 (application-layer) balancer reads HTTP — path, headers, cookies — and can route /api/* to one pool and /static/* to another, which is why almost every production HTTP load balancer (nginx, Envoy, an ALB) operates at L7.

Load-balancing algorithms

"Which backend gets this request?" has a handful of standard answers, each with a different trade-off between simplicity, fairness, and how much state the balancer has to track.

AlgorithmHow it picksStrengthWeakness
Round robin Cycle through backends in order, one request each Trivial to implement, no per-backend state needed Assumes every backend has identical capacity — hands a small box the same share as a big one
Weighted round robin Cycle through backends, but give each a share proportional to a configured weight (usually its capacity) Fixes round robin's capacity blindness with almost no extra cost The weight is a static guess — doesn't react to a backend that's suddenly slow for reasons unrelated to its rated capacity
Least connections Send the request to whichever backend currently has the fewest in-flight requests Self-correcting — automatically favors whichever backend is actually keeping up, including under uneven request costs Needs the balancer to track live connection counts per backend; can misjudge if request cost varies wildly and cheap ones finish before load evens out
IP / session hash Hash a key from the request (client IP, session cookie) to deterministically pick the same backend every time for that key Gives you "sticky" routing without a session table on the balancer Uneven if keys aren't uniformly distributed; a naive hash(key) mod N remaps almost every key when N changes — see the callout below
! Caution

Naive modulo hashing (backend = hash(key) % N) is a trap: add or remove one backend and N changes, which changes the result of the modulo for almost every key — not just the keys that needed to move. For a cache pool, that's a stampede of cache misses; for sticky sessions, it logs everyone out at once. The fix is consistent hashing, which remaps only the ~1/N share of keys that actually need to move when a node joins or leaves. That's genuinely a different topic with its own data structure (a hash ring) — it's covered properly in Replication & Partitioning, unlocked by this page. For now, the takeaway is narrower: know that plain hash-mod-N routing has this failure mode before you reach for it.

Health checks: how a load balancer notices a backend is dead

A load balancer can't see inside a backend — it only knows what health checks tell it. There are two flavors, and production systems use both:

Active health checks
The balancer periodically calls a dedicated endpoint (often /healthz) on each backend and expects a fast 200. Miss enough checks in a row and the backend is pulled from rotation; pass enough in a row and it's added back. This is deliberately asymmetric — one slow check shouldn't evict a healthy backend, and one lucky check shouldn't re-admit a flapping one, so real systems require a streak in both directions (a debounce).
Passive health checks
The balancer watches real traffic: a backend that starts returning 5xxs or timing out on actual requests gets marked down without waiting for the next scheduled probe. Faster to react than active checks alone, at the cost of the first few real users hitting the dying backend before it's evicted.
Liveness vs. readiness
A refinement worth knowing precisely (from the Kubernetes vocabulary, but the concept predates it): liveness asks "is this process still running and not deadlocked" — fail it and the orchestrator restarts the process. Readiness asks "is this instance ready to take traffic right now" — fail it and the balancer stops routing to it, without killing it. A backend that's alive but overloaded, or still warming a cache on startup, should fail readiness without failing liveness.
! Pitfall

There is always a window between a backend actually failing and the load balancer noticing — the health-check interval plus the debounce streak. Requests routed to a dying backend during that window fail or hang. This is exactly why Resilience Patterns (a few pages ahead) layers client-side timeouts and retries on top of load balancing: health checks reduce how often you hit a dead backend, they don't reduce it to zero, and a caller that waits forever for a reply from a backend the health checker hasn't evicted yet is a self-inflicted outage.

Sticky sessions

If a service hasn't fully externalized its state, the load balancer can paper over it with session affinity ("sticky sessions"): route a given client's requests to the same backend every time — usually via a cookie the balancer sets, or via IP hashing above. It works, but it reintroduces exactly the coupling statelessness was designed to remove: that one backend now matters more than the others for that client, scaling and deploys have to account for draining sticky clients before removing a node, and an uneven distribution of "sticky" clients can quietly create a hot spot no algorithm will rebalance away. Treat sticky sessions as a stopgap for legacy state, not a design goal — the fix that actually scales is moving the state to a shared store and letting any instance serve any request.

Back-of-the-envelope: when do you actually need to scale out?

Before reaching for more machines, do the arithmetic. Recall ρ = λ·S/N from the concurrency page: a single server handling requests that each take S = 20ms of CPU time, with N=8 worker threads, saturates (ρ = 1) at λ = N/S = 8 / 0.02 = 400 req/s. If your actual peak traffic is 50 req/s, adding servers buys you nothing that tuning thread count or fixing a slow query wouldn't buy more cheaply — the bottleneck isn't machine count. If peak traffic is trending toward 4,000 req/s, no amount of per-request optimization gets one machine there; that's a horizontal-scaling problem, and the question becomes how many machines (same formula, solved for N: N ≥ λ·S/ρ_target, usually with ρ_target around 0.7 to leave headroom for bursts) and how the balancer should pick among them. Knowing which regime you're in — before writing any code — is the first move of the system-design method this roadmap builds toward.

★ ML-systems bridge

A fleet of model-serving replicas behind a load balancer is the exact same picture, with one wrinkle: request cost is far less uniform than a typical CRUD endpoint. A prompt with 10 tokens and one with 4,000 tokens can differ in service time by 100x, which makes round-robin's capacity-blindness bite much harder — two GPUs running round robin can end up with one saturated and one idle purely from an unlucky sequence of long prompts. This is why inference gateways (e.g. how vLLM- or Triton-fronting routers work) lean toward least-connections-style or queue-depth-aware routing over simple round robin, and why autoscaling a serving fleet usually keys off queue depth or GPU utilization rather than request count — request count alone hides exactly the variance that causes the hot spots.

1. A service holds each user's in-progress checkout state in the memory of whichever instance handled their first request. What happens when you scale it from one instance to three, with a plain round-robin load balancer and no sticky sessions?

In-memory state that isn't externalized only survives if the same instance keeps serving that client. Round robin makes no such guarantee, so scaling out (without sticky sessions or externalized state) directly breaks correctness — this is why statelessness is a precondition for horizontal scaling, not a style choice.

2. Three backends have capacities 5, 5, and 1 (requests they can handle concurrently). Under plain round robin, why does the smallest backend become a hot spot even though total traffic is well within the pool's combined capacity?

Round robin has no concept of capacity — it just cycles. An equal share of traffic is a very unequal share of *load* when capacities differ. Weighted round robin or least connections both correct for this by accounting for capacity or actual in-flight load.

3. A backend crashes at t=0. The load balancer's active health check runs every 2s and requires 2 consecutive failures to evict. Requests routed to that backend between t=0 and eviction fail or hang. What does this imply about load balancing alone as a reliability strategy?

Health checks are probabilistic-in-timing, not instantaneous — there's an inherent window between failure and eviction (interval × debounce streak). Load balancing meaningfully reduces how often clients hit a dead backend, but client-side timeouts and retries (Resilience Patterns) are what actually bound the damage during that window.
