DATA & DATABASES // 01

Relational Data Modeling

Every hop in the request lifecycle you traced in Anatomy of a Backend Service eventually bottoms out at a data store, and Data & Databases is the deepest area of this course for a reason: most production incidents that survive past "restart it and see" turn out to be data problems — a schema that allowed a bad state, a query that scans a table it shouldn't, a transaction that raced another one. Relational modeling is where that starts, because the shape of your tables determines which bugs are possible before a single line of application code runs. A schema that models the domain honestly prevents whole classes of bugs by construction; one that doesn't will generate them indefinitely, no matter how careful the code on top of it is.

Entities, attributes, and relationships

A relational schema is a claim about the shape of your domain, expressed as tables. Getting the vocabulary precise matters because it's what you reach for when a design goes wrong.

Entity
A distinct "thing" your system needs to track — a customer, an order, a product. Becomes a table; each row is one instance of that thing.
Attribute
A property of an entity — an order's total_amount, a customer's email. Becomes a column.
Relationship
How entities connect — a customer places orders, an order contains products. The cardinality of that connection (one-to-one, one-to-many, many-to-many) determines how you wire the tables together, covered below.
CardinalityExampleHow it's modeled
One-to-one (1:1) A user has one profile Rare in practice — usually the profile's columns just live on the user row, unless split out deliberately (e.g. a large, rarely-read blob kept off the hot table)
One-to-many (1:N) A customer places many orders Foreign key on the "many" side (orders.customer_id)
Many-to-many (M:N) Students enroll in many courses; courses have many students A junction table in between (enrollments), covered below

Keys: natural vs. surrogate

Every table needs a primary key — the column (or columns) that uniquely identifies a row. The choice of which column plays that role is one of the first decisions a schema locks in, and it's more consequential than it looks.

Candidate key
Any column (or set of columns) that could uniquely identify a row. A table can have several; you pick one as the primary key.
Natural key
A candidate key drawn from real-world data that already means something — an email address, a national ID number, an ISBN.
Surrogate key
A key manufactured purely to identify the row, with no business meaning — an auto-incrementing integer or a generated UUID/ULID.
Composite key
A primary key made of more than one column together — common on junction tables, e.g. (student_id, course_id).
ChoiceUpsideDownside
Natural key No extra column; the key is human-meaningful, useful for debugging Real-world facts change — a person's email or legal name is not a stable identity, and "stable enough until it isn't" is how a natural key ends up needing a migration at the worst time
Auto-increment integer Small, fast to index, sorts by insertion order (useful for "most recent N") Sequential and guessable (leaks row count and lets an attacker enumerate /orders/1, /orders/2, …); a single point of contention under very high write concurrency; awkward to generate client-side or merge across shards
UUID (v4, random) Generateable anywhere without coordination (client, multiple services, offline); not guessable; trivially mergeable across shards/replicas 16 bytes vs. 4-8 for an integer, and random order means every insert lands in a random spot in a B-tree index — worse cache locality, more index-page splits (see Indexes & Storage Engines)
ULID / UUIDv7 (time-sortable) Same coordination-free generation as UUIDv4, but the leading bits encode a timestamp, so inserts stay roughly sequential in index order Slightly leaks creation time; still 16 bytes; newer, so tooling support varies
✓ Tip

Default to a surrogate key for the primary key, and enforce natural keys as a separate UNIQUE constraint (e.g. users.email UNIQUE) instead of using them as the primary key directly. You get the natural key's uniqueness guarantee and the freedom to fix a mistaken or changed value later without a foreign-key migration touching every table that references it — because nothing else in the schema points at the email, only at the surrogate id.

Modeling one-to-many

The foreign key always lives on the "many" side, pointing back at the "one." A customer places many orders, so orders gets a customer_id column referencing customers.id — not the other way around, because a customer row can't hold a variable-length list of order IDs in a single column without breaking the atomic-values rule covered under normalization below. 

customers (id PK, name, email)
orders    (id PK, customer_id FK -> customers.id, total_amount, created_at)

Modeling many-to-many: the junction table

A student can enroll in many courses, and a course has many students — neither side's table can hold a single foreign key to the other, because it would need one value per row and there are many. The fix is a junction table (also called an associative or join table) sitting between them, holding one row per pairing: 

students    (id PK, name)
courses     (id PK, title, instructor_id FK)
enrollments (student_id FK -> students.id,
             course_id  FK -> courses.id,
             grade,
             PRIMARY KEY (student_id, course_id))

Notice enrollments has a composite primary key — the pairing itself is the identity, so (student_id, course_id) together must be unique (a student can't enroll in the same course twice). It also carries its own attribute, grade, which belongs to neither the student nor the course alone but to the relationship between them for a specific enrollment. Constraints: the database as the last line of defense

A schema is only as strong as what it refuses to store. Constraints are how you push invariants down to the data layer instead of trusting every code path — every service, script, and future engineer — to remember to check them in application code.

ConstraintWhat it prevents
PRIMARY KEYDuplicate or missing row identity
FOREIGN KEYAn orders.customer_id pointing at a customer that doesn't exist — an orphaned reference
UNIQUETwo users registering the same email
NOT NULLA required field silently missing — an unset total_amount that later divides-by-null downstream
CHECKA structurally valid but semantically nonsense value — a negative price or a quantity of zero

Foreign keys also govern what happens on delete — a decision that's easy to skip and expensive to get wrong:

ON DELETE RESTRICT
Refuse to delete the parent row while children reference it (default in most databases). Safe, but surfaces as a confusing error if you didn't expect the dependency.
ON DELETE CASCADE
Deleting the parent deletes all referencing children automatically. Convenient, and dangerous if applied somewhere you didn't mean to cascade — deleting a customer silently deleting their entire order history is rarely what "delete this customer" meant.
ON DELETE SET NULL
Deleting the parent nulls out the child's foreign key instead of deleting the child — appropriate when the child can meaningfully exist without that parent (an order whose referred_by_employee_id employee left the company).
! Pitfall

"We validate this in the application layer" is not the same guarantee as a database constraint, and the gap shows up exactly when it's expensive: a batch script that bypasses the ORM, a second service writing to the same table, a manual UPDATE during an incident, a race between two requests that both pass the application check before either commits. Constraints are enforced by the database itself, atomically, no matter what wrote the row — application validation is a good first line for a fast, friendly error message, but the constraint is what actually stops bad data from landing.

Normalization: functional dependencies and anomalies

Normalization is the discipline of structuring tables so that each fact is stored exactly once. The formal tool behind it is the functional dependency: column B is functionally dependent on column A if, for any given value of A, there's exactly one possible value of B. instructor_office depends on instructor_name — one instructor, one office. Normal forms are a sequence of rules about which functional dependencies are allowed to exist in a single table.

1NF — First Normal Form
Every column holds a single, atomic value — no repeating groups (a comma-separated list of course IDs crammed into one cell), no arrays-as-strings.
2NF — Second Normal Form
1NF, plus: every non-key column depends on the entire primary key, not just part of it. Only matters when the key is composite — a column that depends on just one column of a multi-column key is a partial dependency.
3NF — Third Normal Form
2NF, plus: no non-key column depends on another non-key column instead of the key directly — a transitive dependency. The classic mnemonic (William Kent): every non-key attribute must depend on the key, the whole key, and nothing but the key.

The payoff for following these rules isn't academic tidiness — it's avoiding three specific, concrete failure modes that show up the moment a table stores the same fact in more than one place:

Insertion anomaly
You can't record a fact until an unrelated fact also exists — e.g. you can't add a new course to the catalog until at least one student has enrolled in it, because "course" isn't its own row anywhere.
Update anomaly
The same fact is duplicated across rows, so changing it means updating every copy — miss one, and the data now contradicts itself.
Deletion anomaly
Deleting one row's data destroys an unrelated fact as a side effect — deleting the only student enrolled in a course deletes all record of the course ever existing.

Deliberate denormalization

Normalization optimizes for one thing: storing every fact exactly once, so updates can never go inconsistent. That's the right default. But it's not free — a fully normalized schema often means more joins to answer a read, and at high read volume or reporting scale, join cost becomes the bottleneck. Denormalization is the deliberate, informed decision to duplicate data anyway, in exchange for read speed:

  • Cached aggregates — storing orders.total_amount precomputed instead of summing line_items on every read. Fast to read; must be kept in sync on every write to line_items (a trigger, or an application-level transaction that updates both).
  • Reporting / analytics tables — a wide, flat, denormalized table built by an offline job specifically for dashboards, so analytics queries don't hit the normalized transactional schema (and its indexes tuned for OLTP access patterns) at all.
  • Materialized views — a query's result set stored as if it were a table, refreshed on a schedule or on write. Same trade: fast reads, a staleness window you have to accept and document.
! Caution

The dividing line between "deliberate denormalization" and "an update anomaly you'll be debugging at 3 AM" is whether the duplication is documented, owned, and has a defined sync path. The widget's own lesson applies at any storage layer, not just inside a single table: every place the same fact is copied is one more place it can drift, and drift is silent until a customer notices two screens disagree. Denormalize when you've measured that the read cost justifies it — not by default, and not without deciding up front exactly what keeps the copies in sync.

★ ML-systems bridge

A feature store lives on both sides of this trade-off at once. The offline store — used for building training sets — is typically modeled close to normalized, warehouse-style: entities, events, and joins across them, so training data reflects ground truth without duplication bugs. The online store — used for real-time inference — is aggressively denormalized on purpose: a single row per entity key (user, item) holding every feature that entity needs, precomputed, so serving is an O(1) key lookup instead of a join under a latency budget. Training-serving skew is, structurally, the exact same anomaly as the widget's update anomaly: the same logical fact (a feature's value) computed or stored two different ways in two different pipelines, and nothing enforcing that they agree. The fix is the same instinct as 3NF, generalized: make each fact's computation live in exactly one place, and have both the training and serving paths read from it.

1. A table has primary key (student_id, course_id) and a column student_name that depends only on student_id. Which normalization rule does this violate?

1NF is about atomic values, which this already satisfies. 3NF is about a non-key column depending on another non-key column (a transitive dependency) — that's not what's happening here. This is exactly 2NF's rule: with a composite key, every non-key column must depend on the entire key, and student_name only depends on student_id.

2. In the widget, why does the 2NF stage still let Dr. Singh's office go inconsistent if you only click "update" on one of the two Course rows?

2NF only removes *partial* dependencies (columns depending on part of a composite key). It does nothing about a non-key column depending on another non-key column — here, instructor_office really depends on which instructor, and the instructor happens to teach two courses, so the office is copied once per course row. That's a transitive dependency, and fixing it is exactly what 3NF (splitting out an Instructor table) does.

3. A reporting table stores orders.total_amount precomputed instead of summing line_items on every read. Is this a normalization mistake?

Denormalization isn't automatically wrong — it's a trade-off you make on purpose, in a specific place, for a measured reason (here, avoiding a sum-on-every-read). It becomes a bug when the duplication is accidental, undocumented, or has no defined path keeping the copies in sync — at that point it's indistinguishable from the update anomaly the whole normalization discipline exists to prevent.
