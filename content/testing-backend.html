Testing Backend Systems

Backend Security & the OWASP Top 10 was about not shipping the wrong thing. This page is about the machinery that lets you ship anything, fast, without finding out it was wrong from a paging alert. Every production-readiness property you've studied so far — correct isolation levels, idempotent retries, safe rollouts — is a claim about behavior under conditions you can't fully observe by reading the code. Tests are how you make that claim checkable by a machine, on every commit, before a human ever has to find out the hard way. A team with no tests can still ship fast for a while; a team with the wrong shape of tests ships slow and still gets paged, because their test suite is expensive to run and still doesn't catch the bugs that matter. Testing strategy — what to test, at which layer, with which kind of double — is a design decision with real trade-offs, not a checkbox.

The testing pyramid

The pyramid is a shape, not a rulebook: many fast, isolated tests at the bottom, fewer, slower, more-integrated tests as you go up, and a small number of full end-to-end tests at the top. The shape exists because speed and confidence trade off in opposite directions at each layer, and a healthy suite needs both: fast feedback on every keystroke, and real confidence before a release.

LayerExercisesSpeedWhat it catchesWhat it can't catch
UnitOne function/class, in isolation, no I/OMilliseconds; thousands run per secondLogic bugs, edge cases, off-by-ones — cheaply, exhaustivelyWhether the pieces actually fit together, or whether a real dependency behaves as assumed
IntegrationYour code against a real (or realistic) dependency — a database, a message broker, a filesystemSeconds per test; a real process is involvedWrong assumptions about how a dependency actually behaves (a DB constraint, a serialization format, a query's real result set)Whether the dependency's current API version still matches what you both expect
ContractThe request/response shape between your service and one it calls (or is called by)Seconds; no full environment neededBreaking API changes between independently-deployed services, before either side deploysWhether the two services' business logic agrees — only the shape of the conversation
End-to-end (E2E)A full user journey across the whole running systemTens of seconds to minutes; slow and comparatively brittleWhether a real critical path — the thing users and revenue depend on — actually works, wired together for realRoot cause on failure (a broken checkout could be the cart, payment, email, or DNS) and edge-case coverage (too slow/expensive to run exhaustively)
★ Insight

The pyramid's shape is really a statement about where a bug is cheapest to catch. A pricing-logic bug caught by a unit test costs a developer 200 ms of feedback loop. The same bug, if the only test covering it is a full checkout E2E test, costs minutes of CI time to even discover, and probably more minutes debugging which of five wired-together services is actually at fault. Pushing coverage as far down the pyramid as the bug's nature allows isn't a purity rule — it's the fastest, cheapest place to catch that particular class of mistake.

! Pitfall — the ice-cream-cone anti-pattern

Invert the pyramid — a handful of unit tests, some integration tests, and the bulk of coverage sitting in slow, brittle, end-to-end (often manual or Selenium-style) tests — and you get the ice-cream cone: wide at the top, narrow at the bottom. It's a common organic outcome, not a deliberate choice: E2E tests feel like they cover "the real thing," so teams under deadline pressure keep adding more of them instead of writing cheaper, more targeted tests lower down. The result is a suite that takes an hour to run, fails intermittently for reasons unrelated to the change under test, and tells you that something broke without telling you what — the opposite of what a test suite is for.

Test doubles: precise vocabulary

"Mock" gets used loosely for anything fake, but the five kinds of test double (Gerard Meszaros's taxonomy, still the industry vocabulary) mean genuinely different things, and picking the wrong one is how tests end up brittle or worthless:

Dummy
An object passed around to satisfy a parameter list but never actually used by the code path under test — e.g. a placeholder logger a constructor requires but this test never triggers a log call for.
Stub
Provides canned, hardcoded answers to calls made during the test, with no real logic behind them — a payment client stub that always returns {status: "approved"}" regardless of input, so you can test the code that reacts to approval.
Fake
A genuinely working, simplified implementation — an in-memory hash map standing in for a database repository. It has real behavior (insert then get actually round-trips data) but isn't fit for production (no persistence, no real query semantics).
Mock
Pre-programmed with expectations about which calls it should receive, and the test fails if those expected interactions didn't happen — verifying behavior (was this method called, with these arguments) rather than the resulting state.
Spy
Wraps a real or fake implementation and records how it was called, for inspection after the fact — similar to a mock, but the assertion is made afterward instead of pre-programmed as an expectation.
! Pitfall — over-mocking

Mocks verify how code did its job; most tests should verify what job it did — the observable output or resulting state, not the sequence of internal calls that produced it. A test that mocks a private helper method and asserts it was called with specific arguments is coupled to the current implementation, not the behavior a caller actually depends on: refactor the internals (even correctly, with identical output) and the test breaks anyway, training the team to see red test runs as noise rather than signal. The rule of thumb: mock things at the boundary of your system (the payment gateway you don't own, the flaky third-party API) where you genuinely can't or shouldn't invoke the real thing — and assert on outcomes, not on internal call sequences, for logic you own.

Testing against real dependencies

A fake in-memory repository is fast, but it only behaves the way you assumed a database behaves — and production databases have opinions of their own. A unique constraint that treats two NULLs as distinct (or doesn't), a transaction isolation anomaly from Transactions, ACID & Isolation Levels, a query that's correct SQL but returns rows in an order your code silently depended on — none of these show up against a hand-rolled fake, because the fake was written by the same assumptions the production code makes.

Testcontainers (and similar tooling) closes that gap by spinning up the real dependency — an actual Postgres, Kafka, or Redis — in a throwaway Docker container for the duration of an integration test, then tearing it down. You get real engine-specific behavior with none of the pain of a shared, stateful test environment that other test runs (or other engineers) can corrupt.

In-memory fakeReal dependency (Testcontainers)
SpeedMicroseconds — no process boundaryHundreds of ms to a few seconds to boot the container
FidelityOnly as correct as whoever wrote the fakeExactly the engine you run in production
CI requirementsNoneDocker (or equivalent) available in the CI runner
Best forHigh-volume, logic-heavy unit tests where the dependency's exact semantics don't matterThe smaller set of tests where a real constraint, real query plan, or real transaction behavior is exactly what's being verified

Contract testing across services

Once a system is split into independently-deployed services — the world of Messaging, Queues & Event-Driven Architecture and everything downstream of it — "does my code work" stops being answerable in isolation. Your order service can be perfectly correct and still break in production the moment the payment service's team renames a field. Standing up the entire payment service (and everything it depends on) just to test against it is the E2E trap: slow, whoever owns the environment becomes a bottleneck, and a failure two services away still shows up as "checkout is broken" with no clue why.

Consumer-driven contract testing (the pattern popularized by Pact) solves this without a shared environment. The consumer team writes an expectation — "when I call POST /charge with this shape, I expect a response shaped like this" — against a mock of the provider, and that expectation is published as a contract. The provider's own CI pipeline then replays every published contract against its real implementation and fails the build if it no longer satisfies a contract some consumer depends on. Neither side needs the other's full stack running; both sides find out about a breaking change before either one deploys it.

✓ Tip

Contract tests are not a substitute for integration or E2E tests — they verify the shape of a conversation, not that the business logic on either end is correct. A provider can satisfy a contract perfectly (right fields, right types) while still computing the wrong charge amount. Think of a contract test as a very cheap, very fast tripwire for the specific failure mode of independently-deployed services drifting apart — it earns its keep by catching that one thing constantly, not by replacing the rest of the pyramid.

Flakiness: the trust killer

A test suite only works as a safety net if a red run reliably means something is broken. A flaky test — one that sometimes passes and sometimes fails against the exact same code — destroys that guarantee: engineers learn to re-run failures instead of investigating them, and eventually stop trusting red at all, at which point the suite is providing negative value (false confidence plus wasted CI minutes).

CauseWhy it flakesFix
Shared mutable stateTwo tests touch the same global, DB row, or singleton and run order changes the outcomeIsolate state per test — a fresh fixture, transaction rollback, or container per run
Real wall-clock timeA test computes an expiry with now() and occasionally crosses a boundary mid-runInject a controllable clock/fake timer instead of reading real time
Unpinned randomnessA random seed occasionally produces an edge-case input the test didn't account forFix the seed in tests; treat any resulting failure as a real bug, not noise
Real network callsAn external dependency is slow, rate-limited, or briefly downStub the boundary in anything below E2E; reserve real calls for a deliberately small integration/E2E set
Missing async waitsA test asserts before an async operation (a queued job, a debounced UI update) has actually finishedWait on the actual condition/event, never a fixed sleep() — a sleep that's "usually enough" is a flake generator
! Caution

The tempting quick fix — retry a failing test a few times and only fail the build if all retries fail — treats the symptom and buries the disease. It keeps CI green while the underlying nondeterminism (a real race condition, sometimes) stays in the code, silently. Quarantine a known-flaky test out of the required gate with a tracked ticket to fix it if you must unblock a pipeline, but blanket retry-until-green policies are how a suite quietly stops meaning anything.

CI gates: mapping the pyramid to the pipeline

A production CI/CD pipeline (from Deployment, CI/CD & Release Strategies) should run cheap, high-signal tests first and gate expensive ones behind them — there's no point spinning up a Testcontainers Postgres for an integration suite against code that a five-second unit-test run would already have rejected.

StageRunsWhenGate
Pre-commit / on saveA fast subset of unit testsContinuously, locallyAdvisory — tightens the loop before code is even pushed
Every push / PRFull unit suite + fast contract testsSeconds to a couple minutesRequired — blocks merge on failure
On merge to mainIntegration suite (real dependencies via Testcontainers)A few minutesRequired — blocks the deploy pipeline from proceeding
Pre-deploy / canaryA small, curated E2E smoke suite on the critical pathsMinutes, against a near-production environmentRequired before promoting a canary to full rollout
★ ML-systems bridge

The pyramid maps cleanly onto an ML pipeline once you stop thinking of "the model" as the only thing worth testing. Feature-engineering and data-transform functions are pure logic — unit-test them like any other function, including edge cases (nulls, out-of-range values, empty batches). A feature-store read against a real store, or a training job against a real (small) data warehouse, is exactly the integration-test case Testcontainers-style tooling targets. The serving client's expected input/output tensor shape versus the model server's actual contract is a contract test in every sense of the term — and it's exactly what catches the schema drift behind a lot of real training-serving skew incidents, cheaply, before a bad deploy. And a fixed evaluation set with expected outputs, re-run on every retrain to catch a silent quality regression, is the ML analogue of an E2E smoke test: expensive to run exhaustively, but the last line of defense on the path that actually matters — whether the model that ships is still good enough to ship.

1. A team's test suite is 80% slow Selenium end-to-end tests, with only a handful of unit tests underneath. What's this shape called, and what's the core problem with it?

Inverting the pyramid (wide at the top) is the ice-cream-cone anti-pattern: it trades cheap, fast, precisely-localized failures for expensive, slow, hard-to-diagnose ones, and teams under it tend to stop trusting red CI runs because failures take too long to triage.

2. A test mocks a class's private helper method and asserts it was called exactly twice with specific arguments, rather than checking the value the public method actually returns. What's the risk?

Tests should generally verify what a unit does (its output or resulting state), not exactly how it internally does it. Asserting on internal call sequences to code you own makes tests brittle to safe refactors — the opposite of what a test suite should protect.

3. Your order service calls an independently-deployed payment service's /charge endpoint. You want to catch a breaking API change from the payment team before either side deploys, without standing up the payment service's full environment. Which testing approach fits best?

Contract testing is designed for exactly this: catching shape-level drift between independently-deployed services without needing a shared full-stack environment. A unit test with a mock only proves your code handles whatever shape you assumed — it can't catch the provider actually changing that shape.
