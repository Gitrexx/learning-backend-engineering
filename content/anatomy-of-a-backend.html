Anatomy of a Backend Service

If a backend interviewer says "not enough evidence you can design and implement production-ready backend services," it almost never means you can't write a handler function. It means you don't yet have a stable mental map of everything a request touches between a client hitting "send" and a response coming back — and everything that has to be true of a service for that round trip to be dependable at 3 AM, under load, with a teammate on call instead of you. This page builds that map. Every later topic in this course — networking, data, distributed systems, reliability, security — is a zoom-in on one piece of it.

A useful working definition: a backend service is a program that receives requests over a network, does something with state (read it, change it, coordinate it with other services), and returns a response — reliably, at some scale, for as long as it's expected to run. Everything on this page follows from taking that last clause seriously.

The request lifecycle

Take the most ordinary case: a client calls GET /api/orders/42 against api.example.com. Before your handler function ever executes, the request has already crossed several layers you don't own and rarely think about — and after your handler returns, it crosses them again in reverse. Here's the full hop-by-hop path:

1. Client
A browser, mobile app, or another backend service constructs the request: method, path, headers (auth token, content type, trace id), and maybe a body. It hands this to the OS network stack.
2. DNS resolution
api.example.com has to become an IP address. A resolver walks the DNS hierarchy (root → TLD → authoritative nameserver) if nothing is cached — tens of milliseconds. If it's cached (by the OS, the browser, or an intermediate resolver, within the record's TTL), this is close to free. This is your first lesson in a recurring theme: caching turns an expensive step into a cheap one, and the cache's staleness window becomes your problem later.
3. TCP + TLS handshake
A TCP three-way handshake opens a connection (one round trip), then TLS negotiates encryption on top of it (one more round trip on TLS 1.3, two on TLS 1.2). Paid once per connection — not once per request — which is exactly why connection reuse (keep-alive, connection pooling) matters so much for latency at scale. You'll go deep on this in Networking & Protocols.
4. Load balancer
The connection lands on a load balancer (L4, working on IP/port, or L7, working on HTTP semantics) that picks one of many healthy backend instances — by round-robin, least-connections, or a hash — and forwards the request. It's also usually where TLS is terminated, and where a health check silently stops sending traffic to an instance that's unhealthy. None of your application code runs yet.
5. App server
The request reaches a process running your code. It flows through a middleware pipeline — routing, authentication, logging, rate limiting — and finally into the handler: the actual business logic for "get order 42." This is the only hop on this list that's your code; everything before it is infrastructure whose entire job is getting the request here correctly.
6. Cache lookup
Before touching the database, a well-built handler often checks a cache (Redis, memcached, an in-process cache) for the data it needs. A hit returns in sub-millisecond time and the database is never touched. A miss falls through to the next hop — and, in the naive implementation, so does every other concurrent request for the same key. (That failure mode has a name — cache stampede — and its own deep-dive.)
7. Database / data store
On a cache miss, the handler queries the authoritative store. A query planner decides how to execute the query (index scan vs. sequential scan, join strategy), the storage engine reads pages from disk or page cache, and — if this write contends with another transaction — the handler may wait on a lock. This single hop is where most production latency and most production incidents live, which is why Data & Databases is the largest area in this course.
8. Downstream services (optional)
Many handlers aren't done yet — they call one or more other internal services (a payments service, a recommendations service, a fraud check). Each of those calls is its own full request lifecycle, nested inside yours, with its own network hop, its own latency, and its own chance of failing or being slow. This is the seed of fan-out latency and cascading failure — the subject of Resilience Patterns later on.
9. Response
The handler serializes a response body (JSON, protobuf, …), sets a status code and headers, and returns. The response flows back through the app server, the load balancer, and the already-open TLS connection to the client. Total time from step 1 to now is what the client — and your dashboards — call latency.
i Note

Every one of those nine hops can fail or be slow independently, and none of them know about the others. "Production-ready" starts with designing as if every hop will eventually fail, because at scale and over time, it will.

The layers of a real service

Zoom into hop 5 — "app server" — and it isn't one thing. A service you'd actually deploy has its own internal layering, and knowing which layer a piece of logic belongs in is most of what "clean architecture" means in practice.

LayerResponsibilityExampleIf it's missing / wrong
Edge / network TLS termination, routing, DDoS protection, static-asset delivery Load balancer, CDN, API gateway Every instance re-terminates TLS; no protection from traffic spikes or abuse
API / presentation Parse and validate the request, enforce the contract, shape the response Route handlers, request/response DTOs, input validation Malformed input reaches business logic; internal errors leak to clients
Business logic The actual rules: what "place an order" means, what's allowed, what happens next Domain/service classes, use-case functions Rules get duplicated across handlers, or leak into SQL / the UI
Data access Talk to stores and caches; translate between domain objects and rows/documents Repositories, ORMs, query modules SQL scattered through business logic; no single place to add a cache or an index hint
Cross-cutting / infra Config, secrets, auth, logging, metrics, tracing — needed everywhere, owned by none of the above Middleware, a config loader, an observability SDK Every layer reinvents logging; secrets end up hardcoded; nothing is traceable

The point of separating these isn't ceremony — it's that each layer fails and changes for different reasons, on different timelines, owned by different people. A schema migration shouldn't require touching the API layer; a new auth provider shouldn't require touching business logic. When a bug report comes in, "which layer" is usually the first productive question.

Stateless vs. stateful

This is the single most consequential design axis in the whole diagram, because it decides whether you can survive success. A component is stateless if any instance of it can handle any request, because no request-specific data lives only in one instance's memory. A component is stateful if it's the opposite — it holds data that would be lost, or would make answers inconsistent, if you routed the next request to a different instance.

Typically stateless
App servers / API handlers, most business logic, load balancers themselves (modulo sticky-session config) — as long as they don't keep per-user data in local memory or on local disk between requests.
Typically stateful
Databases, caches, message queues, session stores, anything with a local filesystem that matters (uploaded files not pushed to object storage, an in-memory rate-limit counter).

Why it matters: a stateless app tier can be scaled horizontally by adding identical instances behind a load balancer, with zero coordination — this is the entire trick behind cloud elasticity and auto-scaling, and it's the precondition for Scaling & Load Balancing later in this course. A stateful component can't be scaled that way; it needs replication, partitioning, or consensus to add capacity without losing or splitting data — each of which is an entire area of this roadmap on its own.

! Pitfall

Sticky sessions — routing a user to "their" instance because that's where their session lives in memory — is the classic way statefulness sneaks into an app tier that was supposed to be stateless. It works until that instance is redeployed, crashes, or is auto-scaled away, silently losing every session pinned to it. The fix is almost always to push the state out: a shared session store (Redis), a signed token the client holds (JWT), or a database row — so any instance can serve any request again.

★ ML-systems bridge

A model-serving fleet is the same shape: the inference workers should be stateless — any replica can score any request, so you scale by adding pods — while the model weights, the feature store, and any request-level cache are the stateful pieces that actually need careful engineering (versioning, replication, consistency). If you've ever debugged "why does this pod give a different prediction than that one," it was almost certainly state that leaked into a component that was supposed to be stateless — a locally cached model version, a warm feature cache that diverged. Same failure mode, different noun.

What "production-ready" actually means

"Production-ready" is vague enough to be useless unless you break it into checkable properties. Here's the working definition this course uses — five pillars, each of which gets its own deep-dive later:

Reliable
The service does the right thing under failure, not just under the happy path: it survives a dependency timing out, a spike in traffic, an instance dying mid-request. What breaks without it: one slow downstream call exhausts your thread pool and takes the whole service down with it — a cascading failure from a single weak link.
Observable
You can answer "what is it doing right now, and why" from logs, metrics, and traces — without SSH-ing into a box. What breaks without it: a latency regression ships, a customer complains three days later, and nobody can reconstruct what happened because nothing was measured or ever will be.
Secure
It correctly authenticates and authorizes every request, never trusts client input, and keeps secrets out of code and logs. What breaks without it: the breach — an unauthenticated endpoint, a SQL injection, an API key committed to a public repo.
Operable
It can be deployed, rolled back, scaled, and configured without a single person's tribal knowledge — runbooks exist, config isn't hardcoded, deploys are boring. What breaks without it: the one engineer who knows how to restart it correctly is on vacation during the incident.
Owned
Someone is accountable for it staying healthy — on-call rotation, a clear escalation path, alerts that reach a real person. What breaks without it: the alert fires into a channel nobody reads, for a service everyone assumes someone else is watching.

Notice none of these five is "has tests" or "is fast" in isolation — those are inputs to reliability and operability, not the goal itself. When an interviewer probes for "production-ready" thinking, they're checking whether you reach for these five properties unprompted, not whether you can recite a framework's routing syntax.

1. A client reuses an open keep-alive connection for a second request to the same API. What happens to the TLS handshake cost on that second request?

TLS establishes an encrypted channel over a TCP connection — once that's done, every subsequent request on the same connection rides on it for free. This is exactly why connection pooling and keep-alive are a first-order performance lever, not a minor optimization.

2. Which of these makes an app-server instance "stateless"?

Statelessness is about where request-specific data lives, not about whether the service touches durable storage (it usually does — that's what the database is for) or how it's packaged. A containerized app server that keeps a session in local memory is just as stateful as one running on bare metal.

3. A service has had 100% uptime this quarter, but when latency creeps up, nobody can tell you the p99, which endpoint is slow, or when it started — without manually grepping logs on a box. Which production-readiness pillar is missing?

Uptime alone doesn't tell you the service is observable. Reliability is about surviving failure; observability is about being able to *see* what's happening — metrics, logs, and traces that let you answer "what, when, where" without spelunking. A service can be up and completely opaque at the same time.
