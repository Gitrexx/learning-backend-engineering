Indexes & Storage Engines

The last deep-dive treated the index as a box: given a query, the planner either uses one or it doesn't, and the cost model tells you which is cheaper. That's the right level for tuning queries, but it leaves a question unanswered — why does an index scan cost roughly log(N) plus one read per matching row? Why does INSERT-heavy workloads make some databases sweat and others shrug? Why does Postgres feel nothing like Cassandra even though both index data for fast lookup? The answer is that "index" isn't one thing — it's a data structure, physically laid out on disk, with its own write path and read path and its own trade-offs. This page opens the box. There are really only two designs that matter in production, and almost every database you'll touch is built on one of them.

What an index actually costs you

Start from a definition precise enough to reason with: an index is a second, redundant copy of some columns, physically organized for fast lookup by a key you didn't pick for the table's primary storage order. Redundant is the operative word. Every index is data that has to be kept correct as the underlying table changes — every INSERT, UPDATE, and DELETE on an indexed column now writes to the table and touches every index that covers it. An index isn't a free accelerator; it's a standing trade of write cost and disk space for read speed on one specific access pattern. The two dominant structures make that trade very differently.

B-trees: the workhorse of relational databases

A B-tree is a balanced, sorted tree where each node holds many keys — not two, like a binary tree, but as many as fit in one disk page (Postgres pages are 8 KB by default). That single design choice is the whole point: disk (and even SSD) I/O happens in whole-page units, so a data structure built around "how much fits in one page read" minimizes the number of page reads needed to find anything.

Fanout / branching factor
How many children each internal node has. With ~30-byte index entries in an 8 KB page, a node can hold on the order of 200–300 keys — so each level of the tree multiplies how many rows it "covers" by roughly 200–300x.
Height stays tiny
A B-tree over 1 billion rows with fanout 200 has height log₂₀₀(1,000,000,000) ≈ 3.7 — rounded up, 4 levels. Four page reads (three internal + one leaf, often fewer once the top levels are cached in memory) locate any row in a billion-row table. That's the entire reason "index scan" reads as instant even at huge scale — logarithmic growth is almost flat once the base is in the hundreds.
Write path
Descend from the root comparing keys to pick a child, all the way to a leaf, then insert the key there in sorted position — an in-place, random-access write. If the leaf is now over capacity, it splits into two nodes and pushes its median key up into the parent, which may itself overflow and split, cascading up to the root in the rare case the whole tree grows a level. Splits are what make B-tree writes more expensive than they look: an insert is usually one page write, occasionally a cascade of several.
Read path
Descend the same way, comparing the search key against each node's keys to pick the next child, until a leaf either contains the key or doesn't. O(log N) page reads, each one a potentially random disk access — which is exactly the RANDOM_PAGE_COST constant from the previous deep-dive's cost model.
! Caution

Production databases actually use B+-trees, a variant where only leaf nodes hold row data — internal nodes hold copies of keys purely for routing — and leaves are linked in a chain for fast in-order range scans. The visualizer below draws a classic B-tree (data at every node) because it makes the split/promote mechanics easier to see in a small example; the branching-factor-keeps-height-low argument, which is the part that matters for reasoning about cost, is identical either way.

Clustered vs. secondary indexes

Once you know a B-tree's leaves hold the "real" data, one more distinction falls out for free. A clustered index is one where the table's physical row order is the index order — the leaves don't point to rows elsewhere, they are the rows. MySQL/InnoDB always clusters the table by its primary key. A secondary (non-clustered) index is a separate tree whose leaves store a pointer to the row rather than the row itself — in Postgres that pointer is a TID (page + offset in the heap); in InnoDB, a secondary index's leaf stores the primary key value, so a secondary-index lookup is really two B-tree descents: one down the secondary index to get the PK, one down the clustered index to get the row. A table can have exactly one clustered index (rows can only be physically sorted one way) but any number of secondary ones — which is why picking the clustering key well (usually the column your hottest range queries filter on) is a real, mostly-one-time design decision.

This is also the mechanical reason the leftmost-prefix rule and covering indexes from the previous page work the way they do. A composite index on (status, created_at) is literally one B-tree keyed on the concatenation of those columns — sorted by status first, then by created_at within each status value — so you can only binary-search into it starting from the column it's sorted by first. A covering index skips the heap fetch for the same reason an index-only scan is cheap: if every column the query needs is already sitting in that leaf entry, there's nothing left to go fetch.

LSM-trees: trading read latency for write throughput

A Log-Structured Merge-tree (LSM-tree) starts from the opposite premise: random-access in-place writes are the expensive thing to avoid, so never do one. Instead, batch writes in memory and only ever write to disk sequentially, in bulk. This is the structure behind Cassandra, HBase, RocksDB, LevelDB, and (as the storage engine inside) many time-series and embedded key-value stores.

Memtable
An in-memory sorted structure (often a skip list or balanced tree) that absorbs every write. A write here is about as cheap as a write gets — no disk seek, no page split, just an in-memory insert — usually paired with an append to a write-ahead log (WAL) on disk so a crash doesn't lose data that hasn't been flushed yet.
Flush → SSTable
When the memtable hits a size threshold, its entire sorted contents are written to disk as one immutable file — a Sorted String Table (SSTable) — in a single sequential write. A fresh, empty memtable takes over. SSTables are never modified after they're written, only replaced by compaction.
Compaction
A background process that merges multiple SSTables into fewer, larger ones — like the merge step of a merge sort — dropping overwritten and deleted keys (deletes are written as tombstones, not in-place removals) along the way. Compaction is what keeps read cost and disk usage bounded; skip it and both grow without limit.
Read path
Check the memtable first (newest data). If the key isn't there, check on-disk SSTables — newest to oldest, since a later SSTable's value for a key overrides an earlier one — until it's found or every SSTable has been checked. A key that was written once and never compacted may require checking every SSTable to confirm it's absent — the structural reason LSM reads are slower and less predictable than B-tree reads. Real systems blunt this with a Bloom filter per SSTable: a compact probabilistic structure that can say "definitely not in this file" for free and skip the read entirely, at the cost of an occasional false positive (never a false negative).
★ Amplification: the vocabulary this trade-off is measured in

Write amplification — total bytes physically written to storage per byte of application data written. B-trees keep this low on the write itself (one page, occasionally a split cascade) but pay it back on reads: random page I/O per level descended. LSM-trees keep the initial write nearly free but pay write amplification later, in compaction — the same byte gets rewritten every time it's merged into a bigger SSTable, commonly 10–30x the original bytes over a key's lifetime in a leveled-compaction system. Read amplification — number of physical reads needed to answer one logical read — is low and predictable for a B-tree (≈ tree height) and higher and workload-dependent for an LSM-tree (memtable + however many SSTables a Bloom filter couldn't rule out). Space amplification — how much more disk an LSM-tree uses than the logical data size, from old versions and tombstones not yet compacted away. The RUM conjecture (Athanassoulis et al.) formalizes what the widget below lets you feel directly: no structure minimizes all three — Read, Update, and Memory amplification — at once; every storage engine is a chosen point on that triangle.

Choosing between them, concretely

B-treeLSM-tree
Write cost In-place random write per insert; occasional split cascade. Gets more expensive as the working set outgrows cache (more random page I/O). Sequential append to memtable + WAL — close to the fastest write a storage device can do. Cost is deferred to background compaction, off the write's critical path.
Read cost Predictable, low: O(log N) page reads, largely independent of write history. Variable: memtable + however many SSTables a Bloom filter can't rule out. Best case (well-compacted, filter hits) close to a B-tree; worst case (write-heavy, behind on compaction) noticeably worse.
Space usage Compact; roughly the data size plus index overhead. Deletes and updates are in-place, no extra copies to reclaim. Higher until compaction catches up — old versions and tombstones sit on disk taking space and read-amplifying until merged away.
Where it shows up Postgres, MySQL/InnoDB, SQL Server, SQLite — anything optimized for mixed read/write OLTP with unpredictable ad-hoc queries. Cassandra, ScyllaDB, HBase; RocksDB/LevelDB as an embedded engine inside many time-series DBs, stream processors, and some feature stores. Anything dominated by high-volume writes/appends with comparatively sparse point reads.
The 3 AM failure mode A hot table's working set no longer fits in cache — every index descent now hits disk, and write-heavy tables fragment pages, bloating index size until a REINDEX/vacuum catches up. Compaction falls behind a sustained write spike — SSTable count balloons, reads slow down step-wise as more files must be checked per lookup, and disk fills faster than expected from space amplification. "Why did reads get slow with no code change" is almost always this.
★ ML-systems bridge

This trade-off maps almost exactly onto training vs. serving workloads. Feature-logging and event pipelines — every prediction request, every label arriving hours or days later, high-volume appends that are read back in bulk for the next training run — are a textbook LSM workload, which is exactly why so many feature stores and time-series stores are built on Cassandra/ScyllaDB or embed RocksDB: writes never block on the ingestion critical path. Low-latency online feature serving is the opposite shape — a small, hot set of keys read far more often than written — which is why the serving side of a feature store usually sits on a B-tree-backed or in-memory store (Postgres, DynamoDB, Redis) instead, even when the offline store right next to it is LSM-based. "Why does our feature store use two different databases" is this exact trade-off, made explicit.

1. A B-tree index has fanout (branching factor) 200 and covers 1 billion rows. Doubling the table to 2 billion rows changes the tree's height by roughly:

log base 200 grows extremely slowly — log₂₀₀(1B) ≈ 3.7, log₂₀₀(2B) ≈ 3.83. Height is very likely to stay at the same integer number of levels after rounding up. This is precisely why index lookups feel "instant" regardless of table size — the height barely moves even across huge growth.

2. A service does very high-volume writes (event ingestion) with rare, non-latency-critical reads (nightly batch export). Which storage engine shape fits best, and why?

This is the canonical LSM-shaped workload: write-dominated, latency-insensitive reads. Paying write amplification later via background compaction, in exchange for near-free writes now, is exactly the right trade here — the opposite of an OLTP app doing frequent point lookups on user-facing pages, where a B-tree's predictable low read cost matters more.

3. An LSM-backed store's read latency has been creeping up for weeks with no code or query changes. What's the most likely storage-engine-level cause?

A slow, code-change-free creep in read latency on an LSM-backed store is the classic signature of compaction debt: writes keep flushing new SSTables faster than compaction can merge them away, so every read has more files to check. The fix is usually more compaction throughput/threads or write-rate limiting, not a query change.

What's next

Indexes and storage engines explain how data gets found fast — and how it gets written. What they don't explain is what happens when two things happen to the same data at once: two transactions racing to update the same row, a reader seeing a half-finished write, a crash mid-transaction.
