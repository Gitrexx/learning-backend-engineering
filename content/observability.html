Reliability & Operating in Production // 02

Observability: Logs, Metrics & Traces

Resilience Patterns ended on an honest limit: you cannot prevent a dependency from failing, only bound how much its failure costs you. This page is about the step that has to happen before any of those patterns can be tuned, tripped, or trusted — knowing that something is wrong, and knowing enough about what and where to act. Anatomy of a Backend Service named this as one pillar of production-readiness: a system is only as operable as your ability to see inside it while it's running, under real traffic, without stopping it to look.

★ Monitoring vs. observability

Monitoring answers questions you thought to ask in advance — dashboards and alerts for failure modes you anticipated ("CPU > 90%", "5xx rate > 1%"). Observability is the property of a system that lets you answer questions you didn't anticipate, by exploring the data it emits — "why is this specific customer's checkout slow, and only since this morning, and only for orders with more than 3 items?" Monitoring covers known-unknowns; observability is what you need for unknown-unknowns, which is most of what pages you at 3 AM. The three pillars below — logs, metrics, traces — are the raw material for both, but it's the ability to correlate across them, on the fly, for a question nobody wrote a dashboard for, that separates a merely-monitored system from an observable one.

The three pillars, and what each is actually for

Teams reach for "let's add logging" to every visibility problem, and it's usually the wrong instrument for at least two of the three jobs. Each pillar has a shape and a cost profile that fits one kind of question well and the others badly:

PillarAnswersShapeCost driver
Logs What exactly happened, for this one request/entity, in detail? Discrete, timestamped events with arbitrary structured fields Volume — every request can emit several lines; storage + ingestion scale with traffic
Metrics How is the system behaving in aggregate, right now, and over time? Numbers (counters, gauges, histograms) sampled/aggregated over time, cheap to store Cardinality — number of distinct label combinations, not request volume
Traces Where did the time go, and which service caused it, for one request across a fan-out? A tree of timed spans following one request through every service it touched Instrumentation coverage + sampling rate — capturing every request is rarely affordable

None of the three is a substitute for the others. Logs don't scale to "which of my 40 services is slow" — you'd grep 40 log streams. Metrics don't tell you why a specific request was slow, only that requests-in-aggregate are. Traces don't tell you system-wide health — they show you one request's story, and you only have a story for the ones you sampled. The incident-console exercise later on this page makes that division concrete: you'll use all three, in a specific order, to localize a real regression.

Structured logs: queryable, not just readable

A log line like "user login failed" is readable by a human scrolling a terminal and useless to a query engine. Structured logging emits each event as a set of typed fields — JSON is the common wire format — so a log platform can filter, aggregate, and join on them the same way a database does: 

{"ts":"2026-08-02T14:32:07.114Z","level":"warn","service":"recommendations",
 "trace_id":"9f2a1c...","user_id":"88214","event":"cache_miss",
 "cache_key":"recs:v3:user:88214","fallback":"db_query","msg":"falling back to DB"}

Three fields are worth calling out because they're what make logs useful during an incident rather than only in a postmortem:

A correlation / trace ID on every line
The single field that turns "40,000 log lines across 40 instances" into "the dozen lines for this one request." Every log statement touched by a request should carry the same ID, propagated the same way trace context propagates (see below) — without it, correlating logs to a specific failure means grepping by timestamp and hoping nothing else was happening at the same moment.
A log level used consistently
debug for developer detail, info for normal operations worth recording, warn for recovered-from problems (a cache miss, a retry that succeeded), error for failures that need attention. The discipline matters because alerting and dashboards key off level — logging everything as error trains everyone to ignore error-level alerts, which is how a real error hides in the noise.
Fields, not string interpolation
user_id=88214 as a field you can filter on beats f"user {user_id} failed" as a string you can only grep — grep finds lines that contain "88214" anywhere, including unrelated ones; a field lets you ask precisely for user_id = 88214.
! Pitfall — logging everything

Logs are billed and stored per line, and a service under load can emit millions of lines an hour. The instinct to "just log more, storage is cheap" runs into two real costs: ingestion/storage spend that scales linearly with traffic (unlike metrics, which stay flat as traffic grows because they're pre-aggregated), and — worse — a signal-to-noise problem where the one error line that mattered is buried under a million routine info lines. Log what you'd actually want to read during an incident (request boundaries, state transitions, errors, and warnings for degraded-but-handled paths), sample or drop high-volume routine success logs, and lean on metrics for "how often does X happen" — that's a job metrics do far more cheaply than counting log lines.

Metrics: RED, USE, and why percentiles need histograms

Metrics are numbers aggregated over time, cheap enough to keep at high resolution indefinitely because their cost doesn't scale with request volume — a counter is one integer whether it counted ten requests or ten million. Three metric types cover nearly everything:

  • Counter — only goes up (requests served, errors raised); you graph its rate, not its raw value.
  • Gauge — a value that goes up and down (current queue depth, active connections, memory used).
  • Histogram (or summary) — a distribution of observed values (request durations) bucketed so you can derive percentiles later.

Two field-tested frameworks tell you which metrics to instrument, for two different things you monitor:

FrameworkForSignals
RED Request-driven services (an API, a microservice) Rate (requests/sec), Errors (rate of failed requests), Duration (latency distribution — p50/p95/p99)
USE Resources (CPU, disk, connection pool, a queue) Utilization (% busy), Saturation (work queued/waiting beyond capacity), Errors (resource-level errors — dropped packets, OOM kills)

RED is what makes the incident-console exercise's first move work: a per-service RED dashboard is how you localize which of N services regressed, before you commit to reading any one service's internals in detail.

! Pitfall — averaging percentiles, and the cardinality explosion

Two mistakes recur in every metrics setup:

You cannot average percentiles. If service A's p99 is 200ms and service B's p99 is 220ms, the p99 of A+B combined is not 210ms — percentiles aren't linear, so averaging them silently produces a meaningless number. A histogram must be aggregated at the bucket level (sum the counts in each latency bucket across instances, then recompute the percentile from the combined buckets) — which is exactly what Prometheus-style histograms are designed to let you do, and exactly what naively averaging a "p99" gauge from each instance cannot.

Cardinality is the real cost driver, not traffic volume. A label like user_id or order_id on a metric creates one time-series per distinct value — with a million users, that's a million time-series for one metric, which can crash or bankrupt a metrics backend regardless of how little traffic each user generates. High-cardinality dimensions (user ID, request ID, raw URL with path params) belong in logs and trace attributes, which are built to handle them; metric labels should stay low-cardinality (service name, endpoint template, status code class, region) — a handful to a few hundred distinct values, not millions.

Distributed traces: causality across a fan-out

A single user request to checkout-service might fan out to auth, inventory, recommendations, and payments — each of those possibly calling further services. Logs and metrics from each service, viewed separately, don't reconstruct that call tree; you're left inferring it from timestamps. A distributed trace makes the tree explicit: one request gets one trace ID, and every unit of work it causes — an HTTP call, a DB query, a cache lookup — is recorded as a span with a start time, a duration, and a parent span ID, so the whole request reassembles into a tree (commonly rendered as a waterfall, exactly like the widget below).

The mechanism that makes this possible across service and even language boundaries is context propagation: the trace ID (and the calling span's ID, as the new span's parent) travels as a header on every downstream call — the W3C traceparent header is the standardized version most tracing systems (and OpenTelemetry, the now-dominant vendor-neutral instrumentation standard) use today. Drop that header at any hop — a service that doesn't propagate it, a message queue that doesn't carry it through — and the trace fractures into disconnected pieces at exactly the boundary that would have been most interesting to see.

! Caution — sampling is a bet, not a bug

Recording a full trace for every request at real production volume is often prohibitively expensive, so most systems sample — trace 1% of requests, or trace every request that errors or exceeds a latency threshold (tail-based sampling, which needs to buffer a request's spans until it finishes to decide). The trade-off: low, fixed-rate sampling is cheap but might simply miss the one slow request you cared about; tail-based sampling catches the interesting cases but costs more to run (buffering + a decision step) and adds a little latency to the pipeline that decides. Neither is free, and "why don't we just trace everything" is worth asking explicitly — the honest answer is usually cost at your actual request volume, not laziness.

SLIs, SLOs, and alerting on symptoms, not causes

Metrics and traces exist to be looked at, but you don't want to be staring at dashboards all day — you want to be paged only when something the user would notice is actually wrong. That's what this vocabulary formalizes:

SLI (Service Level Indicator)
A specific, measured metric of user-facing behavior — e.g. "the proportion of requests served in under 300ms" or "the proportion of requests that return a non-5xx status."
SLO (Service Level Objective)
A target for an SLI over a window — "99.9% of requests succeed in under 300ms, measured over a rolling 28 days." An SLO is internal; an SLA is the (usually looser) version with a contractual penalty attached, promised to customers.
Error budget
1 − SLO, turned into a spendable quantity: a 99.9% SLO over 28 days allows about 40 minutes of "badness" in that window. Burn it slowly on planned risk (a migration, a canary rollout); burn it fast and you get paged before it's exhausted — the budget reframes "reliability" from an abstract virtue into a number you can spend deliberately and run out of.

This is also the discipline that keeps you from alerting on every internal wobble. Page on symptoms — SLO burn rate, user-facing error rate, checkout latency — not on causes — "CPU is at 85%" might be completely fine, or the first sign of an incident, depending on whether it's translating into user-visible pain. A cause-based alert that fires constantly without correlating to actual harm is exactly how a team learns to ignore pages, which is the precondition for missing the one that mattered.

✓ Tip

A fast-burn alert (e.g. "we'll exhaust the whole 28-day budget in the next 2 hours at this rate") should page a human immediately; a slow-burn alert (e.g. "at this rate we exhaust the budget in 10 days") can wait for business hours or just show up on a dashboard. Multi-window burn-rate alerting — checking both a short window (catch fast incidents) and a long one (catch slow leaks, and avoid paging on a brief blip that self-corrects) — is the standard refinement or worth knowing the name of even if you don't implement it from scratch; Google's SRE workbook is the canonical reference for the exact thresholds.

1. You need to know, right now, which of your 40 services just started returning more errors. Which pillar answers that fastest?

Metrics are pre-aggregated and cheap to compare across many services at once — exactly the shape of "which of these 40 regressed." Logs and traces are the right tool once you've narrowed to one service and want detail on one request.

2. A metric is emitted as http_requests_total with labels service, status_code, and user_id. What's the problem?

user_id belongs in logs or trace attributes, which are built for high-cardinality data. On a metric it multiplies the number of time-series by the number of distinct users, which is the classic way to crash a metrics backend.

3. Your 99.9% latency SLO over 28 days allows roughly 40 minutes of budget. You're burning it at a rate that would exhaust the whole budget in the next 2 hours. What should happen?

Error-budget alerting is meant to fire before the budget is gone, scaled to how fast it's disappearing. A 2-hour-to-exhaustion burn rate is exactly what a fast-burn alert exists to catch immediately, not after the fact.

★ ML-systems bridge

An inference service needs the same three pillars, plus a fourth signal a plain backend doesn't: model-quality metrics alongside RED. Request rate, error rate, and latency (including the batching/queueing behavior from a capacity planner's perspective) cover the serving path; but a model can be "up" — 200s, low latency — while quietly degrading, e.g. feature drift or training-serving skew silently changing prediction quality with no request ever failing. That needs its own SLI (a proxy label, human feedback rate, prediction-distribution drift versus a baseline) and its own budget, because RED alone will show a perfectly healthy dashboard on a model that's gotten quietly worse. Traces are just as valuable here: a request through retrieval → feature store → model → post-processing is a fan-out exactly like the checkout example, and a trace waterfall is how you'd learn whether a p99 regression is GPU inference time, a slow feature-store lookup, or serialization overhead — the same "where did the time go, across services" question, with "model" as one more span in the tree.
