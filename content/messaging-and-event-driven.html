Distributed Systems & Scaling // 04

Messaging, Queues & Event-Driven Architecture

Everything so far in this section — scaling, replication and partitioning, consensus — assumed services talk to each other synchronously: A calls B, blocks, and waits for a reply. That model is easy to reason about and gets you surprisingly far, but it wires every caller's uptime to every callee's uptime, chains latency additively, and turns a burst of traffic at the front door into a burst of pressure on everything behind it. Messaging breaks that wire: a producer hands work to a broker and moves on; a consumer picks it up whenever it's ready. This page is about the machinery that makes that handoff safe — queues vs logs, delivery guarantees, ordering, and the two problems every real system built this way has to solve: messages that arrive twice, and writes that need to update a database and publish an event as if it were one atomic thing.

Why decouple at all

Picture an order-placed request that, synchronously, has to charge a card, reserve inventory, email a receipt, and update a recommendation model's training log before it can return 200 OK. Every one of those four steps is now on the critical path of the user's click: if the email service is slow, the checkout is slow; if the recommendation logger is down, checkout is down, for a concern the user never asked about. Messaging inverts this: the order service does the one thing that must be synchronous — charge the card — and publishes an OrderPlaced event for everything else. Email, recommendations, and inventory each consume that event on their own schedule, at their own pace, and a slow or down consumer no longer touches the user's response time.

★ Insight

Decoupling here is temporal, not just structural. A synchronous call couples two services in time — both must be up and responsive at the same instant. A queue or log sits between them and absorbs that mismatch: the producer can run far ahead of a slow consumer (the broker just holds a backlog), and a consumer that's down for maintenance simply catches up when it returns. This is the same trade you make everywhere in backend design — caching trades staleness for speed; messaging trades immediacy for resilience. The event will be handled eventually, not necessarily now, and that's the whole point.

The cost is real, though: you've traded a stack trace for a distributed system. A bug in synchronous code fails loudly, in place. A bug in an async consumer fails quietly, minutes or hours later, in a different service, and debugging it means correlating a producer's log with a consumer's log across a broker you may not fully control. Reach for messaging when the work is genuinely deferrable (a receipt email can wait 200ms; a card charge cannot) or when you need to fan one event out to several independent consumers — not as a default architecture style.

Queues vs. logs: two mental models

"Message broker" covers two genuinely different designs, and conflating them is where a lot of confusion starts. Think RabbitMQ (a queue) against Kafka (a log) as the two archetypes:

Queue (RabbitMQ / SQS)Log (Kafka / Pulsar)
Storage model A message is removed once acknowledged. The broker's job is routing and delivery, not history. Messages are appended to an immutable, ordered log and retained for a configured window (time or size) regardless of who's read them.
Who tracks position The broker — it knows what's unacked and redelivers on failure. The consumer — it tracks its own offset (read position) into the log. The broker just serves whatever's asked for.
Multiple consumers of the same message Competing consumers: one queue, each message goes to exactly one consumer (unless you fan out via separate queues bound to an exchange). Natural: any number of independent consumer groups can each read the whole log at their own offset. Adding a new consumer type never affects existing ones.
Replay Not really — once acked and gone, it's gone (unless you've built your own archive). First-class — rewind a consumer group's offset and reprocess history. This is how you backfill a new service or rebuild a corrupted read model.
Routing flexibility Rich: exchanges support direct, topic (pattern), and fanout routing to many queues — a "smart broker." Simple: producers write to named topics, consumers choose what to read — a "dumb broker, smart consumer" design that trades routing flexibility for throughput and replay.
Sweet spot Task queues, work distribution, RPC-style request/reply, complex routing between many small services. Event streaming, event sourcing, feeding multiple independent consumers (analytics, search indexing, caches) off one firehose of truth.
i Note

Neither model is strictly better — they answer different questions. "Do this task exactly once, somewhere" is a queue question. "Let anyone who cares replay the history of what happened" is a log question. A lot of real systems use both: Kafka as the durable backbone of record, with a task queue (SQS, Sidekiq/Redis) downstream for "retry this one job with backoff" semantics that a log doesn't naturally provide.

Topics, partitions & consumer groups

Take the log model further, since it's the one that scales past a single machine the same way partitioning scaled a database. A topic is a named stream (e.g. orders); it's split into partitions, each an independent append-only log with its own offset sequence, spread across brokers exactly the way a sharded database spreads rows across nodes. A producer picks a partition key (often an entity ID like order_id or user_id); the broker hashes it to a partition, so every event for the same key always lands in the same partition, in the order it was produced.

Consumers read as a consumer group: the broker assigns each partition to exactly one consumer within the group, so the group as a whole parallelizes reads across partitions while guaranteeing only one consumer processes any given partition at a time. This is the mechanism, and it has a hard consequence worth internalizing before you provision a topic:

! Pitfall — partition count is your parallelism ceiling

A consumer group can have at most as many active consumers as the topic has partitions — the (N+1)th consumer sits idle with nothing assigned. A 6-partition topic caps you at 6-way parallel consumption no matter how many consumer instances you deploy. Under-provisioning partitions is the single most common Kafka scaling mistake, and re-partitioning later is disruptive: it changes which partition a key hashes to, which breaks the per-key ordering guarantee across the transition. Size partition count for your target peak parallelism up front, the same way you'd think about shard count for a database you don't want to re-shard under load.

Delivery semantics

"Will the consumer definitely get the message?" has three precise answers, and interviewers expect you to know which one any given design actually provides — and why the strongest- sounding one is a trap.

GuaranteeMechanismFailure modeWhen it's fine
At-most-once Consumer acks (or the broker considers it delivered) before processing — e.g. fire-and-forget UDP-style delivery, or ack-on-receive. A crash between ack and finishing the work silently drops the message. No retries, ever. Metrics/telemetry pings, best-effort logging — losing one occasionally is cheaper than the complexity of guaranteeing it isn't lost.
At-least-once Consumer processes then acks. If it crashes, times out, or the ack is lost in transit, the broker redelivers because it never saw confirmation. The same message can be — and eventually will be — processed more than once. The default for almost everything, provided the consumer is made idempotent (below). This is the guarantee real brokers actually give you.
Exactly-once Would require the message delivery and the side effect of processing it to commit as a single atomic step across two separate systems (broker and consumer's data store). Impossible in general, for the same reason two-phase commit across independent systems is expensive and fragile — network partitions and crashes at the wrong instant defeat any protocol you design. What vendors call "exactly-once" is a specific, narrower guarantee (see below). Never assume it from broker configuration alone — assume at-least-once and build for it.
★ The exactly-once you can actually get

What Kafka calls "exactly-once semantics" (EOS) is real but scoped: it guarantees a consume-transform-produce pipeline that reads from Kafka and writes back to Kafka commits both atomically, so a crash mid-pipeline doesn't duplicate the output topic. It does not extend to an arbitrary external side effect — charging a card, writing to Postgres, calling a third-party API — because that system isn't part of the broker's transaction. The general, portable answer to "exactly-once" is always the same recipe: at-least-once delivery + an idempotent consumer, which is effectively-once from the outside even though the message may physically arrive more than once. That's the pattern this page builds toward.

Ordering guarantees

A partitioned log only orders within a partition — messages produced with the same key, on the same partition, are delivered to that partition's consumer in production order. Across partitions there is no ordering guarantee at all: an event for order #1 on partition 0 and an event for order #2 on partition 1 can be consumed in either order, or concurrently. This is exactly the trade-off from the partitioning page, restated for streams: partition by a key that keeps causally related events together (all events for one order go to one partition), and accept that unrelated entities are unordered relative to each other — because forcing global order across partitions would mean funneling all writes through one partition, which defeats the reason you partitioned in the first place.

! Caution

Picking the wrong partition key breaks ordering in ways that are easy to miss in testing and painful in production. Partitioning OrderEvents by event_type instead of order_id, for instance, sends OrderCreated and OrderShipped for the same order to different partitions with no guarantee Created is consumed before Shipped — a shipping consumer can see "ship order #42" before "order #42 exists." Partition by the entity whose event order actually matters, not by a field that happens to be convenient to filter on.

Idempotent consumers

Since at-least-once is the honest guarantee any real broker gives you, the consumer has to be safe to run twice on the same message. A few concrete techniques, roughly cheapest to most general:

  • Natural idempotency — design the side effect so repeating it is harmless. UPDATE accounts SET balance = 500 is naturally idempotent (an absolute set); UPDATE accounts SET balance = balance - 50 is not (a relative delta). Prefer the former whenever the domain allows it.
  • Upsert on a unique key — if the effect is "write a row," make the message ID (or a natural key like order_id) the row's primary key and use INSERT ... ON CONFLICT DO NOTHING/UPDATE. A duplicate insert becomes a no-op at the database's constraint layer, no application logic required.
  • A dedup table or cache — when the effect is a call to something that can't be made naturally idempotent (charge a card via a third-party API), record processed message IDs (with a retention window) and check-then-skip before acting. This is the same idea as the idempotency keys covered for client-facing APIs, applied on the consumer side instead.
✓ Tip

The check-then-act dedup table has its own race: two redelivered copies processed concurrently by two consumer threads can both pass the "not yet processed" check before either writes the marker. Make the marker write itself the atomic gate — a unique constraint on message_id that the second concurrent writer fails against — rather than a separate read-then-write check, the same read-modify-write hazard that shows up under any concurrent access to shared state.

Dead-letter queues

At-least-once redelivery assumes the consumer will eventually succeed. Some messages never will — malformed payloads, a foreign key that doesn't exist, a bug that throws on this one specific input every time. Left alone, that "poison message" gets redelivered forever, wedging the partition behind it (remember: one consumer, in order, per partition — it can't skip ahead) or burning through retries endlessly. A dead-letter queue (DLQ) is the standard escape valve: after N failed attempts, the consumer stops retrying and routes the message to a separate queue/topic for inspection, instead of blocking everything behind it.

What a good DLQ setup includes
A bounded retry count with exponential backoff (not immediate infinite retries — see the retry-storm hazard covered generally in the Reliability section); the DLQ message tagged with the original topic, the failure reason, and attempt count, so someone debugging it doesn't have to reconstruct context from scratch; an alert on DLQ depth, since a silent DLQ is just a slower way to lose data unnoticed; and a replay path — once the bug is fixed, re-publish DLQ messages back to the original topic rather than hand-processing them.

The dual-write problem and the transactional outbox

Here's the failure mode that trips up teams who otherwise have messaging right: a service handles a request by writing to its own database and publishing an event about that write — two separate systems, two separate writes, no shared transaction between them. 

BEGIN;
INSERT INTO orders (id, status) VALUES ('o1', 'placed');
COMMIT;
-- process crashes right here —
publish("OrderPlaced", {order_id: 'o1'});   -- never runs

The database commit succeeded — the order genuinely exists — but the event that was supposed to tell inventory, billing, and email about it never left the building. Nothing downstream ever hears about an order that, as far as the database is concerned, is real. Reversing the order (publish first, write second) just relocates the same bug: now a consumer can react to an event for an order that a crash prevented from ever being committed. There is no ordering of two independent writes to two independent systems that makes this atomic by construction.

★ The transactional outbox pattern

Don't write to two systems — write to one. Add an outbox table to the same database as the business write, and insert the event into it in the same local transaction as the order row:

BEGIN;
INSERT INTO orders (id, status) VALUES ('o1', 'placed');
INSERT INTO outbox (id, topic, payload, published)
  VALUES ('e1', 'OrderPlaced', '{"order_id":"o1"}', false);
COMMIT;

Now the order and the fact-that-an-event-is-owed commit or roll back together — a single-database transaction, nothing distributed about it. A separate relay process (a poller, or CDC — change data capture — tailing the database's write-ahead log, e.g. Debezium reading Postgres's WAL) reads unpublished outbox rows, publishes them to the real broker, and marks them published. If the relay crashes after publishing but before marking the row done, it republishes on restart — that's just at-least-once delivery again, which the idempotent-consumer pattern above already handles. The dual-write problem is fully converted into a problem you already know how to solve.

This is also the mechanism that underlies event sourcing and CDC- driven architectures more broadly: instead of an application explicitly publishing events, every row change is captured off the database's own commit log and turned into a stream — the database becomes the single source of truth, and the event stream is a faithful, ordered derivative of it rather than a second, independently-written copy that can drift out of sync.

★ ML-systems bridge

Feature and training pipelines are event-driven architecture with a different label. A stream of user-activity events feeding a real-time feature computation job (Flink, Kafka Streams) is exactly the topic/partition/consumer-group model above — partitioned by user ID so a user's events stay ordered, consumed by a job that must be idempotent because the stream processor will reprocess events after a restart. "Exactly-once feature computation" is not free for the same reason exactly-once messaging isn't: what these frameworks actually guarantee is at-least-once processing plus transactional, idempotent writes to the output (a feature store row keyed by entity ID, upserted — natural idempotency, straight from the list above). And training-serving skew is very often a dual-write bug in disguise: a feature computed and written to the online store isn't also reliably logged to the offline training-data store, so the two drift apart — the outbox pattern (write once, derive the rest) is a direct fix, and it's why mature feature-store designs write once to a log and derive both the online and offline views from it rather than writing each separately.

1. A topic has 4 partitions, keyed by user_id. A consumer group scales from 2 to 6 consumer instances. What happens?

Partition count is a hard ceiling on a consumer group's parallelism, because each partition is assigned to exactly one consumer at a time. Scaling consumers past the partition count buys nothing — the fix is provisioning enough partitions up front for your target peak parallelism.

2. A payment consumer charges a customer's card, then acknowledges the message. The process crashes after the charge succeeds but before the ack is sent. What does the broker do under at-least-once delivery, and what should the consumer already have in place?

At-least-once means the broker's only signal that work is done is the ack — no ack, no matter why, means redelivery. That's precisely why "process, then ack" side effects that aren't idempotent (charging a card via delta rather than an idempotency-keyed request) are a real production bug waiting to happen.

3. A service writes a row to Postgres and then calls publish() to notify a Kafka topic. The process crashes between the two calls. What's the standard fix, and why doesn't simply retrying the publish call on crash-recovery solve it?

The core issue is that "retry the publish" requires the process to know a publish is still owed, which a crash can wipe out along with everything else in memory. The outbox table makes "an event is owed" a durable fact committed atomically with the business write, so a separate relay can always find and deliver it — no in-memory state to lose. Kafka's EOS covers Kafka-to-Kafka pipelines, not arbitrary external databases.
