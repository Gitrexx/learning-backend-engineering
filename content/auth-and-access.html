Authentication & Authorization Done Right

Every REST endpoint you learned to design in Designing Clean REST APIs eventually answers two questions before it does anything else: who is calling, and are they allowed to do this. Get either one wrong and the failure mode isn't a slow query or a confusing error message — it's someone else's data in your response body, or your name in a breach disclosure. Auth is disproportionately interview-relevant for the same reason it's disproportionately dangerous in production: it's easy to build something that looks correct (login works, tokens are issued, protected routes return 401 when you'd expect) while being subtly, catastrophically wrong in a way that only shows up under attack. This page is about the handful of decisions — hash function, token shape, flow choice, access model — that separate "looks correct" from "is correct."

Authentication vs. authorization

The two words get used almost interchangeably in casual conversation and mean completely different things in a system design:

Authentication (AuthN)
Who are you? The process of verifying an identity claim — a password matches, a token is validly signed and unexpired, a certificate chains to a trusted root. The output of authentication is a confirmed identity (a user ID, a service name).
Authorization (AuthZ)
What are you allowed to do? Given a confirmed identity, deciding whether a specific action on a specific resource is permitted. Authorization always runs after authentication and is checked independently, per request — a valid identity is necessary but never sufficient.
! Pitfall

The single most common access-control bug in real systems is conflating the two: checking "is this token valid" and treating that as "is this user allowed to see order 482," instead of separately checking "does the identity in this valid token own order 482." A perfectly authenticated user with a perfectly valid session can still be making an unauthorized request — this is broken object-level authorization (OWASP's #1 API security risk, more commonly known by its older name, IDOR — insecure direct object reference), and it's covered in depth in the next deep-dive, Backend Security & the OWASP Top 10. Authentication tells you who's knocking; it never tells you which rooms they're allowed into.

Storing passwords: hashing, not encryption

If your service authenticates users with passwords at all, exactly one storage design is acceptable: never store the password, ever, in any recoverable form. Not encrypted (encryption is reversible by design — whoever holds the key can recover every password), and never plaintext. What you store is the output of a password hashing function — one-way by construction, so even a full database dump gives an attacker no direct path back to the password.

But "one-way" alone isn't enough. General-purpose cryptographic hashes like SHA-256 are designed to be fast — that's a feature for verifying file integrity and a catastrophic bug for password storage, because fast means an attacker with a stolen hash dump can try billions of candidate passwords per second on commodity GPUs. Password hashing needs the opposite property: deliberately, tunably slow, so brute-forcing even a single password is expensive.

FunctionVerdictWhy
MD5, SHA-1, SHA-256 (unsalted, direct)Never for passwordsFast by design; a modern GPU rig tries tens of billions of SHA-256 guesses/sec — an 8-character password falls in hours
bcryptAcceptable, widely deployedAdaptive cost factor, battle-tested since 1999, but memory-hard against neither GPUs nor ASICs the way Argon2 is
scryptAcceptableMemory-hard, good GPU resistance, less common tooling than Argon2/bcrypt
Argon2idRecommended defaultWinner of the 2015 Password Hashing Competition; tunable memory, time, and parallelism costs; the id variant resists both GPU cracking and side-channel timing attacks

Every credible password hash also embeds a unique, random salt per password (bcrypt and Argon2id do this automatically as part of the stored hash string), so two users with the identical password get completely different stored hashes — this is what defeats precomputed rainbow table attacks, which only work when the same input always produces the same output.

i Note

OWASP's current guidance for Argon2id: minimum 19 MiB memory, 2 iterations, 1 degree of parallelism, tuned upward from there — raise the memory parameter until a single verification takes roughly 50–100 ms on your production hardware. That's slow enough to make offline brute-forcing expensive and fast enough that a real login doesn't feel laggy. This is a genuine trade-off dial, not a "bigger is always better" setting: too slow and you've built a self-inflicted denial-of-service on your own login endpoint under load.

Sessions vs. tokens

Once a user authenticates, the server needs a way to recognize them on every subsequent request without re-checking a password each time. Two fundamentally different designs dominate, and the choice cuts across the statelessness theme from Scaling & Load Balancing:

Server-side sessions
On login, the server creates a session record (user ID, expiry, metadata) in shared storage (Redis, a DB table) and hands the client an opaque, random session ID in a cookie. Every request, the server looks the session ID up. Revocation is trivial — delete the row — but every app server now needs shared access to that session store, reintroducing the stateful dependency that made horizontal scaling harder.
Tokens (bearer tokens, typically JWTs)
On login, the server issues a signed, self-contained token holding the user's identity and claims directly. Any server that can verify the signature can authenticate the request with no shared storage lookup — genuinely stateless, which is why tokens are the default for APIs and microservices. The cost: revocation is hard (more below), and the token's contents are visible to anyone who has it (signed, not encrypted, unless you deliberately encrypt the payload too).
! Caution

Where you store the credential on the client matters as much as which kind you pick. A token or session ID in localStorage is readable by any JavaScript running on the page — including an attacker's, via XSS. An httpOnly, Secure, SameSite=Lax (or Strict) cookie is invisible to JavaScript entirely, closing that theft vector, but opens a different one — cross-site request forgery (CSRF), where a malicious site makes the browser send the cookie automatically. SameSite cookies mitigate CSRF for most cases; a dedicated CSRF token is the belt-and-suspenders fix for anything sensitive. There's no credential storage location with zero attack surface — only trade-offs, covered further in Backend Security & the OWASP Top 10.

JWTs: structure, and where the bugs live

A JSON Web Token is three base64url-encoded segments joined by dots: header.payload.signature. The header names the signing algorithm; the payload carries claims (sub for subject/user ID, exp for expiry, iss for issuer, aud for intended audience, plus whatever custom claims your app needs); the signature is computed over the first two segments with a server secret (HMAC, e.g. HS256) or private key (asymmetric, e.g. RS256), and is what makes the token tamper-evident.

Note precisely what a JWT's signature guarantees and what it doesn't: it proves the payload hasn't been altered since signing and that the signer possessed the key — it says nothing about whether the token is still meant to be trusted right now. Every one of the following is a real, repeated vulnerability class, not a hypothetical:

BugWhat goes wrongFix
alg: noneSome libraries historically honored an unsigned token if the header said so — an attacker crafts a token with any claims they want and no signature at allExplicitly reject none; better, use an allowlist of exactly one expected algorithm rather than trusting the header
Algorithm confusion (RS256 → HS256)A verifier configured to "accept whatever alg the token claims" can be tricked into treating the server's public RSA key as an HMAC secret — since the public key is, well, public, the attacker can now forge valid-looking HS256 signaturesPin the expected algorithm in code at verification time; never read it from the untrusted token itself
Missing expiry checkLibrary decodes the token and returns the claims without the caller ever checking exp — a stolen token from months ago is silently treated as currentUse a verification call that enforces exp (and nbf) by default, not a raw decode
Missing audience/issuer checkA token legitimately issued for Service A gets replayed against Service B, which also trusts the same signing key and never checks who the token was meant forVerify aud matches this service and iss matches the expected issuer, every time
★ Insight

Nearly every JWT vulnerability above has the same root cause: trusting data the token itself supplies (its claimed algorithm, its claimed audience) to decide how to verify it, instead of anchoring verification to configuration the server controls. This is the same lesson as SQL injection and command injection, just relocated — never let untrusted input dictate how it gets validated.

The revocation problem

A stateless token's whole value proposition — no server-side lookup needed — is exactly what makes it impossible to revoke instantly. Once issued, a valid JWT stays valid until it expires, no matter what happens to the account (password change, employee termination, detected compromise) in between. There's no row to delete. Three practical mitigations, from weakest to strongest guarantee (and correspondingly, least to most state you have to keep):

  • Keep access tokens short-lived (5–15 minutes) and pair them with a longer-lived refresh token the client exchanges for a new access token. A stolen access token is only useful for minutes; the blast radius shrinks to the refresh token's exposure instead.
  • Refresh-token rotation with reuse detection: each refresh issues a new refresh token and invalidates the old one. If a refresh token is ever reused after rotation — a strong signal it was stolen and both the attacker and the legitimate client are racing to use it — revoke the whole token family, forcing re-login everywhere.
  • A server-side deny-list keyed by the token's unique jti claim (checked on every request, typically against Redis with a TTL matching the token's own expiry so entries self-clean). This reintroduces the per-request lookup tokens were supposed to avoid — a deliberate, narrow trade of some statelessness for the ability to revoke immediately, reserved for genuinely sensitive actions.

OAuth2 and OIDC: delegated access, not just login

OAuth2 solves a narrower problem than "log a user in": letting a user grant a third-party application limited access to their data on another service, without handing over their password. Four roles appear in every flow:

Resource owner
The user, who owns the data and grants (or denies) access.
Client
The application requesting access — your web app, wanting to read a user's calendar.
Authorization server
Issues tokens after authenticating the resource owner and recording their consent (e.g. Google's or Auth0's login+consent screen).
Resource server
The API that actually holds the protected data and accepts the resulting access token.
! Pitfall

OAuth2 is an authorization protocol — it proves a client holds a token scoped to act on a user's behalf; it was never designed to prove who the user is to the client. Using a raw OAuth2 access token as a login credential is a well-known misuse pattern (an access token issued for an entirely different audience can sometimes be replayed as if it were proof of identity). OpenID Connect (OIDC) is the actual fix: a thin identity layer on top of OAuth2 that adds a purpose-built id_token (itself a JWT, with standardized identity claims like sub and email) specifically meant to be consumed by the client as a login assertion. If you're implementing "Sign in with X," you want OIDC, not raw OAuth2.

The dominant flow is the authorization code flow with PKCE (Proof Key for Code Exchange, pronounced "pixy") — walk through it in the widget below. The short version: the client redirects the user to the authorization server to log in and consent; the authorization server redirects back with a short-lived, single-use authorization code rather than a token directly; the client then exchanges that code for the actual access token in a direct, back-channel server-to-server call — a code intercepted in a browser redirect is useless on its own.

✓ Tip — what changed in OAuth 2.1

The 2.1 consolidation of OAuth2's accumulated best practices made several things that used to be optional now mandatory, closing real, exploited attack surface: PKCE is required for every client, not just mobile/SPA clients without a secret (it stops an intercepted authorization code from being redeemed by anyone but the client that requested it, via a one-time cryptographic challenge/verifier pair); the implicit flow is removed entirely (it returned access tokens directly in a URL fragment — leakable via browser history, referrer headers, and server logs); refresh token rotation is expected by default; and redirect URIs must match exactly, not via prefix or pattern matching (a loose match is an open redirect waiting to happen). If you're building or reviewing an OAuth integration today, code flow + PKCE is the only flow you should reach for.

API keys: the service-to-service default

Not every caller is a human sitting through a consent screen. Server-to-server integrations (a payment webhook, a partner's batch job, an internal service calling another internal service) most often authenticate with a simple API key — a long, random, opaque secret sent in a header (Authorization: Bearer sk_live_... or a custom header). Simpler than OAuth because there's no user and no consent step, but the simplicity shifts every safety property onto how you handle the secret:

  • Never in code or version control — inject via environment variables or a secrets manager (Vault, AWS Secrets Manager), not a config file committed to the repo.
  • Scope keys narrowly — a read-only reporting integration should hold a key that cannot write, even if nothing in your current code path would misuse that power. Least privilege limits the blast radius of a leaked key to what it can actually do.
  • Make rotation routine, not an incident-response scramble — support multiple active keys per client so a scheduled rotation never causes downtime, and revoking a compromised key is an operational button-press, not a fire drill.

Access models: RBAC vs. ABAC

Once identity is settled, authorization still needs a model for deciding what's allowed. Two dominant approaches, and most real systems end up blending them:

Role-Based (RBAC)Attribute-Based (ABAC)
ModelUsers are assigned roles (admin, editor, viewer); roles are assigned permissionsRules evaluate attributes of the user, resource, action, and context (user.department == resource.department AND time.hour BETWEEN 9 AND 17)
StrengthSimple to reason about, audit, and explain; fast to check (look up the role's permission set)Expresses fine-grained, contextual policy RBAC can't — "your own records only," "only during business hours," "only from a corporate network"
Weakness"Role explosion" — real-world nuance (your own records vs. everyone's) forces ever-more-specific roles until the role list becomes unmanageableHarder to audit ("what can this user actually do" requires evaluating rules, not reading a list); easier to introduce a subtle policy bug
Reach for it whenPermissions map cleanly onto a small set of job functionsAccess genuinely depends on relationships or context, not just who the user is

In practice, most production systems layer both: coarse RBAC roles for broad capability ("can this user access the admin panel at all") plus a narrower, per-resource ownership or attribute check for anything sensitive ("is this specific order this specific user's to view") — which is exactly the object-level check from the broken-authorization pitfall earlier on this page.

★ ML-systems bridge

An inference endpoint has the same two questions as any other backend: who's calling (a user's mobile app? another internal service? a batch scoring job?), and what are they allowed to do (call this specific model? see raw feature values, or only the prediction?). Service-to-service calls into a feature store or model server are exactly the API-key / short-lived-token pattern above — often layered with mTLS between services in a mesh, so even a leaked bearer token is useless without the matching client certificate. Where teams actually get burned is authorization granularity that hasn't caught up to what the model exposes: an endpoint that correctly authenticates the calling service but then returns every feature it computed (including ones scoped to a different tenant or a different privacy tier) is broken object-level authorization wearing an ML costume — the fix is the same one: check what this specific caller is entitled to see, every time, not just that the caller is someone the system recognizes.

How many validation issues does a careful verifier catch here?

    1. A server verifies a JWT by reading the alg field from the token header and using whatever algorithm it names to check the signature. Why is this dangerous?

    The token's header is attacker-controlled input — trusting it to decide how the token gets verified hands the attacker the choice of "no verification, please." Correct verification pins the expected algorithm in server-side configuration and ignores what the token claims about itself.

    2. Why can't a stolen, still-valid JWT access token be revoked the way a server-side session can (just delete a row)?

    Statelessness is the whole point of a JWT — any server holding the verification key can accept it with no lookup. That same property means there's nothing to delete when you want to revoke it early; you can only mitigate with short expiries, refresh-token rotation with reuse detection, or a deliberate deny-list that reintroduces a lookup.

    3. A user is fully authenticated (valid session, valid token) and requests GET /invoices/9931, which happens to belong to a different customer. The endpoint returns it anyway because it only checked that the token was valid. What's the category of bug?

    Authentication and authorization are independent checks, and this endpoint only performed the first one. A valid identity was confirmed, but nothing then asked "does this identity have the right to invoice 9931 specifically" — the exact failure mode the AuthN-vs-AuthZ split at the top of this page warns about.
