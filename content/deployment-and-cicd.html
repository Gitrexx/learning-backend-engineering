Reliability & Operating in Production // 04

Deployment, CI/CD & Release Strategies

Every earlier page in this section assumed a system that's already running well and asked how it stays that way under load or failure. This one asks the question that precedes all of them: how does new code get into that running system without being the thing that breaks it? Performance, Profiling & Capacity Planning gave you the numbers to know when a system is healthy; deployment is the discipline of changing that system while it keeps being healthy — repeatedly, by many engineers, many times a day, without anyone needing to hold their breath.

★ Insight

Production-readiness isn't a property of code at rest — it's a property of a process that gets code from a developer's laptop into users' hands safely, and gets it back out just as fast if it's wrong. A brilliant service with a risky, manual, all-at-once release process is not production-ready, no matter how clean its code is. This page is about building that process: package the same artifact everywhere (12-factor, containers), build infrastructure that's replaced rather than patched (immutable infra), gate every change with automation (CI/CD), and control how much of production a bad build can touch before anyone notices (release strategy).

The twelve-factor app: what makes a service deployable at all

Before any of this works, the application itself has to be built in a way that's amenable to automated, repeatable deployment. The twelve-factor app methodology (Heroku, 2011) codified the habits that make that possible — most of which you've already met from other angles in this roadmap. Four matter most for this page:

Config lives in the environment, not the code
Database URLs, API keys, feature flags, and anything that differs between dev, staging, and prod are injected via environment variables or a config service — never hardcoded or branched on in code (if env == "prod" is a smell). This is what makes "the same artifact" meaningful: one built image runs unmodified in every environment because environment-specific values are supplied at runtime, not baked in at build time.
Processes are stateless and share-nothing
Anything that must persist across requests goes in a backing service (a database, an object store, a cache) — never on the local disk or in local memory of the process itself. This is the same statelessness Scaling & Load Balancing called the precondition for horizontal scale-out; here it's also the precondition for a deploy: you can only kill and replace a process safely if killing it loses nothing.
Disposability — fast startup, graceful shutdown
A process should be startable and killable in seconds, and on receiving a termination signal (SIGTERM) should stop accepting new work, finish in-flight requests, then exit — not be killed mid-request. Every release strategy on this page works by starting new processes and stopping old ones; if that's slow or lossy, every strategy inherits the pain.
Logs are an event stream, not a file to manage
Write logs to stdout/stderr and let the execution environment route them, instead of managing log files and rotation inside the app. This is what makes the app portable across deployment targets and is a direct prerequisite for the log pipeline in Observability.

The other eight factors — a single codebase per app, explicit declared dependencies, backing services treated as attachable resources, a strict build/release/run separation, port-binding as a self-contained service, scaling out via the process model, dev/prod parity, and running admin tasks as one-off processes — are the same spirit applied further. The throughline: an app that doesn't assume anything about the machine it happens to be running on is an app you can deploy by machine, not by hand.

Containers: packaging the "it depends" problem away

"Works on my machine" is a packaging problem: a process depends on an OS version, system libraries, a language runtime, environment variables, and file paths, and any mismatch between where it was built and where it runs is a place for it to break. A container solves this by packaging the application together with its entire user-space dependency tree — runtime, libraries, config defaults — into a single image: a stack of read-only, content-addressed layers built from a Dockerfile-like recipe, plus a thin writable layer added at run time.

Containers are not lightweight VMs, and the distinction matters operationally: a VM virtualizes hardware and runs a full guest OS and kernel per instance; a container shares the host kernel and is isolated from other containers using kernel primitives — namespaces (a private view of process IDs, network, mounts) and cgroups (resource limits/accounting). That's why containers start in milliseconds instead of the tens of seconds a VM boot takes, and why you can pack far more of them per host — but also why the isolation boundary is weaker than a VM's (a kernel-level exploit can cross container boundaries in a way it can't cross a hypervisor boundary, which is why untrusted multi-tenant workloads often still want a VM, or a VM-backed sandbox like gVisor/Firecracker, underneath the container).

✓ Tip — build once, promote the same artifact

The operational payoff of a container image isn't "it's small" — it's that the exact same immutable image, identified by a content digest, can be built once by CI and then run unmodified in staging, then in prod. What differs between environments is only the config injected at start time (per the twelve-factor rule above). If you rebuild the artifact for each environment, you've reintroduced "works on my machine" one layer up — now it's "works in staging." Dev/prod parity, one of the twelve factors, is this idea stated as a principle: keep dev, staging, and prod as similar as possible so what you tested is what you ship.

Immutable infrastructure & infrastructure as code

The same logic that says "don't patch a running process, replace it" applies one layer down, to the servers themselves. Immutable infrastructure means a running server is never modified in place (no SSH-in-and-apt upgrade, no hotfixing a config file on the box) — instead, a new server is built from an updated image or template and the old one is destroyed. The old shorthand is cattle, not pets: a pet server has a name, gets nursed back to health when it's sick, and its exact configuration lives only in someone's memory or shell history; cattle are numbered, replaced without ceremony when unhealthy, and their configuration lives entirely in version control.

Infrastructure as Code (IaC — Terraform, CloudFormation, Pulumi) is what makes that practical at scale: infrastructure (VPCs, load balancers, managed databases, the instances or clusters that run your containers) is described declaratively in files, checked into the same version control as application code, and applied by a tool that diffs the declared state against reality and reconciles it. This buys three things a backend engineer actually cares about at 3 AM: the infrastructure is reviewable (a pull request, not a Slack message), reproducible (rebuild the whole environment from the same files), and driftless-by-construction — if someone changes something by hand in the console, the next terraform plan shows exactly what drifted and offers to undo it.

! Caution

Immutable infrastructure and IaC are enablers, not guarantees — a Terraform config that's manually edited via terraform apply -target under pressure, or an image that's hand-patched "just this once" because a fix can't wait for a pipeline, quietly reintroduces the pet you were trying to avoid. The discipline only holds if the emergency path is also the pipeline, just a faster one — not a bypass of it.

CI/CD: the pipeline that turns a commit into a safe release

Continuous Integration (CI) is the practice of merging and building every change frequently — ideally on every commit — against an automated test suite, so integration problems surface in minutes, not at the end of a multi-week branch. Continuous Delivery extends this so that every change that passes CI produces a release-ready artifact, deployable at any time — deployment to production is still a deliberate (often one-click) decision. Continuous Deployment goes one step further and removes that manual gate: every change that passes all automated checks deploys to production automatically. The three terms are commonly compressed into "CI/CD," but the CD half is a spectrum, not a binary — and where a team sits on it should track how much they trust their automated gates, not how impressive they want to sound.

A representative pipeline, as a sequence of quality gates — each stage only runs if the previous one passed, and a failure stops the artifact from advancing:

StageChecksCatches
BuildCompile / install deps / build the imageSyntax errors, missing dependencies, broken builds
Unit testsFast, isolated tests (see Testing Backend Systems)Logic regressions, in seconds

! Pitfall — rebuilding per environment

A pipeline that runs docker build separately for staging and for prod breaks the "same artifact" guarantee — a dependency resolved slightly differently, a base image that moved between the two builds, and staging just stopped meaning anything. The package stage should produce one immutable, digest-addressed artifact, and every later stage should deploy that exact artifact, not rebuild from source again.

The other structural choice CI/CD forces is how branches flow into that pipeline. Trunk-based development — short-lived branches (hours, not weeks) merged frequently to a single trunk, with incomplete work hidden behind feature flags rather than a long-lived branch — keeps the integration problem small and constant instead of large and occasional, which is what actually makes "every commit through the full pipeline" tractable at team scale. Long-lived feature branches don't just delay integration pain, they compound it: merge conflicts grow with branch age, and the pipeline is exercising code that's increasingly unlike what's actually running in prod.

Release strategies: how much of production a bad build can touch

Everything above gets a validated artifact to the door of production. The release strategy decides how it walks through that door — and it is, in effect, the last resilience pattern from the previous page, applied to your own deploys instead of a downstream dependency: it bounds the blast radius (how much of your traffic can be hit by a bad build) and the rollback time (how fast you can undo it once detected).

StrategyHow it worksBlast radiusRollbackCost
Rolling Replace instances in small batches, health-checking each batch before continuing Grows with each batch until stopped — no separate old environment left once complete Redeploy the old image, batch by batch — a second rollout, not a switch Low — no extra capacity held
Blue-green Deploy a full parallel environment ("green"); cut traffic over all at once when ready 0% pre-cutover; 100% instantly if the bug wasn't caught before cutover Instant — flip the router back to blue, which is still warm High — two full environments running simultaneously
Canary Route a small traffic slice to the new version; expand gradually if it stays healthy Capped at the canary's slice for as long as it's held there Fast — redirect the small slice back; nothing else was ever exposed Low-moderate — a small extra deployment, held temporarily
Feature flags Ship code dark (deployed but inert), then flip a runtime toggle to expose it — per-user, per-cohort, or globally Exactly whoever the flag targets — independent of deploy batches entirely Instant — flip the flag off; no redeploy needed at all Low infra cost; ongoing complexity of flag lifecycle/cleanup
★ Insight — deploy is not release

Feature flags make explicit an idea the other three strategies blur: deploying code (getting it running in production) and releasing it (making it affect users) don't have to be the same action. Once they're decoupled, you can deploy constantly and cheaply — the risky part — and control exposure separately and cheaply too, including turning a feature off for one misbehaving cohort without any deploy at all. Most mature release strategies are really this idea plus a mechanism: canary is "deploy dark, release gradually by traffic weight"; a flag rollout is "deploy dark, release gradually by targeting rule." The mechanism differs; the separation of concerns is the same.

✓ Tip — what to look for

Compare peak traffic on the bad build across the three columns, not just "who rolled back fastest." Blue-green's rollback mechanism is the fastest of the three — a single router flip — yet it produces the worst outcome, because it had already committed 100% of traffic before the flip. Canary never got close to that, precisely because it never exposed more than its slice in the first place. The lesson generalizes: controlling exposure beats fast rollback — rollback speed only bounds how long a bad build hurts you, exposure control bounds how many people it hurts to begin with.

★ ML-systems bridge

Model deployment is this exact picture with "model version" in place of "code version." Shadow deployment sends production traffic to a new model in parallel with the live one, scores its predictions offline, and serves nothing from it — a canary with the exposure dialed to zero, used when even a small live blast radius is unacceptable (e.g. a fraud model). Canary releases of models work identically to canary releases of services — a traffic slice, staged promotion, rollback by redirecting weight. Feature flags gate which model version a request uses, independent of when it was deployed — exactly the deploy/release split above, letting you kill a misbehaving model for one segment without touching infrastructure. And a model registry with immutable, versioned artifacts is the same "build once, promote the same artifact" discipline as a container image — the alternative, mutable model files that get overwritten in place, is precisely the pet-server pattern this page argues against, and it makes "which weights are actually serving right now" an unanswerable question during an incident.

1. A team builds a container image separately for staging and for production, from the same source commit. What does this break?

Config should be injected at runtime into one artifact, not baked in by rebuilding. Rebuilding per environment reintroduces exactly the "works on my machine" class of bug that immutable, promoted artifacts exist to eliminate.

2. Why can blue-green deployment have a worse worst-case outcome than canary, even though its rollback mechanism (an instant router flip) is faster than canary's?

Rollback speed only bounds how long a bad release hurts you. Blue-green's all-at-once cutover means the exposure itself — before any rollback can even trigger — is already total. Canary's gradual exposure caps the damage regardless of how fast its own rollback is.

3. A feature is deployed behind a feature flag that's off. What is true?

Feature flags are runtime toggles, orthogonal to which release strategy shipped the code. "Deployed but dark" means the artifact is live in prod, executing on real infrastructure, but the flag keeps it from being reached — a release-strategy-independent way to decouple exposure from deployment.
