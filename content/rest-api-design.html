Designing Clean REST APIs

Every downstream area of this course — auth, caching, resilience, even the capstone design method — eventually has to cross a wire as an HTTP request. REST won that fight for general-purpose, human-and-machine-readable service interfaces, not because it's theoretically elegant but because it maps cleanly onto the transport you already learned about: verbs and status codes are HTTP, so a REST API is "just" a disciplined way of using HTTP as intended. The discipline is the whole game. A REST API that a team can live with for years and one that generates an endless stream of client tickets often differ by a handful of decisions, made once, at design time — and "did you design a clean, evolvable interface" is one of the first things a backend interview probes, because it's cheap to ask and hard to fake.

Resources are nouns, not verbs

The foundational idea of REST (REpresentational State Transfer) is that a URL identifies a resource — a thing, a noun — and the HTTP verb says what you're doing to it. /orders/482 is a resource; GET, PUT, and DELETE on it are actions. The most common way teams violate this is smuggling the action into the path itself: /getOrder?id=482, /createOrder, /deleteOrder/482. It works, technically — HTTP doesn't enforce REST — but it throws away the part of the contract that makes REST APIs predictable: once you know the noun, every verb behaves the same way across your whole API, and clients, proxies, and caches can reason about requests generically instead of endpoint-by-endpoint.

ShapeExampleWhy it matters
Collection /orders GET lists, POST creates a new member
Item /orders/482 GET reads, PUT/PATCH updates, DELETE removes
Sub-resource /orders/482/line-items Models a real one-to-many relationship instead of a query parameter
Action that isn't CRUD POST /orders/482/cancel A verb-shaped sub-resource for state transitions that don't fit CRUD cleanly — better than inventing a non-standard HTTP method
i Note

The "action that isn't CRUD" row is the honest escape hatch. Not everything is a clean create/read/update/delete — cancel an order, refund a payment, archive a project are state transitions with side effects (emails, ledger entries, downstream calls) that don't reduce to "replace this resource." Modeling them as POST to a sub-resource named after the action is the pragmatic convention, not a REST purity violation — a pure RPC alternative is covered in the next deep-dive, Beyond REST.

Verbs, precisely: safe, idempotent, and neither

Two properties of an HTTP method matter more than any REST style guide will tell you, because they're load-bearing for caching, retries, and resilience patterns you'll meet later:

Safe
The request causes no observable side effect on the server — it's read-only. Only GET, HEAD, and OPTIONS are safe. Safety is what lets browsers prefetch links and CDNs cache GET responses without asking permission.
Idempotent
Calling it once has the same effect on server state as calling it N times. PUT, DELETE, GET, HEAD, and OPTIONS are idempotent by contract. POST and PATCH are not — repeating them is allowed to (and usually does) change state again.
VerbSafe?Idempotent?Typical status on success
GETYesYes200 OK
POSTNoNo201 Created (or 200/202 for non-creation actions)
PUTNoYes200 OK / 204 No Content
PATCHNoDepends on the patch semantics200 OK
DELETENoYes204 No Content
! Pitfall

"Idempotent" describes the contract, not a guarantee your handler automatically satisfies. PUT /orders/482 is only idempotent if your handler actually replaces the resource's state with the request body. A PUT handler that appends a row to an audit log, increments a counter, or sends a notification email as a side effect on every call has broken the contract — and every client, proxy, and retry mechanism in the stack that assumes PUT is safe to retry blindly (see Resilience Patterns later) will now double that side effect on a retried request. This is the single most common way idempotency breaks in practice: not a wrong verb, but a correct verb with an impure implementation.

Why any of this matters beyond taxonomy: idempotency is what makes a request safe to retry. A client (or a load balancer, or a retry-with-backoff layer) that doesn't know whether repeating a call is safe has to guess, and guessing wrong either causes duplicate side effects (double-charging a customer) or gives up on transient failures it could have recovered from. Precise verb semantics turn that guess into a lookup.

Status codes as a contract, not decoration

The five status-code classes each promise something specific to a caller that doesn't parse your response body — which is exactly the case for load balancers, retry logic, and monitoring dashboards classifying traffic by status class alone.

ClassPromiseCommon codes
2xxRequest succeeded200 OK, 201 Created, 202 Accepted, 204 No Content
3xxFollow this redirect301 Moved Permanently, 304 Not Modified
4xxThe client's fault — fix the request, don't retry as-is400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests
5xxThe server's fault — may be transient, safe to retry (if idempotent)500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout
★ Insight

The 4xx/5xx split is really "who should act on this failure." A well-behaved retry policy retries 5xx and 429 (with backoff) but never retries a plain 4xx — a 422 for a malformed request will fail identically no matter how many times you resend it, so retrying just wastes a request and hides the real bug. Getting this distinction right in your API's status codes is what lets a generic client-side retry layer make correct decisions without knowing anything about your specific endpoints.

Idempotency keys: making POST safe to retry

POST's whole job is often "create a new thing" — pay an invoice, place an order, send a message — which is precisely the kind of action you cannot safely retry blindly: a client that times out waiting for a response has no way to know whether the server actually processed the request before the connection died. Resending risks a duplicate charge; not resending risks silently dropping a legitimate request.

The standard fix is an idempotency key: the client generates a unique token (a UUID) once per logical operation and sends it in a header (Idempotency-Key: 6c2f...). The server stores the key alongside the result of the first request it processes with that key; if the same key arrives again — because the client retried after a timeout — the server returns the original stored response instead of processing the operation a second time. This is the same "at-least-once delivery + dedup" pattern that reappears, at a bigger scale, in Messaging, Queues & Event-Driven Architecture and Distributed Transactions, Sagas & Idempotency — a client retry is a miniature version of the exact-once-delivery problem distributed systems fight everywhere.

Pagination: offset vs. cursor

Any collection endpoint that can grow needs pagination — an unbounded GET /orders that returns every row is a latency and memory time bomb that just hasn't gone off yet. There are two dominant strategies, and they trade off differently.

Offset pagination
GET /orders?offset=200&limit=20. Simple, supports "jump to page 7," but two failure modes: the database still has to scan and discard the first 200 rows (gets slower as offset grows — a preview of SQL Deep-Dive & Query Performance), and rows inserted or deleted between page fetches shift every subsequent offset, causing skipped or duplicated items for a client paging through a live, mutating collection.
Cursor (keyset) pagination
GET /orders?after=cursor_xyz&limit=20, where the cursor encodes the last-seen row's sort key (often an ID or timestamp, sometimes both for a stable tie-break). The next page's query becomes WHERE (created_at, id) > (last_created_at, last_id) ORDER BY created_at, id LIMIT 20 — a query an index serves directly, with no growing scan, and stable under concurrent inserts because it never re-numbers positions. The cost: no "jump to page 7," and the cursor is an opaque token, not a page number.
! Caution

Default to cursor pagination for anything that's actively written to while being paged (feeds, logs, order lists) — it's the difference between "consistent under concurrent writes" and "quietly drops or repeats rows for some users, some of the time," which is a brutal bug to reproduce because it depends on write timing. Offset pagination is fine for small, mostly-static, or admin-only lists where "jump to an arbitrary page" genuinely matters more than that correctness guarantee.

Filtering, sorting, and the shape of query parameters

Query parameters are the conventional place for anything that narrows or orders a collection without changing which resource you're addressing: GET /orders?status=shipped&sort=-created_at&limit=50. Keep the convention consistent across your whole API — the same parameter name for the same concept everywhere (always limit, never page_size on one endpoint and limit on another) — because inconsistency is what actually generates client tickets; the specific convention you pick matters less than picking one and holding the line. Always cap limit server-side regardless of what the client requests (min(requested, 100), say) — an uncapped limit parameter is just unbounded pagination with extra steps.

Error-contract design

A status code alone rarely gives a client (or the engineer debugging a client's bug reports) enough to act on. A consistent, structured error body is one of the highest-leverage, lowest-effort things an API can do for the people who consume it: 

{
  "error": {
    "code": "insufficient_inventory",
    "message": "Cannot fulfill order: 2 units of SKU-4471 requested, 0 in stock.",
    "field": null,
    "request_id": "req_9f2c1e"
  }
}

A machine-readable code (stable, for programmatic branching) alongside a human-readable message (for logs and debugging, not for building conditional logic against — messages change wording; codes shouldn't), an optional field for validation errors, and a request_id that ties the response back to your server-side logs and traces (foreshadowing Observability) turns "the API returned an error" into "the API returned a specific, traceable, actionable error."

! Pitfall

Two error-contract mistakes account for most of the pain in practice. First, returning 200 OK with an {"error": true} body — this breaks every piece of generic HTTP tooling (load balancers, monitoring, client HTTP libraries' error handling) that classifies success by status code, not body content. Second, leaking internals in a 500 response — a raw stack trace, a SQL error message, or an internal file path handed straight to the client is both an information disclosure risk (see Backend Security & the OWASP Top 10) and useless to a legitimate caller, who can't do anything with "NullPointerException at OrderService.java:142." Log the detail server-side against the request_id; return the client a stable, generic message.

Versioning and backward compatibility

An API is a contract with every client that has ever integrated against it, and some of those clients you can't force to redeploy on your schedule (a mobile app in app-store review, a partner's server you don't control). The practical discipline is knowing which changes are safe to ship without a version bump and which aren't:

ChangeBreaking?Why
Adding a new optional field to a responseNoWell-behaved clients ignore unknown fields
Adding a new optional request parameterNoExisting requests without it keep working
Removing a fieldYesAny client reading it breaks
Renaming a fieldYesIdentical to removal, from the client's view
Changing a field's type or meaningYesSilent breakage — often worse, because it may not error, just misbehave
Making an optional request field requiredYesExisting requests that omit it now fail

When you do need a breaking change, the two conventional mechanisms are a version segment in the URL (/v2/orders) or a version in a header (Accept: application/vnd.myapi.v2+json). URL versioning is more visible and cache-friendly (a CDN can key on the path); header versioning keeps URLs stable as the canonical resource identifier and is arguably more "correct" REST — most real APIs pick URL versioning anyway for its operational simplicity. Either way, the discipline that matters more than the mechanism: keep the old version fully functional for a published deprecation window, announce it, and only remove it after the window closes — "we shipped a breaking change with no notice" is the failure mode versioning exists to prevent, and skipping the deprecation window recreates it even with a version number in place.

★ ML-systems bridge

A model-serving endpoint is a REST API with an extra dimension: the model version is part of the contract too, not just the schema. POST /v1/predict silently swapping the underlying model for a retrained one is exactly the "changing a field's meaning" breakage above, just harder to notice because the response still type-checks — it's a distribution shift instead of a parse error. The same fixes apply: version the model explicitly in the path or a header (model_version: churn-v3), keep the previous model callable during a rollout, and treat "which model produced this prediction" as required, traceable metadata — the inference-time analogue of the request_id above, and a prerequisite for catching training-serving skew (covered in ML Systems as Backend Systems). Idempotency keys matter here too: a client retrying a timed-out inference call against a non-deterministic or side-effecting model (one that writes a prediction to a ledger) needs the same dedup guarantee as a retried payment.

    Fixed design

    1. A PUT /carts/91 handler fully replaces the cart's state on every call, but also sends a "cart updated" notification email each time it's invoked. Is this endpoint idempotent?

    Idempotency is about the total observable effect of repeating the call, not just the primary resource's final state. A side effect that fires on every call (an email, a webhook, an audit-log append) breaks the contract even when the "main" resource ends up identical — which is exactly why a retry layer that trusts the verb blindly can still cause damage.

    2. Why does cursor (keyset) pagination stay stable under concurrent inserts, while offset pagination can skip or duplicate rows?

    Offset pagination asks "give me the rows starting at position 200" — a position that silently shifts if rows are added or removed before it. Cursor pagination asks "give me rows after this specific row's key," which stays correct regardless of what happens elsewhere in the table.

    3. A team adds a required shipping_zone field to the request body of an existing, widely-integrated POST /orders endpoint, with no version bump. What's the risk?

    Adding an *optional* field is safe; adding a *required* one is not, because every existing request that omits it now fails validation. This is exactly the kind of change that needs either a default value (keeping it optional) or a genuine version bump with a deprecation window for the old behavior.
