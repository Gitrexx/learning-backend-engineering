Foundations // 03

Concurrency, Threads & Async I/O

The request lifecycle page treated "the app server handles the request" as one box. The networking page flagged that a connection pool is a finite resource. This page opens both of those boxes: what actually happens inside a single process the moment more than one request needs attention at the same time — which, in production, is always. Get this model right and you can reason about throughput, tail latency, and the specific way a service falls over under load. Get it wrong and "just add more threads" or "just use async" becomes cargo-culting instead of engineering.

Blocking vs. non-blocking I/O

Almost every backend request spends most of its time waiting, not computing — on a database round trip, a downstream HTTP call, a disk read. The question that defines your concurrency model is: what does the thread do while it waits?

Blocking I/O
The calling thread issues the I/O operation and is suspended by the OS until it completes — it cannot do anything else in the meantime. Simple to reason about (code reads top-to-bottom, one line at a time) but the thread is dead weight for the whole wait.
Non-blocking I/O
The thread issues the operation and immediately moves on to other work; the OS notifies it (via a mechanism like epoll, kqueue, or IOCP) when the operation is ready, and a scheduler resumes the associated work. One thread can have thousands of I/O operations in flight at once because it's never sitting idle waiting on any single one.

Neither is "better" in the abstract — they're a trade between programming simplicity and the number of concurrent waits a thread can absorb. The three concurrency models below are really just three different answers to "how many blocking waits do I let pile up, and on what?"

A fourth model is worth knowing by name even though it's less common in typical backend frameworks: green threads / M:N scheduling — Go's goroutines, Erlang's processes. The language runtime multiplexes many cheap, growable-stack "logical" threads onto a small number of real OS threads, and the runtime scheduler itself switches a goroutine off its OS thread when it blocks on I/O — giving you thread-per-request's simple blocking-style code with close to an event loop's per-unit cost. It's why Go services routinely handle tens of thousands of concurrent connections with ordinary-looking blocking code and no callback soup.

★ Insight

Every one of these models is solving the same constraint from a different angle: a real CPU core can only execute one instruction stream at a time, but a request spends most of its life waiting on something that isn't the CPU. The models differ in how cheaply they can "park" a waiting request and resume something else. Thread-per-request parks it on an OS thread (expensive to create, cheap to reason about). An event loop parks it as a tiny callback record (cheap to create, harder to reason about — no linear top-to-bottom control flow without async/await sugar). Green threads try to get both.

The C10k problem

In the late 1990s, "handle 10,000 concurrent connections on one server" was a research problem, not a Tuesday. Thread-per-connection was the default model, and it fell over for two compounding reasons: each thread reserved megabytes of stack (10,000 threads × a few MB is real, provisioned memory, most of it never touched), and the OS scheduler's cost to context-switch between threads grows with the number of runnable threads — at high counts, the machine spends more cycles deciding what to run next than running it.

The fix that defined the next twenty years of server design was the non-blocking, event-driven I/O model: epoll (Linux), kqueue (BSD/macOS), and IOCP (Windows) let a single thread ask the kernel "wake me when any of these thousands of sockets is ready," instead of dedicating a thread to block on each one individually. nginx, Node.js, and every modern async runtime (Python's asyncio, Java's Netty, Rust's tokio) are built on exactly this primitive. It's why a single nginx process comfortably reverse-proxies tens of thousands of concurrent connections that would need tens of thousands of threads — and tens of gigabytes of stack — under the old model.

i Note

"C10k" is dated — modern hardware and kernels have pushed the frontier to C10M (ten million) in specialized cases — but the underlying lesson didn't expire: the cost of concurrency has to scale with the number of things waiting, not with a fixed per-connection overhead. That's the lens for evaluating any concurrency model you're handed.

CPU-bound vs. I/O-bound work — and why the distinction is everything

The table above has one row that should stand out: an event loop is excellent for I/O-bound work and poor for CPU-bound work, on the same thread. This isn't a minor caveat — it's the single most common way people misapply async frameworks in production.

An event loop's superpower is that when a callback hits a non-blocking I/O call, it yields control back to the loop, which goes and runs some other pending callback while the I/O completes in the background. But if a callback instead does something CPU-bound — parsing a large JSON body, running a regex against megabytes of text, computing a hash, running a small ML model inline — it never yields. It runs to completion on the one thread the loop has, and every other pending request, no matter how simple, waits behind it. A single slow CPU-bound handler doesn't just slow down its own request; it stalls the entire process.

! Pitfall

This is why Node.js and Python's asyncio both push CPU-heavy work out of the event loop entirely — into a worker thread pool (Node's worker_threads, Python's loop.run_in_executor) or a separate process. "Just make it async" does nothing for CPU-bound work; awaiting a function that doesn't actually do I/O just delays when the blocking happens, it doesn't remove the block.

Python adds a wrinkle worth knowing precisely: the Global Interpreter Lock (GIL) means only one thread executes Python bytecode at a time, even on a multi-core machine — so Python threads don't give you CPU parallelism for CPU-bound work no matter how many you spawn. They still help for I/O-bound work, though, because the GIL is released during blocking I/O calls (the C extension doing the socket read drops the lock while it waits), letting another Python thread run. That's why a Python web server can use a thread pool productively for I/O-bound handlers, but reaches for multiprocessing (separate processes, separate interpreters, separate GILs) or a native extension for CPU-bound parallelism.

Backpressure: what happens when arrivals outpace processing

Every queue in front of a fixed-capacity worker pool — a thread pool's task queue, an event loop's pending-callback queue, a message broker's topic — eventually faces a moment where requests arrive faster than they can be drained. What the system does next is called backpressure, and there are exactly three honest options:

  • Let the queue grow unbounded. Latency climbs without limit as requests wait longer and longer; eventually memory holding the queued requests exhausts and the process dies — the worst outcome, because it took down requests that hadn't even started yet.
  • Bound the queue and reject when full. New requests get an immediate, fast failure (503, connection refused) once the queue hits a cap, instead of joining a line that will never be served in time. This preserves latency for the requests already in-flight at the cost of visibly failing some traffic.
  • Shed load deliberately, upstream. Rate-limit or reject at the edge — before work even enters the queue — often prioritizing by request type (fail health checks last, fail best-effort background jobs first). This is the mature version of option 2, chosen deliberately rather than discovered accidentally.

Option 1 is the default in far more systems than anyone intends, because an unbounded queue is the path of least resistance to write and looks fine in every test that doesn't push past capacity. It's also the shape of nearly every "service fell over at 3 AM" incident that traces back to one slow downstream: not a crash, a queue that never stopped growing.

The Load ρ readout is a preview of a formula you'll use constantly once you reach Performance, Profiling & Capacity Planning: for N servers each taking S seconds per request, serving arrivals at rate λ, the offered load is ρ = λ·S / N. Below 1, the system is stable — a queue may fluctuate but drains. At or above 1, arrivals outpace service capacity and the queue grows without bound, no matter how the moment-to-moment randomness shakes out. Notice that the event loop's ρ in I/O-bound mode uses a tiny S (registering a callback is cheap) and effectively N=∞ workers-worth of waiting capacity — which is exactly why it can shrug off request rates that would drown a modest thread pool. Flip to CPU-bound mode and the event loop's effective N collapses to 1, and its ρ rockets past the thread pool's.

Pool exhaustion: the anatomy of a 3 AM incident

The networking page's connection-pool caution said sizing a pool wrong causes two failures. Here's the full mechanism for one of them, because it's the single most common cause of a cascading outage: a service calls a downstream that gets slow (not down — slow, which is worse, because health checks and circuit breakers built for "down" don't trip). Every thread that calls it blocks longer than usual. The thread pool's queue starts absorbing new requests instead of draining them. Once the queue is full, every request to the service — including ones that don't even touch the slow downstream — waits behind it, because they're all sharing the same finite pool. A dependency problem for one endpoint becomes an outage for the whole service.

This is precisely ρ crossing 1: the downstream getting slower increased S (service time per request), and nothing else in the system compensated, so the pool that was comfortably under capacity a minute ago is now unboundedly backed up. The fix previewed here — and covered properly in Resilience Patterns — is to bound the wait: a tight timeout on the downstream call stops S from growing without limit, and a bulkhead (a separate, smaller pool dedicated to that one downstream) stops its queue from cannibalizing capacity that unrelated requests need.

★ ML-systems bridge

Model-serving frameworks live directly on top of this chapter. FastAPI + Uvicorn is an event loop under the hood — great for the I/O-bound parts of serving (auth checks, feature store lookups, calling other services), terrible if you run inference synchronously inside an async def handler, because a GPU call or heavy CPU preprocessing blocks the loop exactly like the pitfall above. That's why production servers (Triton, TorchServe, most hand-rolled ones) push inference onto dedicated worker processes or threads and keep the request-handling loop purely I/O-bound. Dynamic batching — buffering several requests for a few milliseconds so the GPU processes them as one larger batch — is a deliberate backpressure/throughput trade: it adds queueing latency per request (bad for p99) in exchange for far higher throughput per GPU-second (good for capacity), the same ρ = λ·S/N trade-off as the widget above, just with N cast as "GPU batch slots" instead of threads.

1. A thread pool has N=10 threads, each request takes 200ms of blocking work, and requests arrive at 40 req/s. What does queueing theory (ρ = λ·S/N) predict?

ρ = (40 × 0.2) / 10 = 0.8. Below 1 means the queue drains on average, but 0.8 is close enough to capacity that variance in arrivals or service time will regularly push instantaneous load over 1, causing visible queueing and tail-latency spikes even though the long-run average looks fine.

2. Why does a single-threaded event loop handle 10,000 concurrent I/O-bound connections well, but a single CPU-bound request can stall all of them?

The event loop's entire advantage comes from parking cheap, yielding waits instead of expensive OS threads. That advantage only applies to work that yields (non-blocking I/O). CPU-bound work runs to completion on the loop's one thread, blocking every other pending callback — the fix is to move it to a worker thread/process pool, not to wrap it in async/await.

3. A service's thread pool starts backing up after a downstream API becomes slow (not down). Requests to endpoints that never call that downstream also start timing out. What's the most direct fix previewed in this chapter?

A slow downstream increases S (service time) for the threads calling it; without a timeout, S is effectively unbounded and every thread can end up stuck waiting. Because all endpoints share one pool, that backup starves unrelated requests too — a bulkhead (a separate pool per downstream) contains the damage, and a timeout stops S from growing without limit. Growing the pool just delays the same failure at a higher threshold; it doesn't remove the shared-fate problem.
