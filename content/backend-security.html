Backend Security & the OWASP Top 10

Authentication & Authorization Done Right covered getting identity and access decisions right by design. This page covers what happens when a service's other trust boundaries fail — the input from a client that turns out to be a program instead of data, the config file that ends up in a public repo, the endpoint that quietly trusts a client-supplied URL. None of these bugs require a sophisticated attacker; they require an unvalidated assumption and someone curious enough to poke at it. The goal here isn't to memorize a checklist — it's to build the reflex of asking "what happens if this input is hostile?" for every boundary a service exposes, which is exactly the reflex a senior backend interview is testing for when it asks "how would you secure this design."

A practical threat model: the OWASP Top 10

The OWASP Top 10 is the industry's running consensus on the most impactful web-application risk categories, rebuilt periodically from real incident and bug-bounty data. It isn't a spec to implement — it's a threat model: a list of the ways backend services most commonly get broken into, ranked by how often and how badly. Several categories are already covered elsewhere in this roadmap; this page focuses on the ones that are this page's job.

Injection: never let input become code

Injection happens whenever untrusted input is concatenated into a command interpreter — SQL, a shell, an LDAP query, a NoSQL query operator — instead of being passed as pure data the interpreter can never reinterpret as instructions. The fix is structurally the same everywhere: separate the code from the data at the API boundary instead of trying to sanitize your way to safety after the fact.

TypeVulnerable patternFix
SQL injection"SELECT * FROM users WHERE id=" + idParameterized queries / prepared statements (WHERE id = ?) or a query builder/ORM that parameterizes by default
OS command injectionexec("convert " + filename + " out.png")Avoid shelling out to build commands from input at all; if unavoidable, use an argument-array API (never a shell string) and an allowlist of permitted values
NoSQL injectiondb.users.find({ password: req.body.password }) where password can be {"$ne": null}Validate input types strictly (reject objects where a scalar is expected) before it reaches the query layer
LDAP / XPath injectionBuilding a filter string from raw inputUse the driver's parameterized filter API, same principle as SQL
★ Insight

This is the same root cause named in the JWT section of Auth & Access: letting untrusted input dictate how the system interprets it. A parameterized query sends the SQL text and the values in separate channels to the database — the database never re-parses the values as SQL syntax, no matter what characters they contain. String concatenation collapses code and data into one channel, and every injection bug is a consequence of that collapse.

Broken access control, beyond the IDOR basics

Auth & Access introduced broken object-level authorization — a valid identity reading a resource it doesn't own because the ownership check never ran. It's OWASP's #1-ranked risk for a reason: it's the natural failure mode of any endpoint that authenticates correctly but forgets that authentication and authorization are two separate checks. A few more shapes it takes in real systems:

  • Mass assignment. A create/update endpoint blindly binds the entire request body onto a model (Object.assign(user, req.body)). Nothing stops a client from including a field they were never shown a form for — {"role": "admin"} in a profile-update payload. Fix: bind an explicit allowlist of fields, never the raw body.
  • Path traversal. A file-serving endpoint builds a path from user input (/files?name=report.pdf → readFile("./uploads/" + name)) and never rejects ../../etc/passwd. Fix: resolve the path and verify it's still inside the intended directory before opening it, and reject any input containing .. outright.
  • Missing function-level authorization. An admin-only route is hidden from the UI but never actually checks the caller's role server-side — "security through obscurity" that a client with a URL and a valid session defeats trivially.
  • CORS misconfiguration. Reflecting Access-Control-Allow-Origin back as whatever Origin header the browser sent, combined with Access-Control-Allow-Credentials: true, lets any site make authenticated cross-origin requests on a logged-in user's behalf.
! SSRF — access control turned inside out

Server-Side Request Forgery is what happens when an endpoint accepts a URL from the client and fetches it server-side — an image-import feature, a webhook-validation ping, a PDF-from-URL export. The server, not the attacker, makes the request, which means it can reach anything the server's network position can reach: internal admin panels with no auth in front of them, or (the classic cloud incident) a metadata endpoint like http://169.254.169.254/ that hands back the instance's IAM credentials with no authentication at all. The fix is an allowlist of permitted destination hosts/schemes, never a denylist — attackers have an endless supply of redirect chains, DNS rebinding tricks, and alternate IP encodings to slip past a blocklist.

Secrets management

A database password, an API key, a signing key — none of it belongs in source control, ever, including in a "private" repo (repos go public by accident, get forked, or get cloned onto a laptop that's later lost) and including in a Docker image layer (layers are cacheable and shippable independently of the final image). The credential itself isn't the only thing at risk — a leaked credential in git history stays leaked even after you delete the file, because the commit history still has it.

  • Inject at runtime via environment variables or a secrets manager (Vault, AWS Secrets Manager, GCP Secret Manager) that the app fetches from at startup — never bake a secret into an image or config file that lives in the repo.
  • Scope narrowly. A service that only reads from one table shouldn't hold credentials that can write to every table — this is the principle of least privilege, covered fully below.
  • Rotate routinely, not reactively. If rotation is a rare, manual, high-stakes event, it will keep getting postponed until a breach forces it under worse conditions. If it's a scheduled, automated non-event, a suspected leak becomes a button-press instead of a fire drill.
  • Scan for leaks in CI. Automated secret-scanning on every commit (gitleaks, truffleHog, GitHub's native scanning) catches an accidentally-committed key before it ever reaches a public branch — a concrete instance of the CI security gates from Testing Backend Systems.

Transport security

Networking & Protocols for Backend Engineers covered what TLS does mechanically; here's what "done right" means operationally. TLS should terminate on every hop that crosses a network you don't fully control — not just the public edge. Plaintext HTTP between your load balancer and app servers is fine only if you're certain that link never leaves a trusted network; in a cloud VPC shared with other tenants, or across an availability zone boundary, it usually isn't a safe assumption.

  • HSTS (Strict-Transport-Security) tells the browser to never even attempt a plaintext connection to your domain again, closing the window for a downgrade/strip attack on the very first request.
  • Redirect HTTP → HTTPS at the edge, and don't serve any sensitive content over the plaintext listener even transiently.
  • Keep certificates and TLS versions current — disable TLS 1.0/1.1 and weak cipher suites; a load balancer or API gateway usually manages this centrally so individual services don't each need an opinion.

Input validation & output encoding

These are two different jobs that get conflated constantly. Validation decides whether input is well-formed enough to process at all (right type, right shape, within bounds) — reject early, at the boundary, with an allowlist of what's acceptable rather than a denylist of known-bad patterns (a denylist only stops the attacks you already thought of). Output encoding is a separate, later step: making sure data is safe for the specific context it's about to be rendered or interpreted in.

! Pitfall — cross-site scripting (XSS)

XSS is what happens when user-supplied data is written into an HTML page without context-appropriate encoding, letting an attacker's <script> or event handler run in another user's browser session — with that user's cookies, DOM access, and ability to act as them. Stored XSS (a malicious comment saved to a database and rendered for every future visitor) is the most dangerous variant; reflected XSS bounces attacker input straight back from a single request (often via a crafted link); DOM-based XSS never touches the server at all — client-side JS writes untrusted data (like location.hash) directly into the DOM. The fix is encoding output for the context it lands in — HTML-entity-encode for HTML body text, attribute-encode inside an attribute, JS-string-escape inside a <script> block — and, as defense-in-depth, a Content-Security-Policy header that refuses to execute inline scripts at all, so even a successful injection has nothing to run.

! Caution — insecure deserialization

Formats like Python's pickle or Java's native serialization can encode executable behavior, not just data — deserializing an untrusted byte stream in these formats can mean handing an attacker arbitrary code execution before your application code even runs. Never deserialize untrusted input with a format capable of this. Prefer data-only formats (JSON, protobuf per Beyond REST) for anything crossing a trust boundary, and if a rich format is genuinely required, validate a strict schema and run the deserializer in a sandboxed, unprivileged process.

Rate limiting & abuse prevention

Not every hostile request is malformed — a login endpoint hit with valid-looking credentials a million times a minute (credential stuffing), or a public API scraped at a rate no real user would generate, are attacks made entirely of "valid" requests. Resilience Patterns covered rate limiting as a stability mechanism against accidental overload; the same token-bucket/sliding-window machinery is also your first line of defense against deliberate abuse — the difference is only intent, not implementation.

  • Layer the key you limit on. Per-IP alone is trivially defeated by a botnet or a residential proxy pool; pair it with per-account and per-API-key limits so a single compromised account can't be hammered from everywhere at once.
  • Limit sensitive endpoints tighter than general traffic — login, password reset, and payment endpoints deserve their own stricter budget independent of the general API limit, since they're the ones an attacker actually wants to brute-force.
  • Respond uniformly. A login endpoint that returns "wrong password" vs. "no such user" leaks which usernames exist — return the same generic failure either way, and apply the same timing regardless of which check failed (a fast-fail on "no such user" is itself a timing side-channel).

Principle of least privilege, tying it together

Nearly every mitigation on this page is a specific application of one idea: grant the minimum access that lets a component do its actual job, nothing more. It shows up at every layer —

  • Database users scoped per service, with only the tables and operations that service needs (a reporting job gets read-only, never write).
  • IAM roles / service accounts scoped to specific resources and actions, not broad admin roles reused everywhere because it's convenient.
  • Secrets scoped to exactly the systems that need them, rotated on a schedule.
  • Network segmentation — a database with no route from the public internet is safe from a whole category of attack regardless of what application-layer bugs exist upstream.

The payoff of least privilege isn't preventing the initial bug — it's bounding the blast radius once one inevitably slips through. A SQL injection in a service whose DB user can only SELECT from two tables is a bad day; the same bug against a superuser DB connection is a breach disclosure.

★ ML-systems bridge

Prompt injection is this era's SQL injection, with the same root cause: untrusted text (a user message, a scraped web page, a retrieved document) gets concatenated into the same channel as trusted instructions, and the model can't reliably tell which is which — the fix, as with SQL, is separating the "code" (system instructions) from the "data" (retrieved/user content) as rigorously as the platform allows, and treating anything a model does as a result of untrusted input as itself untrusted. Model-serving and feature-store endpoints need the exact object-level authorization checks covered above and in Auth & Access — a caller authenticated to query the recommendation service isn't automatically entitled to every feature it computed, especially features scoped to a different tenant or a higher privacy tier. And an "import training data from this URL" or "fetch this image to embed" feature is a textbook SSRF surface: the model server, not the attacker, makes the outbound request, so it needs the same host allowlist discipline as any other server-side URL fetch.

1. An endpoint builds a database query by concatenating a user-supplied string directly into SQL text. What's the structurally correct fix?

Stripping characters is a denylist that the next creative payload slips past, and HTML encoding defends against XSS in a browser, not SQL injection in a database. Parameterization is the only fix that removes the vulnerability structurally, by keeping code and data in separate channels.

2. A profile-update endpoint does Object.assign(user, req.body) and saves the result. A client includes "role": "admin" in the request body even though the UI never exposes that field. What's this bug called, and what's the fix?

Nothing on the server stops a client from sending a field the UI never renders — a raw HTTP client, not the UI, is what an attacker actually uses. The fix is binding an explicit, server-defined allowlist of updatable fields instead of trusting the whole request body.

3. A "fetch a preview image from this URL" feature lets the server make an HTTP request to any URL the client supplies. What's the risk category, and the right mitigation?

SSRF is exactly this shape: a feature that makes the server issue an attacker-controlled outbound request. Denylisting known-bad hosts loses to redirects and DNS rebinding; the durable fix is an allowlist of destinations the feature is actually meant to reach.
