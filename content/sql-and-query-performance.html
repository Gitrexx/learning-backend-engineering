DATA & DATABASES // 02

SQL Deep-Dive & Query Performance

Relational Data Modeling covered the shape of the data — the schema that determines which bugs are possible before any code runs. This page covers the other half: what actually happens when that schema meets a query. The same SELECT, against the same schema, can return in 2 milliseconds or 2 minutes depending entirely on how the database chooses to execute it — and that choice is invisible unless you know how to ask for it. Of every skill in this course, reading a query plan and knowing why it's slow is the one you'll use the most: most production "the database is slow" incidents are not exotic distributed- systems problems, they're one query doing something needlessly expensive, and the fix is usually a single index or a rewritten predicate.

How a query actually executes

SQL is declarative — you state what you want, not how to get it. Turning that statement into an actual sequence of steps is the job of four stages every query passes through:

Parse
Check the SQL is syntactically valid and refers to real tables/columns; build a parse tree.
Plan / optimize
The query planner (optimizer) considers multiple physical ways to execute the same logical query — different access paths, join orders, join algorithms — estimates the cost of each using table statistics, and picks the cheapest one it can find. This is the stage that decides whether your query is fast or slow.
Execute
The chosen plan runs: a tree of physical operators (scan nodes, join nodes, sort nodes) that pull rows from each other, bottom-up.
Return
Rows stream back to the client, often before the whole result set is even materialized.

The planner is doing a genuinely hard combinatorial search — for a query joining five tables, there are thousands of possible join orders and algorithm combinations — so it isn't guaranteed to find the true optimum, only a good-enough one under a cost model. That cost model is only as good as the statistics feeding it, which is why "the planner picked a bad plan" is almost always really "the planner picked the cheapest plan according to stale or misleading statistics" — a distinction that matters when you go looking for the fix.

Access paths: how a single table gets read

Before any join happens, each table in the query has to be read somehow. The planner chooses between a small set of access paths:

Sequential scan (seq scan / table scan)
Read every page of the table, in physical order, and test each row against the filter. Cost is proportional to table size, regardless of how selective the filter is. No setup cost, no index needed — the reliable fallback.
Index scan
Walk a B-tree index to find the matching key(s), then fetch each matching row from the table's heap by its physical location — one extra, potentially random, page read per matching row (unless that row is already cached). Cost is roughly proportional to how many rows match, not to table size.
Index-only scan
Same as an index scan, but every column the query needs is already present in the index itself, so the heap fetch is skipped entirely (subject to a visibility check against recently-modified rows). Dramatically cheaper than a regular index scan — this is what a covering index buys you.
Bitmap heap scan
A hybrid: use the index to build an in-memory bitmap of matching page locations, sort those locations, then fetch the pages in physical order instead of one random read per row. This is why, in practice, indexes stay competitive at higher selectivity than a naive "one random read per matching row" model predicts — it converts many random reads into fewer, sequential-ish ones.
i Note

The universal rule of thumb: indexes win when few rows match; sequential scans win when many do. If a query matches 40% of a table, reading the whole table once sequentially is cheaper than following an index pointer for every one of those rows — this is exactly why the planner will sometimes, correctly, ignore an index you built. That's not a bug to work around; the widget below lets you find the crossover yourself.

Join algorithms: how two tables get combined

Once each table's rows can be produced, a join has to combine them. There are three physical strategies, and the right one depends on table sizes, whether an index exists on the join key, and whether the inputs are already sorted:

AlgorithmHow it worksFavored when
Nested loop For each row in the outer table, probe the inner table for matches. Outer side is small — cost scales with outer rows × per-probe cost, so it's cheap even against a huge inner table if the inner table has an index on the join key. Without that index, it degrades to comparing every outer row against every inner row — O(N·M), catastrophic past small tables.
Hash join Build an in-memory hash table from the smaller ("build") side, keyed on the join column; scan the larger ("probe") side once, looking up each row in the hash table. Both tables are large, no useful index exists, and there's no ordering to exploit. Cost scales with the sum of both table sizes, not their product — the default workhorse for big, unindexed joins.
Merge join Walk both inputs in join-key order simultaneously, like merging two sorted lists. Both inputs are already sorted on the join key (e.g. from an index scan, or a preceding sort) — then it's the cheapest option, since no hashing or per-row probing is needed. If either input isn't sorted, the planner has to pay for an explicit sort first, which usually makes hash join win instead.

The cost-based optimizer, in one paragraph

For each candidate plan, the planner estimates a cost in abstract units built from a handful of constants — a sequential page read, a random page read (typically modeled as several times more expensive than sequential, since random I/O defeats read-ahead and, on spinning disks, costs a seek), and a small per-row CPU cost. It multiplies those by row-count estimates pulled from statistics the database maintains about each table (row counts, most-common values, histograms of value distribution) — kept fresh by an ANALYZE pass, run automatically after enough rows change. Every part of this depends on those estimates being roughly right. Bulk-load a table and forget to run ANALYZE, and the planner is costing plans using row counts from before the load — often picking a nested loop because it still thinks a table has 100 rows when it now has 100 million.

! Caution

This widget's cost formulas are simplified for teaching, not a reimplementation of any real optimizer — real planners also weigh physical row clustering (a correlation statistic — how close an index's order is to the table's physical order), page-cache residency, parallel workers, and bitmap heap scans that blunt the "random read per row" penalty modeled here. Treat the crossover points as illustrative of the shape of the trade-off, not literal thresholds — then go find the real one with EXPLAIN ANALYZE on your own data, covered next.

Reading EXPLAIN and EXPLAIN ANALYZE

EXPLAIN shows the plan the optimizer would choose, with its cost estimates, without running the query. EXPLAIN ANALYZE actually runs it and adds real numbers alongside the estimate — which is where the interesting bugs live, in the gap between the two: 

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 4821 AND status = 'shipped';

Index Scan using orders_customer_id_idx on orders
  (cost=0.43..612.10 rows=850 width=96)
  (actual time=0.08..41.32 rows=48000 loops=1)
  Index Cond: (customer_id = 4821)
  Filter: (status = 'shipped')
  Rows Removed by Filter: 39
  Buffers: shared hit=210 read=1840
Planning Time: 0.21 ms
Execution Time: 41.58 ms
cost=0.43..612.10
Estimated cost to return the first row and all rows, in the planner's abstract units — useful only for comparing plans against each other, not as wall-clock time.
rows=850 (estimated) vs. actual ... rows=48000
The single most useful number on the page. The planner expected 850 matching rows and got 48,000 — a ~56× misestimate. That gap is exactly the kind of thing that makes a planner pick an index scan (cheap for 850 rows) when a sequential scan would have actually been cheaper for 48,000. Stale statistics after a bulk load, or a correlated filter the planner can't model (rows matching customer_id happen to cluster with status), are the usual causes.
Rows Removed by Filter
Rows the index condition matched that then failed the non-indexed part of the WHERE clause (here, status) — read from the heap for nothing. A composite index on (customer_id, status) would let the index itself filter both columns.
Buffers: shared hit=210 read=1840
hit = pages found already in the database's cache; read = pages pulled from disk. A high read count relative to hit on a query that runs often is a sign of either a cold cache or a working set bigger than available cache — often the real story behind "it's fast the second time I run it."
Planning Time vs. Execution Time
Planning time exploding on a simple query usually means an extremely complex query (many joins, many possible plans to weigh) rather than a data problem.

Anti-patterns that turn a clean schema into a slow query

A well-modeled schema (the previous page) doesn't protect you from a query that defeats its own indexes. These five show up constantly in production code review:

Anti-patternWhy it hurtsFix
N+1 queries Fetch a list of N rows, then loop over them issuing one more query per row (a common ORM default: load orders, then order.customer lazily triggers a separate query per order). N+1 round trips at network latency each dwarfs one query's execution time — 200 orders at 2ms round-trip is 400ms of pure waiting, invisible in any single query's EXPLAIN. A single query with a JOIN, or a batched second query (WHERE customer_id IN (...)) — one round trip either way.
SELECT * Pulls columns you don't need — wasted I/O and network — and silently defeats index-only scans, since the planner needs every selected column present in the index to skip the heap fetch. It's also a schema-change landmine: a column added later changes your result shape without any code change flagging it. Name the columns you actually use. It's more typing and it's worth it.
Functions or casts on an indexed column WHERE LOWER(email) = 'a@b.com' or WHERE created_at::date = '2026-01-01' can't use a plain B-tree index on email/created_at, because the index stores the raw column value, not the transformed one — the predicate is no longer sargable (Search ARGument-ABLE). Rewrite to keep the column bare (created_at >= '2026-01-01' AND created_at < '2026-01-02' instead of casting), or build a functional/expression index that indexes the transformed value directly.
Leading wildcard LIKE WHERE name LIKE '%smith' can't use a standard B-tree index — the tree is ordered by the string's prefix, and a leading wildcard means there's no prefix to seek on, forcing a full scan. LIKE 'smith%' (trailing wildcard only) can use the index fine. If leading-wildcard/substring search is a real requirement, reach for a trigram or full-text index built for that access pattern, not a plain B-tree.
Wrong composite index column order A composite index on (a, b, c) can only be used efficiently for predicates on a alone, (a, b), or (a, b, c) — the leftmost prefix rule. A query filtering on b alone gets no help from that index at all. Order composite index columns by how queries actually filter: equality columns first, then the column used for range filtering or sorting last.
★ ML-systems bridge

Batch scoring jobs get N+1'd constantly: "for each of 10,000 users, fetch their features" as 10,000 separate lookups is the exact same anti-pattern as an ORM lazily loading a customer per order, just wearing a feature-store costume — the fix is the same batched IN (...)/join query instead of a loop. Online, low-latency inference paths take the opposite lesson from the composite-index row above: production feature stores are deliberately designed so the hot lookup is a single-key, index-only fetch — no join, no multi-column predicate to get the order wrong on — because a p99 latency budget of a few milliseconds has no room for a query the planner has to think hard about. When a serving path does need a join (enriching a request with account-tier data, say), the same "small outer side, indexed inner side ⇒ nested loop" reasoning from the widget above is what tells you whether that join is safe at your latency budget or needs to be precomputed and denormalized ahead of time instead.

1. A query's EXPLAIN ANALYZE shows rows=120 estimated but actual ... rows=61000. What does this most directly explain?

The planner picks a plan using its cost estimate, which is built from the row-count estimate. A 500x underestimate means whatever plan looked cheap for 120 rows may be badly wrong for 61,000 — the fix is usually running ANALYZE to refresh statistics, not manually forcing a different plan.

2. A composite index exists on (status, created_at). A query filters only on created_at > '2026-01-01', with no filter on status. What happens?

Composite indexes are only efficiently searchable via their leftmost columns. Skipping straight to the second column without constraining the first means the tree can't be usefully seeked into — the planner falls back to a sequential scan (or a much less efficient full index scan). If created_at-only lookups are common, that needs its own index.

3. Joining a 50-row "outer" table against a 20-million-row "inner" table, with a B-tree index on the inner table's join column. Which join algorithm is almost certainly cheapest, and why?

Nested loop with an index on the inner side is exactly the case it's built for: the outer side is tiny, so 50 cheap indexed probes beats building a 20-million-row hash table or sorting either side. Hash join would still work but pays to scan/hash the full 20 million rows up front — wasted work when only 50 probes are needed.
