Caching Strategies

Every deep-dive so far in this section has been about making the backing store itself faster — better schemas, better indexes, the right data model. Caching is a different move entirely: it's about not asking the backing store at all. A cache is a copy of data, kept somewhere faster to reach than its source of truth, on the bet that the same data will be wanted again soon. Done well, it's the single cheapest latency win available to a backend engineer — often turning a 10ms database round trip into a 0.1ms memory lookup. Done carelessly, it's also one of the more reliable ways to serve a user data that's simply wrong, or to take an entire system down the moment the cache goes cold. Phil Karlton's famous line — "there are only two hard things in computer science: cache invalidation and naming things" — is a joke with a real point: the mechanics of caching are simple, but knowing when a cached value stops being true is genuinely hard, and most production caching incidents trace back to getting that one question wrong.

i Note

A cache is always a trade of consistency for latency. The backing store (usually a database from earlier in this section) remains the source of truth; the cache is a bet that a slightly-stale or eventually-consistent copy is an acceptable price for speed. Every decision on this page — what to cache, how long, how to invalidate — is really a decision about how much staleness a given piece of data can tolerate.

Where caching happens

"Caching" isn't one layer — a single request typically passes through several caches before it ever reaches a database, each solving a different distance problem:

LayerWhat it cachesTypical lifetime
Browser / clientStatic assets, API responses via Cache-Control/ETagSeconds to days

This page focuses mostly on the distributed application cache layer (Redis-shaped), because that's the one you design and operate directly — the others are largely configuration on top of infrastructure someone else built.

The four core caching patterns

These patterns answer two questions independently: who talks to the backing store (the application, or the cache itself), and when does the cache get written relative to the backing store.

Cache-aside (lazy loading)

The most common pattern by far. The application owns the logic: on read, check the cache first; on a miss, read the backing store, then write the result into the cache before returning it. On write, update the backing store and either update or (more often) delete the corresponding cache entry. 

def get_user(user_id):
    cached = cache.get(f"user:{user_id}")
    if cached is not None:
        return cached                      # cache hit
    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    cache.set(f"user:{user_id}", user, ttl=300)
    return user                            # cache miss, now populated

def update_user(user_id, fields):
    db.execute("UPDATE users SET ... WHERE id = %s", user_id)
    cache.delete(f"user:{user_id}")        # invalidate, don't update-in-place

Only requested data ever gets cached (no wasted memory on things nobody reads), and the cache can fail entirely without taking the system down — every read just falls through to the database. The cost: every miss pays the full backing-store latency plus a cache write, and — as the race-condition section below shows — the read-then-write isn't atomic, which opens a real consistency hole.

Read-through

Same idea as cache-aside, but the cache library or a caching layer sits between the application and the store and owns the miss-fill logic itself — the application only ever talks to the cache. Functionally similar to cache-aside from the app's point of view; the difference is architectural (where the fill logic lives), not behavioral.

Write-through

Every write goes to the cache and the backing store synchronously, as one logical operation, before the write is acknowledged. The cache is never stale relative to the store because it's updated in lockstep — but every write now pays cache-write latency on top of store-write latency, and a write is only "done" once both succeed, which needs its own failure handling (what if the cache write fails after the DB write commits?).

Write-behind (write-back)

The write lands in the cache immediately and is acknowledged right away; the write to the backing store happens asynchronously afterward, batched or delayed. This is the fastest write path by far, and it can absorb write bursts the backing store couldn't handle synchronously — but it introduces a durability gap: if the cache node dies before the async write lands, that write is gone. Used selectively, for data where a small durability window is acceptable in exchange for write throughput (view counters, activity feeds) — rarely for anything resembling money.

✕ Pitfall

On cache-aside writes, prefer deleting the cache entry over updating it in place. Updating the cache with the new value duplicates your write logic in two places that can drift out of sync (what if the cache write encodes the value slightly differently than the DB write, or a second concurrent writer interleaves?). Deleting is idempotent and simple: the next read just repopulates from the source of truth. The one cost is an extra cache miss right after a write — almost always worth it for the correctness it buys.

TTLs and eviction: bounding how wrong the cache is allowed to be

A time-to-live (TTL) is a ceiling on staleness: even if nothing ever explicitly invalidates an entry, it disappears after a fixed duration and the next read repopulates it. TTL choice is a direct trade-off:

  • Short TTL → fresher data, but more cache misses, more backing-store load, and less protection if invalidation logic has a bug (the blast radius of a missed invalidation is capped at one TTL window).
  • Long TTL → higher hit ratio, less backing-store load, but staler data for longer, and a missed invalidation stays wrong for longer too.

Separately from TTL, every cache has finite memory, so it needs an eviction policy for what to remove when it's full, even before anything expires:

PolicyEvictsTrade-off
LRU (Least Recently Used)The entry not accessed for the longest timeGood default — matches "recently used data tends to be used again" for most workloads
LFU (Least Frequently Used)The entry accessed the fewest total timesBetter for stable popularity distributions; slower to adapt when popularity shifts
FIFOThe oldest entry by insertion time, regardless of useCheapest to implement; ignores access patterns entirely — rarely the best choice

Redis defaults to no eviction (writes fail once memory is full) unless you configure a maxmemory-policy — in production this is almost always set to an LRU or LFU variant (e.g. allkeys-lru) so the cache degrades gracefully under memory pressure instead of refusing writes outright.

Invalidation: the actually hard part

Expiring by TTL is invalidation on a timer, blind to whether the underlying data actually changed. The harder, more precise problem is invalidating exactly when the data changes, no sooner and no later:

  • Explicit invalidation on write — the cache-aside pattern above: the code path that writes the database also deletes (or updates) the corresponding cache key. Precise, but only as correct as your ability to find every code path that writes that data — a second service, a batch job, or an admin script that writes the database directly and forgets the cache exists is how stale reads sneak back in.
  • Event-driven invalidation — a write publishes a change event (often via change-data-capture off the database's write-ahead log, a preview of the upcoming Messaging, Queues & Event-Driven Architecture deep-dive) and any number of caches subscribe and invalidate themselves. Decouples "who wrote the data" from "who needs to know it changed" — useful when several services cache the same underlying data.
  • Version / tag-based invalidation — instead of deleting individual keys, bump a version number or tag associated with a group of related entries (e.g. user:42:v3); old-versioned keys simply age out via TTL and are never read again because new reads ask for the new version. Sidesteps having to enumerate every related key to delete.
★ Negative caching

Don't forget to cache absence. If a lookup for a nonexistent key hits the database every time (a classic side effect of typos, scrapers, or a missing-row bug upstream), caching the "not found" result for a short TTL stops the backing store from absorbing repeated queries for something that will never exist. This is also the standard defense against a targeted cache penetration attack — deliberately requesting keys guaranteed to miss, to bypass the cache and load the database directly.

The read/write race in cache-aside

Cache-aside's read-fill step is not atomic with the database read it's based on, and that gap is a real, exploitable window under concurrency. Classic sequence with two concurrent actors:

  1. Request A reads the cache for user:42 — miss.
  2. Request A reads the database — gets the old value.
  3. Request B updates the database with a new value, then deletes the cache key (which isn't there yet, so the delete is a no-op).
  4. Request A finishes and writes the old value into the cache.

Now the cache holds a stale value with no pending invalidation to fix it — it will sit there until its TTL expires. This is precisely why a bounded TTL is a safety net, not an optional nicety, even when you have "proper" invalidation: it guarantees this race resolves itself within one TTL window instead of persisting indefinitely. The other common mitigation is a delete-delay / double-delete: delete the cache key again a short delay (a few hundred milliseconds) after the write, to catch exactly this race by cleaning up whatever a straggling read might have written in the meantime.

Cache stampede (thundering herd)

A cache stampede is what happens when a cache miss stops being a rare event and becomes a simultaneous event across many requests — instead of one request quietly repopulating the cache, dozens or thousands hit the backing store at once, for data that's about to be identical once any one of them finishes. Two common triggers:

  • Hot-key concurrent miss — a single popular key expires, and every concurrent request for that key (which could be thousands, for something like a homepage feed or a viral product page) independently sees a miss and independently queries the backing store — for what will be the exact same result.
  • Mass synchronized expiry — many different keys were all populated at the same time with the same TTL (a cold cache after a deploy, or a nightly batch warm-up), so they all expire at the same moment, producing a load spike across the whole key space rather than one key.

Three mitigations, each aimed at a different half of the problem:

FixHow it worksSolves
Locking / request coalescing (single-flight) The first request that misses acquires a short-lived lock (or registers as "the one fetching") and queries the backing store; every other concurrent request for the same key waits and reuses that result instead of issuing its own query. Hot-key concurrent miss — collapses N concurrent misses into 1 backing-store query.
Jittered TTL Add a small random offset to each key's TTL (e.g. base ± 20%) so keys populated at the same time don't expire at the same instant. Mass synchronized expiry — spreads a single spike across a wider window.
Stale-while-revalidate / probabilistic early refresh Serve the slightly-stale cached value immediately while asynchronously refreshing it in the background (or refresh probabilistically before expiry, more likely the closer the entry is to its TTL — the XFetch approach) instead of ever letting requests see a hard miss. Both — no request ever has to wait on a cold cache at all, at the cost of occasionally serving data that's a few seconds stale.
! Caution

A stampede is a genuine "what breaks at 3 AM" scenario: a deploy rolls out, every app instance restarts with an empty in-process cache (or a shared cache gets flushed), and the resulting synchronized flood of backing-store queries can be enough to tip the database over — which then makes every retry slower, which increases concurrent in-flight requests further, which makes it worse. This is the same feedback loop the upcoming Resilience Patterns deep-dive covers for retries in general; caching just gives it a very common entry point.

Consistency hazards beyond staleness

Two more failure modes worth naming explicitly, because they're easy to overlook until they bite:

  • Split-brain across cache and store during a partial failure. If the cache write in a write-through pattern fails after the database write already committed, the two are now out of sync with no automatic reconciliation — worth deciding up front whether that failure mode should retry, alert, or fall back to deleting the cache key so the next read repopulates from the (correct) database.
  • Big keys and hot keys in a distributed cache. A single oversized cached value (a multi-megabyte serialized object) can dominate network bandwidth to one Redis node and blow past its response-time budget; a single overly popular key can concentrate all traffic on one shard even when the rest of the cluster is idle, since consistent hashing (from the earlier indexing deep-dive's cousin — full treatment in Replication & Partitioning) places one key on one node by design. Both are operational smells worth actively monitoring for, not theoretical edge cases.

Redis in practice

Redis is the default distributed-cache choice in most production stacks, and it's worth knowing why: it's an in-memory key-value store (see the earlier NoSQL deep-dive) with rich native data structures beyond plain strings — hashes, sorted sets, lists, sets, and streams — which means it can often serve as a cache and a lightweight materialized index at once (a sorted set as a live leaderboard, a hash as a partial-object cache you can update one field at a time instead of round-tripping the whole blob). It supports TTLs and eviction policies natively, and offers optional persistence (RDB snapshots, an AOF write log) for the cases where losing the cache entirely — not just having it cold — would be a real outage rather than a performance blip. In cluster mode, keys are sharded across nodes by hash slot, which is where the hot-key problem above becomes concrete: one popular key still lives on exactly one shard, cluster or not.

★ ML-systems bridge: two very different "KV caches"

Worth disambiguating a name collision that trips up ML engineers specifically: the KV cache in transformer inference (caching each token's attention key/value projections so autoregressive decoding doesn't recompute them from scratch every step) shares a name with, but is not, the key-value caching this page describes — it's a per-request, in-memory data structure local to one inference pass, not a shared, persistent cache across requests. The caching pattern that does map directly is semantic response caching in front of an LLM API: cache-aside, keyed by a hash (or embedding-similarity match) of the prompt, to skip a full model call for a repeated or near-duplicate question. It inherits every hazard on this page — a prompt-template change or a model version bump is exactly the "wrote the database directly and forgot the cache" invalidation gap, and a viral prompt going cold at the same instant as thousands of similar concurrent requests is exactly the hot-key stampede above, just with a much more expensive "backing store" (a GPU inference call) behind it.

What's next

Caching lets one machine punch above its weight — but eventually one machine, cache or not, runs out of headroom. The next deep-dive, Scaling & Load Balancing, is where the roadmap turns from "make one machine fast" to "add more machines" — starting from why statelessness (a theme since Anatomy of a Backend Service) is the precondition that makes horizontal scaling possible at all.

1. A service uses cache-aside and, on every write, updates the cache entry in place (instead of deleting it) to "save a round trip." What's the main risk this introduces?

Deleting is the safer default specifically because it has no way to encode the new value incorrectly — the next read simply repopulates from the database. Updating in place duplicates write logic and is exposed to the same read/write race described on this page.

2. A popular product page's cache entry expires, and 4,000 concurrent requests all miss at the same instant, each independently querying the database for identical data. Which mitigation targets this specific failure mode?

Jittered TTL solves *mass* expiry across many different keys populated at the same time — it doesn't help when many concurrent requests hit the *same* key at once. That's exactly what request coalescing / single-flight locking is for.

3. Why is a bounded TTL still worth setting even on data that has "proper" explicit invalidation on every write path?

Explicit invalidation only covers write paths you remembered to wire up, and doesn't protect against the read/write race itself. A TTL is a correctness safety net, not just a memory-management knob — it bounds how long any missed or raced invalidation can persist.
