DATA & DATABASES // 04

Transactions, ACID & Isolation Levels

Every deep-dive so far assumed a single query running alone. Production databases never work that way — dozens or thousands of transactions run concurrently, many touching the same rows. What happens when two of them overlap is not obvious, and getting it wrong doesn't throw an exception; it silently produces a wrong answer that looks fine until an audit, a double-booked seat, or a bank balance that doesn't add up surfaces it. This page is about the guarantees a database gives you under concurrency and failure, precisely enough that you can reason about which guarantee you actually need — because the honest answer to "what isolation level should I use" is almost always "it depends on which anomaly you can't afford," not "the strictest one, always."

ACID, precisely

ACID names four guarantees a transaction gives you. Each is doing different work, and conflating them is a common source of fuzzy reasoning:

Atomicity
A transaction's writes happen all or nothing. If a transaction touches three rows and crashes after the second write, the database guarantees you see neither write, not just one — implemented via a write-ahead log (WAL) that lets a crash-recovery pass roll back anything not confirmed committed.
Consistency
The database moves from one valid state to another — application-defined invariants (foreign keys, check constraints, "balance can't go negative") hold before and after every transaction. Unlike the other three letters, the database doesn't fully deliver this one for you; it enforces the constraints you declare, but an invariant you never told it about (e.g. "the sum of two accounts must stay constant during a transfer") is on you to preserve inside the transaction logic.
Isolation
Concurrent transactions don't see each other's uncommitted, or sometimes even committed, intermediate state — exactly how much they're shielded from each other is a dial, not a fixed guarantee, and it's the subject of the rest of this page.
Durability
Once a transaction commits, it survives a crash — the WAL record is fsync'd to durable storage before the client is told "committed," so a power loss a millisecond later can't undo an acknowledged write.
i Note

The "C" in ACID and the "C" in CAP (covered later in Consistency Models, CAP & Consensus) are different guarantees that happen to share a letter — ACID's Consistency is about application invariants on a single node; CAP's Consistency is about whether replicas agree with each other. Interviewers use this collision to check whether you're pattern-matching on the word or actually understand both. Keep them separate in your head.

What isolation actually protects you from: four anomalies

"Isolation" is really shorthand for "which of these things can't happen." Four anomalies show up over and over, and the isolation levels are literally defined by which subset of them each one rules out:

AnomalyWhat happensWhy it's dangerous
Dirty read T1 reads a row that T2 has modified but not yet committed — then T2 rolls back, and T1 acted on a value that never actually existed. The most severe anomaly; almost no real database allows it by default (SQL's "Read Uncommitted" permits it in theory, but Postgres, for one, doesn't actually implement a level that allows it).
Non-repeatable read T1 reads the same row twice in one transaction and gets different values, because T2 committed a change to that row in between. Breaks the assumption that a transaction sees one consistent world — a report that sums a value at the start and re-checks it at the end can disagree with itself.
Phantom read T1 re-runs the same range query twice (e.g. "count orders over $100") and gets a different set of rows, because T2 committed an INSERT/ DELETE matching that range in between. Like a non-repeatable read but for row existence, not row values — row-level locks can't prevent it, since the phantom row didn't exist to lock yet.
Lost update / write skew Two transactions each read a value, compute a new value from it, and write back — and one write silently clobbers the other, or both writes individually look fine but together they violate an invariant neither transaction alone broke. The one that doesn't announce itself with an error. Both transactions commit successfully; the bug is in the data, discovered later if at all. The stepper widget below is built around exactly this anomaly, because it's the one most engineers underestimate.

The SQL standard's isolation levels

The SQL standard defines four isolation levels purely in terms of which of the above anomalies they permit — a specification of the ceiling on bad behavior, not of how the database has to achieve it:

! Caution — the standard is a floor, not a spec of behavior

Real databases routinely give you more than the standard requires at a given level, and which anomalies remain possible is engine-specific — this is a frequent interview trap. Two concrete deviations in Postgres, the reference most backend engineers meet first:

  • Postgres has no true Read Uncommitted — requesting it silently gets you Read Committed. Dirty reads are simply not something Postgres will ever show you.
  • Postgres's Repeatable Read is implemented as snapshot isolation, which happens to also prevent phantom reads — stricter than the standard requires at that name. But (this is the important part) snapshot isolation does not prevent write skew, an anomaly the 1995 SQL standard's anomaly table doesn't even name. "Repeatable Read" sounding safe is exactly the trap the write-skew scenario in the widget below is built to demonstrate.

The takeaway: know the anomaly you're worried about, then check your specific database's docs for that level — never assume from the name alone.

MVCC vs. locking: two ways to implement isolation

The isolation levels above describe what is guaranteed; there are two fundamentally different engineering approaches to actually delivering it:

Two-phase locking (2PL)
A transaction acquires a shared (read) or exclusive (write) lock on each row it touches, holds every lock until commit, and never acquires a new lock after releasing one (the "two phases": growing, then shrinking). Simple to reason about, but readers block writers and writers block readers — a long-running report can stall unrelated writes to rows it merely reads.
MVCC (multi-version concurrency control)
Instead of locking rows for reads, the database keeps multiple versions of each row and gives every transaction a consistent snapshot — reads never block writes and writes never block reads, because a reader simply sees the version of the row that was committed as of its snapshot, while a writer creates a new version. This is what Postgres, MySQL/InnoDB, and Oracle all use, and it's why "a slow SELECT" almost never blocks an unrelated UPDATE in those engines the way naive 2PL would.

MVCC isn't free: old row versions have to be garbage-collected once no active transaction can still see them (Postgres's VACUUM), and a long-running transaction that holds a snapshot open prevents that cleanup — table bloat from a forgotten open transaction is a genuine, recurring 3-AM incident in Postgres shops. MVCC still needs some locking for write-write conflicts (two transactions can't both win when they update the very same row); that's the "first updater wins" rule the lost-update scenario below walks through.

Deadlocks

Whenever transactions acquire locks in different orders, they can each end up waiting on a lock the other holds — a deadlock. T1 locks row A then waits for row B; T2 locks row B then waits for row A; neither can ever proceed. Databases detect this by building a wait-for graph (an edge from transaction X to Y whenever X is blocked waiting on a lock Y holds) and periodically checking for a cycle; when one's found, the database picks a victim — usually the transaction that's done the least work — and aborts it with a deadlock error, letting the other proceed.

✓ Tip

Deadlocks are a code-review-catchable class of bug, not a database flaw to route around with retries alone: the fix is a consistent lock/update ordering across every code path (e.g. always update the lower account ID first in a transfer), plus keeping transactions short so the window for a conflicting interleaving is small. Retry-on-deadlock is a reasonable safety net on top of that discipline, not a substitute for it.

Interactive — two-transaction stepper

    ★ ML-systems bridge

    Write skew shows up constantly in ML infrastructure under a different name. Two feature pipeline runs that each read "current row count for partition X," decide independently that it's safe to proceed, and both write — that's the on-call-doctors scenario with partitions instead of doctors. A model registry's "promote to production" transition guarded by "read current production model, check it's not already being promoted, then flip the pointer" has the exact same shape: two concurrent promotion jobs can both pass the check under Repeatable Read and both flip the pointer, leaving the registry in a state neither job intended. The fix is the same one covered here — either SELECT ... FOR UPDATE to take an explicit lock on the rows the invariant depends on, or run the transaction at SERIALIZABLE and handle the resulting serialization failure with a retry. "It passed the check" is not the same as "it's still true when I commit" — the entire lesson of this page in one sentence.

    1. T1 reads a row twice in the same transaction and gets two different values, because T2 committed an update to that row in between. Which isolation level is the minimum that prevents this, per the SQL standard's anomaly table?

    This is a non-repeatable read by definition. Read Committed permits it — each statement sees a fresh snapshot of committed data, so T1's second read can legitimately differ from its first. Repeatable Read (via a snapshot taken at transaction start) is the first level in the standard's table that rules it out.

    2. Two transactions each check "at least 2 of N rows satisfy condition X" before independently flipping a different row from true to false, and both commit, leaving fewer than the required minimum. Running both at Postgres's Repeatable Read (snapshot isolation), what happens?

    This is the write-skew trap: Repeatable Read/snapshot isolation only blocks conflicting writes to the *same* row. Two transactions writing to disjoint rows based on a shared read never trip that check, so the invariant they were jointly protecting can still be violated. Preventing it requires either SERIALIZABLE or an explicit SELECT ... FOR UPDATE on the rows the check depends on.

    3. Under MVCC, a long-running analytics query starts a transaction, then takes 10 minutes to finish. What's the main operational cost of that, even though the query never blocks any writer?

    MVCC's defining feature is that readers don't block writers — but the trade-off is that old row versions can't be reclaimed while any transaction might still need to see them. A long-open transaction (even a read-only one) pins the vacuum horizon, which is why "a report that's been running for hours" is a classic cause of unexpected table bloat in Postgres.
